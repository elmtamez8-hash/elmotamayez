# Gotchas — Privacy, retention, erasure and offboarding

Moved verbatim from `CLAUDE.md` (the rule headlines stay there). Read this file before changing `Modules/Compliance/`, retention sweeps, data requests, legal holds, teacher exit. Bullets that say «above» may now point into another file in `docs/gotchas/`.

- **The three expiry behaviours are not interchangeable, and `Anonymise` is unavailable wherever the identifying column is `NOT NULL`.** `exam_attempts.student_user_id` and `attendances.student_user_id` both are, and `->change()` on either re-declares the column and REBUILDS the table on SQLite — a trade this repository has refused twice in writing. So `exam_attempt` expires as `Delete` (its `exam_answers` are already gone at 1095 days, so at five years the row is a bare score naming a person for no reader), while `attendances` anonymises by clearing the FREE TEXT and keeping the row: deleting a seat breaks `ReconcileCreditBalancesJob`'s "one consumption entry per seat" invariant for ever, with no cause anybody can find. ⚠️ **And `Archive` needs a mark or it never converges**: "older than N days" is true again tomorrow, so `media_assets.archived_at` is what stops the same recording being re-archived — and the same file re-deleted at the provider, billed each time — every night, counted afresh in `retention_sweep_runs` each night. `Delete` cannot show that defect in a test, because a deleted row does not come back; the idempotency fixture therefore MUST include an archive category.
- **A legal hold has a FOURTH door, and it is the one with nobody asking.** `PlaceLegalHold` suspends an erasure REQUEST; retention needs no request at all, so a hold that only touched `data_requests` would let the nightly sweep delete the exact rows a court ordered kept — on a schedule, with the hold row sitting green beside it and not one line logged. `RunRetentionSweepJob` resolves the held subject ids once and passes them down through `PersonalDataOwner::expire()`, so `Compliance` still names no module's table and no module imports `LegalHold`. Two shapes of that exemption are traps: on `lesson_progress` it has to run through `enrollment_id` (the table names nobody), and on a nullable column a bare `whereNotIn` spares nothing — `NULL NOT IN (…)` is NULL — while the `orWhereNull` that fixes it ORs at the TOP level unless it is grouped, discarding the age bound and deleting the whole table.
- **Retention on a class recording is a write to the COURSE TREE, and the seventh road to 016's worst defect.** A recording IS a lesson, so expiring the asset without archiving the lesson leaves an item pointing at an id nothing resolves. It is survivable today only because `progressEligible()` drops any lesson carrying a `class_session_id` — make recordings countable tomorrow and every enrolled student is capped below 100% for ever. `FR-031ب` therefore mandates `CourseStructureChanged`, fired **once per COURSE**: fifty recordings ageing out together would otherwise run fifty full resyncs over one identical set of enrolments, which is what actually threatens the sweep's timeout. The dedup lives in the listener, where the courses are known, which is why `Media` announces a BATCH of `(id, owner_type, owner_id)` and each module claims the type it recognises. And `MediaProviderResolver::for()` reads the asset's `provider` COLUMN and makes that class — so a test mock bound to `MediaProviderInterface` is never consulted, the real provider runs, and "no second deletion" passes by counting zero of both.
- **`FR-037` ends the teacher's access and their ASSISTANTS', never their students'.** The obvious implementation deletes every `workspace_members` row for the workspace, which takes away the course the student bought one requirement after the platform promised it stays. In production a student is a member of no workspace at all, so the exclusion is usually a no-op — **which is exactly why it needs its own test**: a guard that only bites in the unusual case is one nobody notices missing. And the scoping half is spatie's team id: `model_has_roles` puts `team_id` in its primary key, so a role removal with none set takes the job the assistant still holds with the teacher who is staying.
- **The clearance bridge is a CONTRACT because `ContextIsolationTest` says so — and that test did not cover `Compliance` until this phase widened it.** 013's own design document cites the guard as the reason a departing teacher's settlement is asked rather than queried, and then records, correctly, that the sweep read `Modules/Settlement/` and `Modules/Payments/` alone. **A cited guard that does not run is worse than none: it ends the argument without settling it.** ⚠️ The vocabulary half of that test then fired on `$this->settlement_cleared_at` inside a Resource — comments are stripped before the scan, so the property access itself is the offence. The fix is a method on the MODEL (`duesCleared()`), not a renamed column: the boundary belongs at the edge of the payload, and a screen that talks about settlement is one field away from carrying a number from it.
- **`FR-036` cannot be a row in `data_categories`, and the reason generalises.** That table holds one number and one behaviour PER CATEGORY, for everybody; the requirement asks that a departing teacher's recordings "respect the rights of the students who appear in them" — a duration belonging to OTHER PEOPLE and different for every asset. `media_assets.retain_until` is the exception, and it is an **OR** against the age rule rather than an extra `AND`: written as a further condition it could only ever shorten, so a student two months into a paid year loses the lesson on its second birthday — the requirement inverted. ⚠️ And a null `expires_at` means access that does **not** expire, which is the default shape of an enrolment here: a naive "latest expiry" reads null and would delete every recording on the platform the day its teacher left, so the directory answers a date **and a boolean**, and the boolean is the load-bearing half.
- **The register of processors is checked against the CODE, never against itself.** A test that walked `data_processors` asserting each row is well-formed proves the seeder agrees with the seeder, and stays green on the day somebody integrates a vendor and writes no row — the only failure SC-011 is about. `ProcessorAllowlistTest` starts from the tagged notification channels and from an outbound delivery actually made under `Http::preventStrayRequests()`, so a second endpoint nobody declared shows up as a stray request rather than as a passing comparison of two config strings.
- **A public reporting route earns its exposure with a CONSTANT response, not with a login.** `POST /privacy/breach-reports` carries no `auth:sanctum` because the best-known leaks are reported by people who hold no account — requiring one restricts the report to the population least likely to be making it. What makes it safe is that it returns no uuid, no id, no count and no echo: an unauthenticated endpoint that varied its answer by what it found would tell an attacker whether an address holds an account or whether a report already exists, which is the payment webhook's uniform-`202` rule reached from a second direction. The incident's SCOPE is likewise absent from the request — accepted there, anyone could assert the size of an incident into our own record of it — and `status` too, since a reporter who could open a report already `closed` is a reporter who can hide one.
- **`notified` is refused until BOTH notification timestamps exist, and neither is ever re-stamped.** The authority and the people whose data leaked are two obligations on two clocks, which is why `breach_reports` carries two columns rather than a flag: a status anybody can set to `notified` while one of them is null is a row that reads as complete over an obligation nobody discharged, and it also stops the derived countdown beside it. The timestamps are the record of WHEN, measured against a deadline, so re-stamping one on a later edit moves a legal fact to whenever somebody last touched the row — always inside the window, however late the notification actually was. The refusal is raised before the row is saved, so a rejected PATCH leaves the record exactly as it was rather than half-applied.
- **`ExecuteTeacherOffboarding` could never complete an exit for an officer whose own workspace differed, and one workspace in every fixture is what hid it.** All three of its conditional UPDATEs were workspace-scoped, and `WorkspaceContext::id()` falls back to `users.last_workspace_id` for every user including platform staff — so each statement ANDed the wrong id, matched zero rows, and the Action answered «لم تنتهِ مهلةُ الإخطار بعد» about a notice that ran out a week ago, permanently, with nothing logged. Found from spec 010's side by a Community test that needed a second teacher for an unrelated reason. **Any test of a platform-permission write needs TWO workspaces**, the same rule the audit chain already wrote down for platform READS.
- **`PersonalDataContractCoverageTest` is a per-MODULE guard, and a NEW TABLE inside a registered module is invisible to it.** Its own docblock says so; spec 010's Phase 8 then shipped `announcements.author_user_id` with no data category, no export path and no expiry, and 1916 tests stayed green. The table-level version was measured before that hole was written down: it lights up **forty-two** tables across every module, which is the guard-silenced-by-exemptions shape that file already rejected once. So the limit is recorded rather than half-closed — **when you add a table with a personal column to an existing module, add its `data_categories` row and its three walks in the same change, because nothing will tell you.**
