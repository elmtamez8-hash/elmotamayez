# Gotchas — Courses, the tree, lessons and learning access

Moved verbatim from `CLAUDE.md` (the rule headlines stay there). Read this file before changing `Modules/Courses/`, `Modules/Learning/`, cohorts, lesson doors, progress. Bullets that say «above» may now point into another file in `docs/gotchas/`.

- **Reordering the tree is a write to ACCESS RIGHTS, not to a display order.** `Enrollment::accessTo()` derives what a student may open from the triplet of section, chapter and lesson positions, so moving an item changes who can reach what, immediately. Every reorder therefore sends the COMPLETE sibling list plus `structure_version`, and `StructureVersion::claim()` — one conditional `UPDATE … WHERE structure_version = ?`, the seat idiom — is both the check and the bump. Comparing a loaded model and incrementing later is the lost update it exists to prevent: two teachers both pass, both write, neither sees a 409. Never `lockForUpdate()`, a no-op on SQLite.
- **The progress denominator excludes a recording through BOTH its doors.** A recording is entitled by a SEAT, not by enrolment, so `countableForProgress()` drops it *and* `accessTo()` refuses to let it stand as a prerequisite. One without the other still bricks the course: left in the denominator, a seatless student can never reach 100%; left in the chain, it locks everything after it. This is the family of the spec's worst defect — an item that enters the denominator and can never be completed caps every enrolled student below 100%, so `CourseCompleted` never fires and no certificate ever issues, permanently. Six roads led there and all six are named in `docs/README.md`; the two that outlive publishing are **archiving** and **deleting** the last item a student had left, which is why anything moving the countable set fires `CourseStructureChanged` → `ResyncCourseProgress`. `progress_pct` is otherwise written when a lesson is completed and at no other moment.
- **`LessonEditor` renders by `asset_kind`, and the ONE type that had a page of its own is where the bug came from.** Video was routed to `/manage/courses/{course}/lessons/{lesson}` — a screen whose heading said «فيديو الدرس» and whose input was `accept="video/*"` — while the course overview linked EVERY item to it whatever its type. So opening an article offered to upload a video for it, and `RequestUploadTicket` refused with «هذا النوع من العناصر لا يحمل ملفاً خاصاً به»: a correct answer to a request the screen invented. That page also never fetched the lesson, so it never knew about an existing video — a teacher who had already uploaded one was told «لا يوجد فيديو لهذا الدرس بعد» on every visit, with no way to replace it or reach its captions. `VideoEditor` joins the `AssetUploader` family with the others and the page is deleted; the overview links to `/content?lesson={uuid}`. **The rule underneath: a screen that does not know an item's type must not offer an action that depends on it** — `LessonTypeRegistry` answers that question and `LessonResource` already sends `family` and `asset_kind` so nothing restates it in TypeScript.
- **A publish is previewed by the code that performs it, never by an estimate beside it.** `PreviewPublishImpact` borrows `PublishTreeNodes::resolve()`, its `assertReady()`, `Lesson::progressEligible()`, `CourseProgress::percentage()` and `ExamGateSatisfaction`; the ONE thing it simulates is the three status conditions, because that is what a publish changes. A second denominator computed "just for the preview" is how the teacher gets shown a number no student ever had (`SC-018`). The preview also returns the item list it costed, and the client publishes THAT list — deriving the draft set on both sides is the same drift wearing a different face.
- **Authored text is Markdown, rendered per response, never stored as HTML.** `MarkdownRenderer` strips raw HTML rather than escaping it, so the allowlist is the Markdown feature set itself — there is no sanitiser configuration to get wrong. A stored `content_html` would be a second copy of the same words that drifts from the source at the first typo fix, and a stored-HTML column is an XSS sink with a teacher's keyboard attached to it.
- **`/learn/lessons/{lesson}` is the ONLY surface that plays a lesson, so it carries the author's branch too.** It required an enrolment, which no teacher holds in their own workspace — so the recording button on the teacher's own session page, the single link to a published recording, answered 404 about a video they had just taught. Membership of the lesson's workspace is the predicate, spelled in Learning rather than calling Media's Action across the boundary; it is not a widening of the student route, because a student is never a workspace member (only `AcceptInvitation` and `CreateWorkspace` write that pivot). `lessonPayload()` takes a `LessonAccess` rather than an `Enrollment` so all three entrances stay one payload.
- **⛔ THE MANDATORY-GROUP LOCK WAS REPEALED, AND THIS ENTRY USED TO DESCRIBE IT AS LIVE.** 021 · FR-028أ made membership a condition on opening the curriculum, and `LessonGate` refused every lesson with `no_cohort` while a joinable group existed and the reader was in none. **034 · FR-015 abolishes that condition in as many words** — «يُلغي هذا شرطَ ٤٢١ · FR-028أ ويُبقي مقصدَ FR-028ب», owner-decided 2026-09-11 — so the curriculum opens for a student with no group and a sentence above it says who does the placing. **`LessonGate` no longer consults groups at all**: both `NO_COHORT` branches, `CohortGate::locks()` and the `LessonAccess::NO_COHORT` constant are gone, because a code with a reader and no writer is how `ClassSessionStatus::Interrupted` survived a whole phase looking implemented. `CohortGate::describe()` is the only reader left and it produces a SENTENCE, never a lock. ⚠️ **The repeal shipped 2026-09-14 and the lock had already bitten**: a teacher created the first group of «Laravel Mastery» on 2026-09-10 and the curriculum shut, retroactively, on **4 of 4 enrolments** that had signed up on 2026-08-28 — one of them at 100% with every lesson completed. Creating a group must never repossess what a student already bought, which is `CohortSessionVisibility`'s rule (a booked seat stays on the timetable) reached through the curriculum instead. **What is still true**: `joinable_exists` remains on the payload — it no longer decides anything, it picks which of two sentences the server sends («not placed yet» vs «no group open at all») — and the verdict travels on `cohort_gate` and the page READS it. Re-deriving `status === "open" && !is_full` in TypeScript is still the two-spellings defect that made a paid-for recording unreachable in 018.
- **A FACTORY WHOSE DEFAULTS NAME THE SAME PARENT TWICE BUILDS A NODE THE PRODUCT CANNOT REACH, and the tree walk and the validator disagree about it in silence.** `ChapterFactory` listed `section_id => Section::factory()` **and** `course_id => Course::factory()`, and `LessonFactory` listed all three of `course_id`/`section_id`/`chapter_id` as independent factories — so one bare `Lesson::factory()` created **four unrelated courses** and a lesson none of them contained. `ManageChapters::create()` and `ManageLessons::create()` both derive those ids from the one parent the caller named, and both say in their own comments that this is the defect they exist to prevent; the factories were the only writers in the tree that did not. What it looks like from a teacher's screen: the course outline walks `section_id` and **shows** the chapter, while `StoreLessonRequest`'s `WorkspaceRules::exists('course_chapters','uuid')->where('course_id', $course)` refuses every item added to it — «القيمة المختارة في chapter uuid غير موجودة», on a chapter sitting right there. Eight such chapters (and their eight lessons) reached the development database on 2026-09-02 and were reported as a product defect a week later. ⚠️ **The caller was never found and this sentence says so on purpose**: no seeder in the tree calls either factory, `git log -S` finds none that ever did, and the rows carry pure `LessonFactory` defaults with `course_id` pinned to a marketplace demo course — measured, not inferred. What matters is that the MECHANISM was in the factories, so it did not need a caller anybody could name. ⚠️ **And the countable set was wrong in the direction that caps students for ever**: each stray lesson was `Published` with no `class_session_id`, so it sat in `countableForProgress()` for a course whose tree could never reach it — the forever-below-100% family, on eight courses with live enrolments. The repair derives from the structural parent exactly as the Actions do (`chapter.course_id ← section`, then `lesson.section_id`/`course_id` ← the corrected chapter) and fires `CourseStructureChanged` for every course on both sides of the move. ⚠️ **No existing test could see any of it**: every fixture in the suite pins the parents by hand, which is precisely what a factory with self-contradicting defaults teaches everybody to do — `tests/Feature/Courses/TreeFactoryConsistencyTest.php` is the one that drives the bare call. Two details in the fix are load-bearing: the derived key must be named **below** the parent it reads (`expandAttributes()` walks the definition in order and hands each closure only what it has already resolved), and the read is `DB::table(...)`, never `Model::find()`, which runs under `WorkspaceScope` and returns null for a fixture whose current workspace is not the factory's hardcoded `1`. The residual ceiling is written beside it: `->for($course)` overrides `course_id` before the closure runs and still gets a chapter of its own, so pin the chapter when the course has to be a particular one.
- **A SCOPED RELATION READ ON THE STUDENT'S PATH RETURNS AN EMPTY COURSE, NOT AN ERROR — AND `Enrollment::course()` CARRYING THE BYPASS DOES NOT COVER WHAT HANGS OFF IT.** `course()` was fixed in spec 032 and says so in a comment; `Course::lessons()` beneath it is a **fresh query on `Lesson`** and runs `WorkspaceScope` again, and `WorkspaceContext::id()` falls back to `users.last_workspace_id` — stamped on every student a teacher, an invitation or a seeder ever added to a workspace (six rows with role `student` measured on a real database, 2026-09-09). So `orderedLessons()` answered **zero rows** for any such student whose stamp names a DIFFERENT workspace than the course they bought — a student teacher A added to their workspace and who then enrolled with teacher B, which is the ordinary shape on a marketplace: `/courses/{uuid}/curriculum` returned `200` with an empty tree, a course they had paid for reading as if nothing had been written in it, with no error anywhere and every guard below it working correctly. ⚠️ **The eager load is the second half, not a detail**: a scoped `->with(['section','chapter'])` returns null for both, and `loadMissing` inside `isVisibleChain()` then finds them «already loaded» and does not refetch — so a published lesson reads as invisible and is dropped by a guard written correctly. It is the CLAUDE.md rule about a preload defeating a bypass, reached from the relation side instead of the controller side. ⚠️ **And the defect is invisible to every fixture in the tree**, because `CurriculumStudentContextTest`'s own subject is the student with a NULL context — the self-registered one — and for them the scope is inert, so the file that exists to prove this endpoint works was green over it. The stamped student is that file's missing mirror; it was found by a spec 026 release test that only needed a stamped student for an unrelated reason. **Any test of a student-facing read needs BOTH shapes** — null context and stamped-elsewhere — and the stamping must be `forceFill`, since `last_workspace_id` is in `User::$guarded` and `create([...])` drops it in silence, rebuilding the null-context student and passing against the broken build.
- **«THE AUTHOR» IS THE PIVOT ROLE, NEVER MERE MEMBERSHIP — AND THE THIRD DOOR OPENED PAID CONTENT.** Three places asked `workspaces()->where('workspaces.id', …)->exists()` and answered yes to everything in that workspace **including drafts**, above every status check: `IssuePlaybackGrant::mayWatch()`, `mayWatchMany()`, and `/learn/lessons/{uuid}`, the only surface in the product that opens a lesson page. Each carried the comment «a student is not a workspace member — the only writers of that pivot are `AcceptInvitation` and `CreateWorkspace`», which is true of a self-registered student and **false in general**: `addWorkspaceMember`, `UpdateWorkspaceMemberRole`, `CreateAssistantAssignment` and both seeders write it too, and six `student` rows were measured live. The predicate is `wherePivot('role', '!=', Roles::STUDENT)` — asked in the negative, as `User::teachesOnPlatform()` does, so an unknown custom role falls toward refusal. ⚠️ **The lesson-page door is the worst of the three and needs a DIFFERENT fixture to see**: its enrolment branch runs first, so an enrolled member never reaches the membership line — the exposure is a student-role member with **no enrolment in that course**, who was handed `LessonAccess::allow()` for every lesson in the workspace, published ones included. A mutation test built on the enrolled member is green with the bug fully present.
- **LESSON CONTENT HAS FOUR DOORS, NOT ONE — AND THE ONE THAT ACTUALLY SERVES THE FILE ENDS AT `hasActiveEnrollment`.** Spec 026 added two axes to every item («who is this for» and «when does it appear»), and asking them at the curriculum payload alone would have been a screen that hides a button, which is not a guard. The four are `LessonGate::for()`/`forTree()` (the curriculum and the lesson page), `IssuePlaybackGrant::mayWatch()`/`mayWatchMany()` (the video), `StartAttempt::guardSessionContent()` (sitting a paper), and `ExamController::index()` + `PracticePool::questionsFor()` (the exam tab and the practice bank). They do **not** share a code path: `mayWatch()` walks its own chain — author, `is_free`, withholding, seat, then `hasActiveEnrollment` — and returns without ever consulting the gate, which is exactly how spec 018 produced a **paid** recording that `mayWatch()` allowed and the sequence refused, unreachable from the only door it opens through. So the verdict is ONE class, `Courses\Support\LessonAudience`, asked from all four; a rule written four times is four rules that agree until the first one moves. ⚠️ **And no door asks for a code** (`=== 'out_of_scope'`) — only `!== null`: naming the code is a second spelling of «is it hidden» that diverges at the first code anybody adds, and the author exemption lives INSIDE the class for the same reason (four exemptions is four places to forget the pivot-role predicate). ⚠️ **The exam doors reach the verdict through `lessons`, because `exams` carries neither axis**: the link is a lesson of type `exam` naming the paper in `reference_id`, so an exam's audience is its lesson's audience — invent a column on `exams` and it is a second answer to a question the tree already answers. ⚠️ **The two LIST doors need a candidate narrowing or they read the whole bank**, and that narrowing (`release_session_id IS NOT NULL OR a scope row exists`) sits in `LessonAudience::couldBeHidden()` beside the axes themselves — put it in the callers and a third axis added later is silently blind on the lists alone. ⚠️ **And `BuildPracticeFromMistakes` bypasses `questionsFor()` entirely**, building its paper from the notebook's ids, so the exclusion is written there too — with the `whereNull('lesson_id')` arm grouped beside it, since `questions.lesson_id` is nullable and `NULL NOT IN (…)` is NULL, which would drop every bank question that has no lesson instead of keeping it.
- **A deleted course KEEPS its slug, and every door that writes one has to agree with the index.** `courses.slug` carries a platform-wide unique index that counts soft-deleted rows, and that is the decision, not an accident: `/courses/{slug}` is one namespace read by guests and search engines, so freeing a deleted course's slug would let a course in ANOTHER workspace take the address over, and every shared link and search result would start serving somebody else's course under the first teacher's reputation. `Rule::unique` in both requests is a raw query and already counted the deleted row; the panel field had no rule at all (a taken slug was a raw integrity 500) and now carries `->unique(ignoreRecord: true)`, which is also raw. The one that disagreed was `CourseSlug::taken()`: the `SoftDeletes` scope hid the deleted row, `for()` handed its slug to a new course with the same title, and `CreateCourse` died on the index. It asks `withTrashed()` now. There is no restore surface; if one is ever added, the restored course still owns its slug by construction. `DeletedCourseSlugTest` drives all three doors.
- **A COURSE'S VISIBILITY IS THE TEACHER'S CALL, NOT `courses.update`'s (owner decision 2026-09-26).** An assistant holds `courses.update` and `courses.create` and keeps editing content, but switching public/private is `CoursePolicy::changeVisibility()` (update) and `chooseVisibility()` (create, asked in `CreateCourse` only when the value is not the default `public`), both reading `User::decidesCourseVisibilityIn()`: a `tenant-owner`/`teacher` pivot row in that workspace, asked in the POSITIVE because this predicate grants, and walled by a live assistant assignment whatever the role is named. The update door asks only on a CHANGE, so a client echoing the current value is not refused. The screens never guess from the role: the edit page reads `can_change_visibility` (stamped in `withReach()` beside the blockers, absent on the index — a Resource runs per row) and the create page reads `can_choose_course_visibility` from `/auth/me`; absent means hidden. Not a spatie permission on purpose — the roles screen could then hand it to an assistant with one tick, and a new permission row never reaches an existing database without a migration.
