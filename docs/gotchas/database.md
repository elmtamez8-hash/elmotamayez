# Gotchas — Database, migrations, MySQL vs SQLite, catalogues

Moved verbatim from `CLAUDE.md` (the rule headlines stay there). Read this file before changing any migration, seeder, raw query, Eloquent relation or runtime catalogue. Bullets that say «above» may now point into another file in `docs/gotchas/`.

- **A Resource runs once per row, so a query inside one is an N+1 by construction.** `ClassSessionResource` asked every published session where its recording went — one `lessons` SELECT per row, on both the teacher's calendar and every student's timetable. The fix is the `recordingLesson` relation plus eager loading at each call site; the fallback query stays as the last branch, because a caller who forgets would otherwise publish a recording with no way in, silently. `QueryBudgetTest` fails if the eager load is dropped.
- **`whereDate()` costs the index the column was given.** MySQL cannot use `(workspace_id, starts_on, ends_on)` once a function wraps the column, and `FreezePeriod::covering()` is consulted on every booking, every schedule and every absentee sweep. Compare against a date string instead. When the column is a *timestamp* and the bound is a date, the upper bound is the START of the next day — `<= ends_on` silently drops everything after midnight on the last day.
- Module directory names are matched literally by `Module::registerMigrations()`/`registerFactories()`. Migrations must live in `Database/Migrations` (capital M) — a casing mismatch resolves fine on Windows/macOS and silently loads **zero** migrations on Linux.
- **Renumbering comes before the index, and `chunkById` before `chunk`.** 016 added `unique(chapter_id, order)` to rows that already held duplicates, so the densify migration must run before the index migration or the deploy fails on live data. And the uuid backfill walks with `chunkById`: `chunk` paginates by OFFSET while the predicate (`uuid IS NULL`) shrinks under it, so every page after the first skips as many rows as the previous page fixed — and reports success. The parking offset in a reorder is `max(order) + 1` for the same reason a constant fails: `max(order)` tracks a group's LIFETIME create count, not its row count.
- **Dropping a column drops its index FIRST, in its own statement — and only SQLite will tell you.** MySQL discards a single-column index along with its column and never complains, so `dropColumn()` alone reads as correct; SQLite's native `ALTER TABLE … DROP COLUMN` **refuses an indexed column**, and every test in this repository runs on in-memory SQLite. So the redundant-looking `dropIndex(['col'])` above it is the only form that runs at all here. Two separate `Schema::table` closures, for the same reason `->change()` is avoided: a multi-alteration on SQLite is a table rebuild. The mirror of this is the rollback — a `down()` that cannot restore what was there must SAY so above itself (`_000600_drop_exam_id_from_questions`), because a column re-added empty reads as data and holds none.
- **`insertOrIgnore` writes a row without booting the model, so `HasUuid` never fires** — and on MySQL the resulting NOT NULL violation is downgraded to a warning and `''` is stored, after which *every* later entry on the platform collides with that row on `unique(uuid)`, is read as "already recorded", and is silently skipped. The ledger stops after one row while every caller reports success. **This is a rule about the insert ARRAY, not a ban on the call.** `CreditLedger::writeEntry()` uses `insertOrIgnore` deliberately and correctly: the unique index is the idempotency guard, and `uuid` and `created_at` are passed EXPLICITLY because the model layer is not there to supply them. `create()` in a try/catch was rejected in R7 — it makes a real failure (a null, a foreign key, an out-of-range value) indistinguishable from a duplicate. What `insertOrIgnore` needs instead is the read-back: zero rows means *either* a duplicate or a swallowed failure, so the entry is fetched by its key and a miss **throws** rather than returning null.
- **The floor comparison is CAST to signed, and MySQL alone will tell you why.** `remaining + limit >= n` evaluated at `remaining = −3` on `unsignedInteger` columns raises **ERROR 1690, BIGINT UNSIGNED value is out of range** — and SQLite has no unsigned arithmetic to overflow, so no local test can ever reproduce it. The guard is `CAST(... AS SIGNED)` in `CreditLedger::applyToBalance()` and the signed column widths in the migration; both carry the reason beside them, because the failing environment is the one nobody runs the suite in.
- **A unique index carrying a nullable column does not bite, and 008 has TWO of them.** `concept_stats.lesson_id` and `unlock_rules.course_id` are `NOT NULL` with **0** meaning "no narrower scope", because NULL never equals NULL: `upsert()` matches nothing on the one row every workspace reads, INSERTs a new one every night, and after a month the screen shows whichever came back first — a number thirty days old beside the correct one, with not one error logged. `RollupIdempotencyTest` runs the job TWICE for that reason; one run is green for ever and proves the opposite. The price of the sentinel is that `(int) null === 0`, so a failed uuid resolve addresses the DEFAULT row — `UnlockRuleController` guards it with `abort_if` before writing.
- **`SeedCommand` runs every seeder inside `Model::unguarded()`.** So `$fillable` protects the application and not the seeders: dropping `exam_id` from `Question::$fillable` in 008 left `DemoDataSeeder` writing the column, which was the last writer standing between the codebase and `T180`'s drop. Any claim of the form "nothing writes this column any more" has to be checked against `database/seeders/` separately, because the guard everyone reasons from is switched off there.
- **A column added by a migration and not to `$fillable` is a column that silently never gets written — and spec 013 shipped THREE of them on one table.** `date_of_birth`, `dob_is_estimated` and `guardian_contact` landed in the `student_profiles` migration; `RegisterStudent` passes all three to `create()`; mass assignment **discards a non-fillable key in silence** — no exception, no log, a `201` and a profile row with three nulls in it. So the guardian-consent gate FR-009 hangs on the student's AGE never fired for anyone who signed up themselves, the contact they typed for their guardian was thrown away, and the coming-of-age sweep walked an empty set. ⚠️ **Every US1 assertion was correct and none of them could see it**: they were made against the response body and against `parent_student_relations`, and the response echoes what was submitted rather than what was stored. It was found by MEASUREMENT — one `tinker` round-trip — while writing the sweep that reads the column two phases later. `ownership_transferred_at` is deliberately NOT fillable for the opposite reason: it is claimed by a conditional UPDATE, the `captured_order_id` rule. **And the same shape ruins a fixture**: `created_at` is not fillable either, so a test row aged inside a `create()` array is born today, and every retention assertion over it passes against data too young to sweep — proving the opposite of what it claims. Age by query.
- **A `date` column compared against a bare date string is off by one day, and the day it loses is the only one that matters.** The model's date format writes `2008-08-21 00:00:00` into `student_profiles.date_of_birth`, so `<= '2008-08-21'` compares as a STRING and is FALSE for the person born that day: `TransferDataOwnershipJob` skipped them and told them tomorrow — on a date the law attaches meaning to. The predicate is `< (threshold + 1 day)`, which is right on both engines. **On MySQL the `<=` form works**, so no local test of it would ever have disagreed with production; the same boundary already cost `FreezePeriod::covering()` and a settlement close their own fixes.
- **`->with('relation:id,uuid,name')` on a User relation selects a column that does not exist, and every screen using it renders a BLANK NAME.** `users` has no `name`; it is an accessor over `first_name`/`last_name`, so a constrained eager load that omits those two returns `'' . ' ' . ''`. No error, no warning, a `200` — and **six call sites across four modules** shipped that way: the assistants team, the accommodations list, the submissions list, the essay grading board, and `/manage/billing/students`, the screen where a teacher decides whom to chase for money, listing every student as «». Found by walking the product by hand (spec 010 · `T186`), never by a test: the suite's own fixtures read the model, not the payload, and `ReportCardSegmentController` had the correct spelling one file away the whole time. The rule generalises past this column — **a constrained eager load must name the columns the ACCESSOR reads, not the attribute the Resource prints.**
- **A catalogue row a release adds never reaches an existing database, and this tree has now hit it THREE times.** `NotificationTemplateSeeder`, `DataCategorySeeder` and `GamificationCatalogSeeder` are all reference data read at runtime, all seeded only by `migrate:fresh --seed`, and all silent when a row is missing: a notification with no template is dropped, a data category with no row is never swept, and `AwardPoints` returns without a word when the action key is unknown. So `helpful_answer` sat in the seeder and was absent from a real database — a teacher endorsed a student's answer, `is_helpful` turned true, the event fired, the listener ran, and **zero points were awarded, permanently, with nothing logged.** Every test passed because `tests/Pest.php` seeds all three catalogues before every case, so every assertion was made against a table production did not have. Each seeder now has **two modes** — `run()` overwrites (development), `seedMissing()` writes only what is absent (`firstOrCreate`) — plus a migration calling the second. ⚠️ The two modes are not ceremony: every row in all three is editable from `/admin`, so an `updateOrCreate` in the deploy path resets every duration, every xp value and every Arabic template body an operator ever tuned, on every release. **When you add a row to a runtime catalogue, add the backfill migration in the same change.**
- **A required field validated against a runtime catalogue is the ONLY one of the four that fails loudly — and it fails at the front door.** `regions` is the fourth catalogue in this tree read at run time (`notification_templates`, `data_categories`, `gamification_actions`), and the other three go quiet when a row is missing: a notification is dropped, a category is never swept, an award returns without a word. `region_slug` is **required** by `RegisterStudentRequest` and validated with `Rule::in` against the rows, so an empty table on a live database answers **422 to every new registration** in front of a picker with nothing in it. The seeder ships with a `seedMissing()` backfill migration in the same change, and `tests/Pest.php` seeds it before every Feature test — which is exactly why the migration matters: the suite is green over a table production may not have. ⚠️ And the payload carries the **slug**, never the row id (`grade_level_slug` one file away is the precedent), while `student_profiles.region_id` is the FK — resolved inside `RegisterStudent`, where an unknown slug becomes NULL rather than an error, because the form request has already refused everything outside the catalogue.
- **A dashboard number is stored as a numerator and a denominator, and the platform row is COMPUTED rather than summed.** `SC-012` asks for a zero-difference match against the source, and a rounded percentage cannot produce one — so a count is `denominator = 0` (read as «not a ratio», never divided by) and a rate is two columns. `RollUpPlatformMetricsJob` writes `workspace_id = 0` by re-running the same queries with `withoutWorkspaceScope()`: adding up the per-workspace rows counts a student enrolled with two teachers twice and reports more students than the platform has. Both sentinels (`workspace_id`, `region_id`) are `0` and NOT NULL for the `feature_flags` reason, `numerator`/`denominator` are **signed** because `dues.overdue_credits` sums negative balances (ERROR 1690 on MySQL, invisible on SQLite), and the table carries **no `uuid`** — `upsert()` boots no model, so `HasUuid` never fires and MySQL would store `''` and collide every later row. ⚠️ **And the region report starts from `regions` and joins LEFT**: the rollup writes only what it counted, so a region nobody has registered from would otherwise vanish from the report instead of showing the zero that is the answer.
- **A field whose options come from a catalogue that is not seeded in production is a CLOSED DOOR — and `MarketplaceSeeder` was called only outside production.** `DatabaseSeeder:87` wraps it in `if (! app()->environment('production'))`, and it held the ONLY writer of the nine subjects and four stages, so a production database was born with an empty taxonomy: the teacher application offered nothing to pick and the student's required stage field rendered a select with no options. The fix is an extraction (`TaxonomySeeder`, called unconditionally) plus a `seedMissing()` backfill migration — the **fifth** instance of one mechanism in this tree after the notification templates, the data categories, the gamification actions and the regions. ⚠️ Two details are not ceremony. `seedMissing()` (`firstOrCreate`) is the ONLY mode a deploy path may call: every row is editable from `/admin`, and `run()`'s `updateOrCreate` resets an operator's renaming and reordering on every release. And `sort_order` is an **explicit value, never an array index** — `firstOrCreate` writes it for new rows only, so an index-derived order makes production's ordering differ from development's the moment a row is inserted in the middle of a list. ⚠️ **Laravel orders migrations by FILENAME, so a backfill can predate the table it would write to**: `TaxonomySeeder` guards its years with `Schema::hasTable`, and a second backfill after `create_school_years` calls the same method again. Without the guard the first backfill writes to a missing table and every `RefreshDatabase` test in the suite throws. And a row whose parent is unknown **throws** rather than being skipped — the backfill runs once and `firstOrCreate` never comes back for a row it did not write, so a skipped row is missing for the life of the deployment, silently.
- **A column with no FOREIGN KEY makes every `->relation->field` in an Action a 500 waiting for one deleted row.** `enrollments.student_user_id` is a bare `unsignedBigInteger` with an index and no constraint — on MySQL as much as on SQLite — so a user row that goes away leaves its enrolment behind. `ListStudentBalances` then read `$enrollment->student->uuid` and answered `ErrorException: Attempt to read property "uuid" on null` — not for that row, **for the request**: every student in the workspace vanished from the teacher's balances panel, permanently, over one record that names nobody. Found by walking the product with the network tab open (029 · `T057`), and **no fixture in the suite could show it**, because every one of them builds the enrolment from a student it created a line earlier. The guard is a `filter()` above the `map()`, and the test asserts the OTHER rows survive — one that only asserted `200` would pass over an implementation returning an empty list.
- **A TRANSLATABLE COLUMN IS A JSON DOCUMENT, AND THE LOCALE IS WHAT DECIDES ITS KEY — so `config/app.php` defaulting to `'en'` would have stored `{"en": "عربي"}` on a product that has no English.** Spec 055 turned fourteen `x_ar` columns on eleven tables into spatie `HasTranslations` columns (`subjects` · `grade_levels` · `regions` · `school_years` · `gamification_actions` · `levels` · `badges` · `data_categories` · `data_processors` · `notifications` · `message_templates`), and five things about that are not obvious. **The locale default moved to `'ar'`**: `.env` and `phpunit.xml` both set `APP_LOCALE`, so the `'en'` fallback was invisible — an environment that forgets the variable writes every row under a key no reader asks for, and the fallback locale then hands back the same string anyway, so nothing fails and the document is simply wrong. **A RUNTIME CATALOGUE SEEDER IS CALLED FROM A BACKFILL MIGRATION DATED BEFORE THE CONVERSION**, so on a fresh database — every `RefreshDatabase` run — `TaxonomySeeder`, `RegionSeeder`, `GamificationCatalogSeeder`, `NotificationTemplateSeeder`, `DataCategorySeeder` and `DataProcessorSeeder` run while the column is still `name_ar` and write `name`: «no such column», and the whole suite dies inside `migrate:fresh` rather than in one test. Each of them returns early behind `TranslatableColumns::converted()` and each conversion migration calls the seeder again at the end, so a database part-way through the sequence still ends with every row — the `Schema::hasTable` guard `TaxonomySeeder` already carried, reached from a second direction. **`pluck('name', 'id')` KEEPS WORKING ONLY BY A SIDE EFFECT**: `HasTranslations::initializeHasTranslations()` merges an `array` cast, and `Eloquent\Builder::pluck()` re-hydrates through `newFromBuilder()` whenever the column has a cast — so eleven picker call sites needed no change at all. **A SUBQUERY ALIAS DOES NOT**, because the alias lands on a model that has no such cast: `BadgeResource::getEloquentQuery()`'s `addSelect(['rule_action_name' => …])` would have printed `{"ar":"…"}` into a table cell, and the fix is `->select('name->'.app()->getLocale())` — Laravel's grammar, never `json_extract` by hand, which returns a *quoted* string on MySQL and an unquoted one on SQLite. `orderBy('name')` is the same trap wearing an accident: ordering the raw document happens to order by the Arabic value while every row carries exactly one language, and stops the day one does not. **AND THE API KEYS MOVED WITH THE COLUMNS** — `name_ar` → `name` across thirty-five frontend files — because a payload key that names a language, over a column that may carry two, is the two-spellings defect this file records a dozen times. The enum labels (`type_label_ar`, `status_label_ar`, `retention_label_ar`, `erasure_capability_label_ar`) are NOT columns and keep their names, while `level_name_ar` moved with the rest because it is `levels.name` echoed onto a progress payload; `data_processors.name` is a vendor's trading name and is deliberately not translatable, because a company is called the same thing in every language and a second spelling of one processor is the last thing a register of processors needs. **⚠️ AND A MIGRATION THAT WRITES THROUGH A MODEL BROKE THE WHOLE SUITE, NOT ONE TEST.** A migration speaks the schema of ITS OWN DATE; a model speaks today's. `2026_08_29_003100_backfill_referral_catalogue_action` and `2026_08_27_000800_backfill_course_subject` both called `Model::firstOrCreate([... 'name_ar' => ...])` — and once `name_ar` left `$fillable`, mass assignment **discarded the key in silence**, exactly as this file records for a column added without one, so the INSERT arrived with no name at all and died on the NOT NULL the migration itself had written. Inside `migrate:fresh`, which means **690 of 690** tests errored with a message naming a constraint rather than a cause. Both write with `DB::table()` now, passing `uuid` and the timestamps explicitly because the model layer is not there to supply them — the `CreditLedger::writeEntry()` rule reached from a new direction. **The check before renaming any column is `grep -rl "Models" app/Modules/*/Database/Migrations/`.** **⚠️ AND A BULK `update()` APPLIES NO CAST, SO IT WRITES A BARE STRING INTO THE DOCUMENT — which reads back as NOTHING.** `UpdateAnnouncement` re-words every notification the fan-out wrote with one raw `DB::table('notifications')->update(['body' => $body])`, deliberately one statement because the audience is a whole class; after 055 that plain string decoded to nothing and every one of those notifications would have shown an EMPTY body in the bell, permanently, with no error anywhere. The spelling is the JSON path — `['body->'.app()->getLocale() => $body]` — which keeps the single statement, leaves any other locale on the row untouched, and is compiled to `json_set` on MySQL and `json_patch` on SQLite by Laravel itself. It is the `LedgerEntry` rule wearing a new face: a bulk update retrieves no models, so nothing the model layer promises is true of it. Two tests were writing the same way and were measuring an operator's panel edit, which goes through the model — they fetch the row first now.
- **FOUR SQL FORMS ARE GREEN ON THE WHOLE SUITE AND BREAK PRODUCTION ONLY, AND SPEC 038 WALKED INTO ALL FOUR.** Everything here runs on in-memory SQLite and deploys to MySQL, so for each of these the form everybody reaches for is the wrong one and nothing local can say so. **`||` is string concatenation on SQLite and LOGICAL OR on MySQL** — `'anonymised:' || id` stores `'1'` in every row, which collides on `unique(user_id, fingerprint_hash)` at a user's second device, rolls back the *entire* erasure transaction (so no name, no email and no phone is anonymised either), and never converges because `'1' NOT LIKE 'anonymised:%'` is true again every night. `config/database.php` sets `'strict' => true` with no `modes`, and Laravel's strict sql_mode carries no `PIPES_AS_CONCAT`. **And `CONCAT()` is not the fix**: SQLite grew it in 3.44 and the CI runner's version is not ours to assume — build the value in PHP, the `Anonymiser::email()` precedent. **`DELETE … WHERE id NOT IN (SELECT … FROM the same table)` is MySQL ERROR 1093**, and SQLite rewrites it to `rowid in (…)` so it passes for ever; discovery is one query, the delete is another, ids passed as values — **`array_chunk`ed at a thousand**, because a single `whereIn` over one heavy account is ERROR 1390 (65,535 bindings, server-side prepares) on MySQL and `SQLITE_MAX_VARIABLE_NUMBER` (32,766) here. **And `->groupBy('x')->get()` compiles to `select * … group by x`, which is ERROR 1055** under `ONLY_FULL_GROUP_BY` — which Laravel puts in the sql_mode *unconditionally* for `'strict' => true` (`MySqlConnector::getSqlMode()`), while SQLite returns an arbitrary row for the bare columns and says nothing. A job written that way throws on its first statement every night in production while every shard of CI is green. ⚠️ **The only instrument that reaches any of them is a comment-stripped source scan** (`tests/Feature/Identity/SqliteGreenFormsTest.php`, the `TrustScoreJobIsolationTest` shape) — and it must assert that it MATCHED something: the first draft of that guard filtered on `query()` in the same statement, which the cap job's chain does not have because its builder comes from a private helper, so it examined nothing and reported success. ⚠️ **And a catalogue row with a mismatched `erasure_mode` switches erasure off for its whole module**: `ExecuteDataErasure::modeFor()` unions the modes a module declares and demands exactly one, else logs `compliance.erasure.unclear_mode` and returns `Retain` — no name, email or phone anonymised for ANY request in that module, with no visible error.
- **A FILAMENT EDIT FORM FILLS FROM `attributesToArray()`, AND FOR A TRANSLATABLE COLUMN THAT IS THE WHOLE DOCUMENT — SO THE PANEL RENDERED `[object Object]` AND WOULD HAVE SAVED IT.** `EditRecord::fillForm()` reads `$record->attributesToArray()`; spatie overrides `mutateAttributeForArray()` to return every translation of a translatable attribute, so a `TextInput` received `['ar' => 'الكيمياء']` and the browser printed what JavaScript makes of an object in a text field. Press «حفظ التغييرات» **without touching the field** and that literal string is what lands: the subject renamed `[object Object]` for every screen on the platform, from a form nobody edited. ⚠️ **The table was right the whole time** — a column reads the accessor, which answers one locale — which is exactly why nothing looked wrong until an edit form was opened, and why a test that measures the list passes straight over it. `App\Shared\Traits\EditsTranslatableRecord` flattens each translatable attribute to the current locale in `mutateFormDataBeforeFill()`, on the eight edit pages that have one (`data_categories`/`data_processors` have no Filament resource at all). ⚠️ **Only the FILL needs it**: `HasTranslations::setAttribute()` already takes both shapes — a string lands under the current locale, an associative array replaces the document — so a save-side counterpart would be a second answer to a question the package answers. ⚠️ **And PHP CANNOT TEST THE HALF THAT DOES THE DAMAGE.** Measured by deleting the guard: 8 of 16 cases failed and every one of them was a *fill* case, because a Livewire test has no browser to stringify the array — it reaches `setTranslations()` intact and the row stays correct. So the guard is the assertion that the form STATE is the locale string; a "save an untouched form" case is green with or without the fix and was rewritten rather than kept. ⚠️ **The two tabbed-editor plugins do NOT have the same answer, and reading the version is what separates them.** Measured 2026-09-10: `pixelpeter/filament-language-tabs` v3.0.0 requires `filament/filament ^4.0` against this tree's 5.7.6 and `composer require --dry-run` refused all three of its majors — a blocker; `solution-forest/filament-translate-field` v3.0.3 requires `^5.0`, installs cleanly, works with spatie, and its `Translate::make()->schema([...])` fills AND saves per locale, i.e. it replaces this trait outright. So the second is a **decision, not a blocker**, and the decision was to wait: the product is Arabic-only by design (spec 002), so `defaultLocales(['ar'])` draws one tab around every field for no gain — and the eight form rewrites cost the same today as they will the day English arrives, so adopting early saves nothing. **The trait must come OUT the day one goes in**, since a tabs component wants the document it flattens. Found by opening the screen on production, not by any suite.
- **MySQL REFUSES ANY IDENTIFIER OVER 64 CHARACTERS AND SQLITE HAS NO LIMIT AT ALL — so the deploy is the first place that sees it, and it takes every migration behind it down with it.** Measured on production 2026-09-14: `course_waitlist_entries` passed locally, passed all four CI shards, and then `ERROR 1059 Identifier name 'course_waitlist_entries_student_user_id_course_id_closed_slot_unique' is too long` (68 characters) stopped the release — **and the two backfill migrations queued after it never ran**, leaving the database with no data-category row to sweep and no notification template to render. The fix is a hand-written name as the second argument to `unique()`/`index()`, never a shorter table name once the table is in the code. ⚠️ **And `Schema::create` is NOT one statement**: it issues CREATE TABLE and then a separate ALTER per index, so the table was created and only the indexes after the failing one were lost — with no row in `migrations`. A migration that can re-run onto that state must branch on `Schema::hasTable()` and repair with `hasIndex()`, never drop: whatever rows exist were written between the containers starting and the migration failing. `tests/Feature/Seeding/SchemaIdentifierLengthTest.php` reads `sqlite_master` after every migration has run and fails on any table or index name past 64 — the only way to guard a constraint that does not exist in the engine the suite runs on, and it covers every migration written from now on without a line being added for it. ⚠️ **AND THE REPAIR BRANCH RESTORED WHAT FAILED RATHER THAN WHAT SHOULD EXIST — measured on the same table five days later.** `show create table` on production answered PRIMARY plus the two hand-named indexes and nothing else: `unique(uuid)` and the three single-column indexes, all of which are issued BEFORE the failing statement, were gone too — so the first deploy lost more than the tail, and `addIndexes()` put back only the pair named in the constant it was written around. The sharp one is `unique(uuid)`: `HasUuid` makes it this model's public identifier (`getRouteKeyName`), so with no constraint on it nothing in the database stops two rows sharing one uuid and a reader takes whichever came back first. **A repair branch restores the COMPLETE index set the create branch declares, not the ones that happened to fail** — and once the create migration has a `migrations` row, the only way back is a NEW migration guarded per index by `hasIndex()` (`2026_09_14_000400_repair_course_waitlist_entries_indexes`). ⚠️ **No test in this tree can see this and none should be written to pretend otherwise**: on SQLite `Schema::create` always produces all six, so an assertion that the six exist is green over the broken production schema — the vacuous-guard shape this file rejects elsewhere. It was found by `show create table` on the live database, which is the only instrument that answers it.
