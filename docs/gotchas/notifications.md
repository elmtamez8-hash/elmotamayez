# Gotchas — Notifications and channels

Moved verbatim from `CLAUDE.md` (the rule headlines stay there). Read this file before changing `Modules/Notifications/`, templates, WhatsApp, push, guardian fan-out. Bullets that say «above» may now point into another file in `docs/gotchas/`.

- **`Notifiable` stays on `User`, and that is deliberate.** Email is an unimplemented *notification channel*, but Laravel's password-reset and email-verification mails still go through `notify()`. They are authentication primitives, not domain notifications — a reset link delivered in-app is unreachable by definition, since the person asking for it cannot sign in to read it. `User::notifications()` is overridden to point at our own model; Laravel's `notifications` table was replaced.
- **A notification with no template is silently dropped.** `TemplateRenderer` refuses to render a missing or unapproved template (FR-037) and `DispatchNotification` logs it rather than failing the enrollment/payment that triggered it. `NotificationTemplateSeeder` is therefore reference data, not fixtures — `tests/Pest.php` seeds it before every Feature test, or every notification assertion would pass vacuously against zero.
- **A channel class alone delivers nothing, and the guard is a COUNT.** `NotificationType::defaultChannels()` returned `[InApp]` for all thirty-five types, so shipping `WhatsAppChannel` without touching it would have created no delivery row at all — nothing fails, because nothing runs, and every assertion about the new channel passes by finding nothing to contradict it. It is now **derived from `targetsGuardians()`** rather than a second list of names: two hand-written lists answering one question diverge at the first type anybody adds, and the divergence is silent. `WhatsAppDefaultsTest` asserts the number **exactly** — **twenty-five** as of spec 011 — the guardian-targeting types plus **two named exceptions**, `security_alert` and `guardian_consent_required`. ⚠️ **Read the assertion, never this sentence**: it said "nineteen · one exception" for four days after 013 moved it to 22, and then said "twenty-two" while the file asserted **25** — spec 011 added `shipment_status_changed` and `store_purchase_unavailable`, both facts about a PURCHASE, both riding the payments consent, and spec 010's design copied the stale number out of here into a research document rather than measuring — the same failure this file records under «verify every code claim». The number moves whenever a guardian-targeting type is added, and moving it is the deliberate part. (It was eighteen until spec 009 added `reward_redeemed`: a redeemed reward can be a DISCOUNT ON A SESSION, which changes what the family pays. Its two siblings `level_up` and `badge_awarded` deliberately stay on the bell — several a week on a parent's phone is how the number gets muted, taking the attendance alert with it.) ⚠️ **And a type added to `targetsGuardians()` must also get a `requiredGuardianPermission()`**: `RecipientResolver` merges guardians only when both are present, so one without the other picks up the WhatsApp channel, is billed, and reaches no guardian at all. ⚠️ That exception lives in `defaultChannels()` and **not** in `targetsGuardians()`, where an earlier version of this line wrongly said one word would do it: that method also fans the message out to every authorised guardian and demands a `GuardianPermission` to gate it by, so one word there would have shipped a student's own security alert to their parent — who may well be the person who just signed in. It leaves the platform because the bell reaches its owner only on their next visit, and if the eviction worked that is the person who no longer can.
- **Every WhatsApp message is an approved template, and `body_ar` is documentation of one — not the text that is sent.** Free-form text is permitted only inside the 24-hour window a user opens *by replying*, and we receive nothing, so that window never opens. What travels is the template NAME (`message_templates.type`) and an ORDERED parameter list (`variables`), read out of the notification payload — the Arabic sentence lives at the provider. So editing `body_ar` from `/admin` changes the notification bell and changes nothing on a phone. **Order is the whole meaning**: a list built by walking the payload, whose key order is whatever a listener happened to write, puts a student's name where the duration belongs in a message to their parent, with no error anywhere. Rows are seeded `pending`, never `approved` — claiming an approval that has not happened turns the first send into a provider error code nobody can map back to a row.
- **The verification code cannot go through `DispatchNotification`, by construction.** `canReach()` asks whether the recipient has a **verified** contact detail, and the code is by definition the message that goes to an **unverified** one — so dispatched normally it is skipped every time, for ever, and no number on the platform can ever be proven. `ContactVerificationController` calls the channel directly through the `SendsVerificationCodes` capability (asked as a capability, not an `instanceof`, so a channel that cannot carry a code simply does not implement it). It writes no feed row: a one-time code has no business in a list a person reads later. ⚠️ This also makes `contact_verification` **the first template that must be approved** — before it, nothing else can be delivered to anyone.
- **A phone number is normalised where it is WRITTEN, never where it is sent**, and read from `contact_verifications`, never from `users.phone`. That column is a free string nobody confirmed, and a typo in it is a message about a child sent to a stranger. `PhoneNumber::toE164()` is Qatar-shaped by design (`libphonenumber` is the world's metadata for one market); the upgrade trigger is a second country, and it is written beside the class.
- **Permanent vs transient is read from the provider's own answer** (`is_transient` in the error body), never from a code list copied into the tree — a copied list ages at the provider's next release and then either drops real messages or burns five attempts and the rate budget on a number the first reply already refused. The rule: a 4xx that is not 429 and does not declare itself transient is permanent; everything else is retried by `DeliverNotificationJob`'s existing backoff.
- **The focus-timer mute is a filter on the READ, and the design put it in the wrong place.** Spec 009's contract said "a new condition in `DispatchNotification`", and the diagnosis behind it is right — `QuietHours::deferUntil()` returns null immediately for anything that is not an external channel, so the bell has never passed through it. But the notification ROW is written before any channel is consulted (003 FR-007: one record however many channels carry it) and the bell reads that row, not a delivery row — so a check inside the dispatcher could only DROP the message or defer a delivery nothing looks at, and the badge lights either way. `NotificationController::muteDuringFocus()` filters the feed and the unread count instead: it mutes for exactly the length of the session, loses nothing, and needs no column. `isMandatory()` stays the valve.
- **Quiet hours and digesting were written in 003 and never once ran** — both apply to external channels only, and `isExternal()` was false for every channel that existed until 020. They are exercised against the real class in `WhatsAppDeliveryPathTest`, not only against the fake one, for exactly that reason.
- **`isFocusing()` asked `status = running` and never read the clock, so one abandoned timer muted an account's notifications for ever.** `muteDuringFocus()` filters the unread COUNT and the feed together, and nothing ends a session whose owner closed the tab — a forty-five-minute session started on 2026-08-21 was still `running` on the 24th, with no badge, no error, and no later message able to restore it. `FR-039`'s «exactly the length of the session» is only true if something reads the length. The window is `started_at` plus a PER-ROW `planned_minutes`, so the comparison is in PHP rather than SQL — `DATE_ADD` on MySQL against `datetime()` on SQLite is two dialects for one predicate, the same reason `BanReader` judges an expiry in PHP. The stale row is deliberately not closed: a read that writes surprises every caller, and it no longer harms anything. Found on a real database, not by a test — the suite only ever created sessions and ended them in the same breath.
- **`NotificationChannel::Push` is deliberately absent from `defaultChannels()`, and SUBSCRIBING is what switches it on.** Three reasons, each read out of a named file rather than assumed: `DispatchNotification::queue()` writes a delivery row and dispatches a job from `isEnabled()` alone — `canReach()` is not asked until the job runs — so in the defaults that is one row and one job per notification per recipient on the whole platform, the large majority of whom have no device registered; `WhatsAppDefaultsTest` asserts `SecurityAlert->defaultChannels()` with `toBe()`, an exact list, and it is the guard that says a channel class alone must deliver nothing; and `PreferenceResolver` merges the defaults ON TOP of a stored preference for a mandatory type, so push would become a channel nobody can switch off, on a device they may be sharing. The way out is that a stored row REPLACES the defaults — `SavePushSubscription` writes them for the three subjects a push is for, with `insertOrIgnore` so a service worker re-registering on every visit cannot resurrect a mute the person set last week, and carrying **the defaults plus push** rather than `['push']` alone, or the settings grid shows in-app unticked for thirty types while the feed keeps receiving them.
- **`ProviderAgnosticTest` fails on a private method NAMED `notify()` inside `Actions/`, and it is right to.** `notify()` is `Notifiable`'s own method, so the guard's substring scan cannot tell a helper called `$this->notify(...)` from a channel being reached for — and the point of the rule is that business logic names a recipient and a `NotificationType`, never a delivery mechanism. Name it for what it says (`tellStudent()`), not for how it travels.
