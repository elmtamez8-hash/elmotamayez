# Gotchas — Media, recordings and playback

Moved verbatim from `CLAUDE.md` (the rule headlines stay there). Read this file before changing `Modules/Media/`, Bunny/R2, recording ingest, the video player. Bullets that say «above» may now point into another file in `docs/gotchas/`.

- **The watermark is the renewal loop, not something watched for.** A playback grant is short-lived; the overlay component is what calls `/playback/{grant}/renew`. Remove it from the DOM and renewal stops, the grant expires, and the next byte-range request is refused — the decision sits on the server, where it cannot be edited away. This is also why the local provider serves with `Accept-Ranges: bytes`: without range requests, expiry could not cut a file already in flight.
- **The transcript is derived, and the caption file expires with the grant.** `media_captions` stores a WebVTT path and nothing else — no transcript column, because a stored second copy of the same words drifts from the subtitles at the first typo fix. `WebVtt::parse()` derives it server-side (validation) and `TranscriptPanel.tsx` derives it again in the browser from the file the `<track>` already fetched. That file is served by `/playback/{grant}/captions/{caption}`, not from a public path: a `<track>` sends no `Authorization` header either, and a permanent caption URL would be the lesson's entire script, permanently linkable. When an asset has captions the watermark rotates through the **top** corners only — the browser's caption band is exactly the `bottom-14` row, and a viewer who needs captions cannot work around a covered word.
- **`ingestFromUrl()`'s `$sourceUrl` must arrive signed, and one provider was signing it privately.** The interface says «short-lived and signed, never a public URL» — a precondition on the CALLER — while `IngestSessionRecordingJob` passes LiveKit's plain `$file->getLocation()`. Bunny compensated inside itself, so the violated contract was invisible until a second provider took the same URL and R2 answered `400 InvalidArgument: Authorization`: the download «succeeded» into a **113-byte** file whose whole content was that XML. `Media\Support\FetchableSourceUrl` is the one spelling both providers call now. (It still reads `media.bunny.source_disk` — a naming wrinkle kept deliberately rather than churn a config key.)
- **The recording retry loop did not exist, and its absence was a teacher's pay.** `IngestSessionRecordingJob::giveUpOrRetry()` increments `recording_attempts`, writes `recording_status = 'pending'` — and **returns**. No `release()`, no second dispatch; the only sender was `SessionCompleted`, which fires once. So the first "not finished yet" was also the last attempt and the counter froze at 1. It was silent because `NullBroadcastProvider` declares `recording: false`, so the job returned before reaching that branch — **017 is what switches it on**, which is why `RetryPendingRecordingsJob` ships with it. And the cost was never a badge on a screen: `Settlement\Support\PackageCompletion` reads the same column and withholds the fee for any session whose recording is not one of `published`, `failed`, `no_course` — so an eternal `pending` withholds pay for a lesson that was actually taught. **`no_course` releases it too** (a session with no course has no lesson to publish into), and `null` and `ingesting` do NOT, which is the part that bites: `RetryPendingRecordingsJob` sweeps `'pending'` alone, so a session whose ingest job died before writing anything holds a wage with nothing left to move it.
- **The guard against a second delivery is a conditional UPDATE, and it was a read followed by a write — with two senders by design.** `SessionCompleted` fires once and `RetryPendingRecordingsJob` re-dispatches every fifteen minutes, so two runners overlapping on one session is ordinary. Both read `media_asset_id` as null, both call `videos/fetch`, and **every call to it creates a video**: a second one, billed monthly, referenced by nothing, invisible without going to look. `UPDATE … WHERE media_asset_id IS NULL` is both the check and the claim — the seat idiom, the same one `captured_order_id` and `StructureVersion::claim()` use, and never `lockForUpdate()`, a no-op on SQLite. The asset row is INSERTed before the claim because the claim needs its id, which is safe precisely because nothing has been delivered yet: a loser deletes its own row having spent one local insert and no provider call. `recording_attempts` moves by `increment()` for the same reason — `$session->recording_attempts + 1` lets two runners write the same number, and a budget that never advances is an unbounded retry loop wearing a counter. **A single-threaded test still reaches this**: `recording()` is asked BETWEEN the read and the claim, so a callback there is the other runner winning inside exactly that window — no threads, no sleeps, and the sequential "second pass" test does NOT cover it (the second call reads a session that already has an asset and never reaches the claim).
- **`ReconcileAssetStatus` is the self-heal, and it needed a ceiling AND a verdict — either alone is a defect.** It runs every five minutes and spends up to two provider calls per `Processing` row (a title search plus a GET), and it had no age ceiling and no attempt budget of any kind: an asset whose delivery never landed was interrogated 288 times a day for the life of the deployment, and the standing bill grew with every asset that ever got stuck. But a ceiling on its own leaves that asset «قيد التجهيز» permanently — the exact state the job was scheduled to abolish, reached by another road — so past `media.reconcile_ceiling_hours` (48) it is written failed WITH a reason, which is what makes manual upload the way out instead of a guess. The age is measured from `created_at`, never `updated_at`: the sweep touches the row on passes that change nothing, and an age measured from the last touch is an age that resets itself. Two days matches the recording sweep's own window — no transcode takes that long and the ingest budget gave up hours earlier — but it does mean the "a late Ready overwrites failed with published" promise is now bounded: it covers a slow encode, not an abandoned one.
- **`recording_status` has THREE stuck values, not one — and the two nobody swept were the ones a crash leaves behind.** The column is nullable with no default and no initial writer outside the ingest jobs, so a job that dies before its first write leaves NULL; `'ingesting'` is written BEFORE the hand-off and corrected on the same pass, so only a hard kill (the 60-second job timeout across four provider calls, or an OOM) can strand it — `catch (Throwable)` covers a throw and never a kill. `RetryPendingRecordingsJob` selected `'pending'` alone, so both sat for ever while `PackageCompletion` held the teacher's fee for a lesson that was actually taught. **The crash was one connection away**: `recording()` is a live HTTP call and it stood ABOVE the `try` in `IngestSessionRecordingJob`, with Horizon at `tries: 1` — one refused connection ended the job with nothing written and a `failed_jobs` row as the only trace. Every provider call is inside that `try` now, and the sweep takes all three states. Two conditions come with them or the fix creates its own defect: the two new states are swept **only while the current provider declares `recording`** (otherwise every completed session on a recording-less provider is re-dispatched every fifteen minutes for two days to a job that returns immediately), and the sweep requires `status = completed` rather than a closed room — a teacher who ends the broadcast early leaves `room_closed_at` set while `CloseClassSession` is still a join window away, and sweeping then spends an attempt on «not finished yet» about a session that has not finished.
- **A provider DECLARES which kinds it accepts, and the day that was merely assumed a PDF got a video object.** `ProviderCapabilities::$kinds` (null = all) plus `MediaProviderResolver::forKind()`: the configured provider gets first refusal and our own disk takes what it declines. Before it, every upload went through whatever `media.provider` named — so flipping the switch to a video host had a worksheet created as a *video* in a video-only library, under video-sized ceilings, failing while naming the wrong cause. **`forKind()` is a different question from `for()`** and both are needed: one reads a declaration before any row exists, the other reads the column afterwards. The column is stamped from whoever actually took the file, never from the config, or `for()` would resolve the wrong provider for every routed asset. And `PUT /media/upload/{token}` now asks `$asset->provider === $provider->identifier()` — the local route used to accept a commercial provider's asset and write a disk path into `provider_asset_id`. Compared against the COLUMN, never the config, so a pre-flip local asset still in `Pending` stays uploadable after the switch.
- **A media asset is resolved from its own `provider` column, never from the config — and the resolver sits BESIDE the binding, not in place of it.** `media_assets.provider` was written on every row since 004 and read by nothing, which was harmless with one provider and is silent data loss with two: the container binds one provider from `media.provider`, so the day production flips, every recording made before it is handed to the new provider and answered "file not found". `createUploadTicket` is asked for an asset that does not exist yet, so there is no column to read and the binding stays the only correct answer there. `SC-011` is measured with **two assets for two providers in one database** — one asset can never see this defect, because a test's config always agrees with its own fixture. The provider map lives in `MediaServiceProvider` alone and is INJECTED into `MediaProviderResolver`, so the resolver names no vendor and `tests/Feature/Media/ProviderNameContainmentTest.php` passes over it (a path, not a namespace — the file is Pest-style with no class, and `LiveSessions/` has one of the same basename).
- **`ingestFromUrl()` is the only change to 004's contract, and the download was MOVED rather than deleted.** It now lives in `LocalMediaProvider`, which is what a provider with no remote fetch has to do. Both providers declare `remoteFetch: true`: the flag answers "can you take a file over from a URL", not "did the bytes avoid our network" — declaring `false` on the local one would be honest about bandwidth and wrong about capability, and would force every caller into two branches for one question. The bandwidth is `SC-001`'s question, and `ZeroVideoBandwidthTest` asks it **as a negation over the whole `Http::fake()` request list plus a positive control**: asserting that `videos/fetch` was called passes on an implementation that downloads, uploads, then calls it — and asserting only negations passes vacuously over a delivery that did nothing at all.
- **`videos/fetch` DOES return the new video's id — the OpenAPI schema is wrong and this file trusted it for a day.** ⚠️ Verified against a live account on 2026-08-17: the 200 is `{"id":"42d1c5e3-…","success":true,"message":"OK","statusCode":200}` and `GET /videos/{id}` returns that value as its `guid`. The schema types the response as `StatusModel` (`{success, message, statusCode}`) and research §R3 built the whole design on it, dismissing the narrative docs page — which showed an id and was **right**. Read the id, and save it inside `ingestFromUrl` before anything else can fail; that is the only window in which it can be lost.
- **A presigned R2 url needs no `headers`, and `headers: []` is a 400.** ⚠️ Both verified live on 2026-08-18. The presigned url carries its own authentication in the query string, so the `headers` field of `videos/fetch` is for sources that need custom auth and ours never is — which is why the key is **omitted** rather than sent empty: `[]` encodes as a JSON array where the schema wants an object, answered `400 {"errors":{"$.headers":[…]}}`, classified permanent, and every recording would have failed on its first attempt. Also measured: Bunny starts the fetch immediately (a 2.8 MB clip was `Ready` with five renditions **15 seconds** after delivery on the free best-effort tier), so `BUNNY_SOURCE_URL_TTL_MINUTES=120` covers the download window with room to spare.
- **The title is still a cross-system JOIN KEY — as the RECOVERY key, not the happy path.** A delivery whose response never came back (a timeout after Bunny accepted, a worker killed between the POST and the save) leaves an asset with no id and a video that exists, and `{prefix}:{asset_uuid}` is the only thing naming one from the other. So changing `BUNNY_TITLE_PREFIX` still orphans every asset not yet recovered, and a duplicate title is still worth reporting — the exposure narrowed, the case did not disappear. And because every call creates a video, `IngestSessionRecordingJob` refuses to deliver twice for one session — a retry after a `429` would be a second video, billed monthly, referenced by nothing. The recovery is the existing sweep, not a webhook: `RetryPendingRecordingsJob` already runs every fifteen minutes, so polling costs zero new routes, zero signature verification and zero tables.
- **A recording can be neither ready nor failed, and that middle state is load-bearing.** A delivery accepted with no id recovered is `Processing`: `Ready` would publish a lesson over a file nothing can address, and `failed` would release the teacher's held fee for a recording still on its way. The session stays `pending` and not `ingesting`, because the sweep only re-sends for `pending` — and `PackageCompletion` withholds pay for anything outside `published`/`failed`/`no_course`. `'ingesting'` is written before the delivery and corrected on the same pass, so only a hard worker kill can strand it; `null` is the wider door, and neither value is swept. An attempt IS spent on "still encoding", deliberately; if a provider's encode outlives the budget the fix is not a bigger number, it is `ReconcileAssetStatus`, whose late `Ready` still fires `MediaAssetReady` and overwrites `failed` with `published`.
- **`token_path` is the whole of the playback protection, and its absence passes any test that asks for the index.** The manifest is HLS, so a token on `playlist.m3u8` alone leaves every `.ts` segment served openly — whoever holds one URL holds the video, with no grant, no watermark and no device limit behind it. The signature is the **advanced** scheme, `HS256-` + Base64URL(HMAC-SHA256(key, signature_path + expires + signing_data)), over the video's DIRECTORY; the basic scheme is an MD5 with no path allowance and cannot protect HLS at all. `SC-002` therefore measures what fetches BYTES, not the index.
- **`token_path` is SIGNED as well as sent, and it goes in the PATH, not the query — two separate mistakes that each 403 every video.** The exclusion list from `signing_data` is `token` and `expires` alone, so the hashed message is `signature_path + expires + "token_path=" + signature_path`; hashing `path + expires` on the reasoning that "we add no query parameters of our own" ignores that `token_path` is one, and ships an invalid signature. And the token belongs in the path (`/bcdn_token=…`), because RFC 3986 lets a relative reference inherit the base query **only when its own path is empty** — Bunny's `playlist.m3u8` is a master playlist pointing at `720p/video.m3u8`, so in the query form the index loads signed and every rendition and `.ts` beneath it leaves bare. Both shipped in 019 and both were green, because the suite asserted the token's SHAPE — which a wrong signature also has. The guard is `tests/Feature/Media/BunnyTokenVectorTest.php`, which needs no account and no network; **never replace it with another structural assertion.** ⚠️ **It is a PIN, not independent corroboration, and this file used to call it «the vendor's own published vector» — which is false: `BunnyWay/BunnyCDN.TokenAuthentication` publishes a reference implementation and no vectors.** The digest was computed from that implementation, so a misread algorithm would have been pinned just as confidently. What corroborates it is an account: on 2026-08-18 a URL from `manifest()` answered **200** from a real zone, and so did `720p/video.m3u8` and `video0.ts` beneath it — inherited under the one path token, no second signature anywhere. The viewer's IP is deliberately excluded from the signature: a phone moving from wifi to mobile data changes address and the lesson would cut out mid-way.
- **`recording_attempts` is a budget of five that everyone read as «an hour and a quarter», and nothing made that true.** ⚠️ Measured 2026-08-18: a `queue:work` started before a code fix and restarted after it left **72** `RetryPendingRecordingsJob` passes queued; they drained in one second and spent the entire budget inside it. The session was written `failed`, the teacher told the recording was lost and every seat holder told the same — about a file sitting intact in R2, mid-transcode, which `ReconcileAssetStatus` published **five minutes later**. A paused Horizon supervisor, a deploy, or any queue outage produces the identical pile in production. The gap is enforced now by `recording_attempted_at`, stamped inside the same statement that increments the counter; `updated_at` was unusable for it for the reason `notified_dormant_at` exists — it moves for every unrelated write to the row. The constant is **14** minutes against a 15-minute schedule: an exact match skips every other pass, because a scheduler is never punctual to the second.
- **«Still encoding» spends no attempt, because that phase belongs to another job.** Before the hand-off the question is whether the BROADCAST provider has finished assembling the file and nothing else is watching, so the budget belongs there. After it, the file is delivered and its id saved, and the question is whether the MEDIA provider has finished transcoding — `ReconcileAssetStatus` owns that, every five minutes, under `media.reconcile_ceiling_hours`. Charging it to the ingest counter meant an encode slower than five sweeps wrote the session `failed` and told the student «التسجيل غير متاح» about a video that published twenty minutes later: **a false sentence that stays in their feed, which no later success removes.** So `Processing` writes `pending` and returns; `Failed` is a verdict and is taken as permanent, because the asset the provider refused is the asset a retry would present again.
- **A valid Bunny token 403s when the request carries NO `Referer`, and that cost an hour of hunting a signing bug that did not exist.** ⚠️ Measured 2026-08-18: the zone answers `403` to a correctly signed URL fetched by `curl`, and `200` to the same URL with any referrer at all — `localhost`, `evil.example.com`, anything. So it is **not** a security control (a header is forged in one flag) and must never be counted as one; it is Bunny Stream's «block direct URL file access», aimed at a URL pasted into an address bar. Two consequences that are not obvious: a server-side probe, a smoke test or a monitoring check that omits the header reads a perfect signature as a broken one — which is exactly how the six-variant elimination above started, with every variant 403 and the key the obvious suspect. And a `Referrer-Policy: no-referrer` added to the frontend one day would 403 **every video for every student**, with the CDN as the only place the refusal appears; Next's default (`strict-origin-when-cross-origin`) sends the origin and is what currently keeps playback alive.
- **The pull zone answers `Access-Control-Allow-Origin: *` — on the bytes, not only on the index.** و-٥ closed by measurement on 2026-08-18: the master playlist, `720p/video.m3u8` and `video0.ts` each carry it, and `*` covers production as much as it covers localhost — an echoed-origin answer would have meant a green localhost proving nothing about a deployed host. hls.js reads the manifest with `XMLHttpRequest`, so without that header Safari (native HLS, no XHR) would be the only browser that plays anything, and no error would name the cause.
- **`PlaybackGrantResource` sends OUR route as `manifest_url`, never the manifest's own url.** For a redirect provider that url is the CDN hostname plus `provider_asset_id` — the one field FR-011 and that class's own docblock forbid in a payload. It travelled for free while the only provider pointed the manifest back at us, and would have started leaking the moment one did not. The signed url exists only as the `302` Location from `stream()`; a segmented player follows the redirect and resolves segments against the final url. ⚠️ **That does NOT make every segment a fresh trip through the grant** — this line used to claim it did. A VOD playlist is fetched once and never refreshed, so after that single redirect the segments come from the provider's host and this server is not consulted again. Revocation on a redirect provider is therefore the RELOAD (`reload_after_seconds`) plus the signed token's own expiry, not the per-range re-check that guards our own disk.
- **The player needed hls.js, and «صيغة غير مدعومة» was the shipped answer until 019.** `VideoPlayer.tsx` gated on `format === "progressive" || isNativeHlsSupported()` — correct while nothing produced HLS, and the moment a provider did, every student not on Safari would read an unsupported-format warning on a lesson that was fine. hls.js is imported **dynamically** and only where MSE is needed, so a progressive lesson downloads no player library, and `src` is left unset when the library drives the element — setting both makes the browser fetch a manifest it cannot parse and report an error over a video that plays.
- **`ReconcileAssetStatus` existed since 004 and was never scheduled.** Invisible, because nothing reached `Processing` and stayed there while the only provider settled an asset inside the request that uploaded it. It now runs every five minutes — and asks about `Processing` **only**, never `Uploading`: bytes still arriving *here* are not a question for a provider, and a 2 GiB PUT outlives the sweep's one-minute age check, so settling one mid-transfer would read a partial file and could publish it as complete.
