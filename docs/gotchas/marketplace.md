# Gotchas — Marketplace, taxonomy and signup catalogues

Moved verbatim from `CLAUDE.md` (the rule headlines stay there). Read this file before changing `Modules/Marketplace/`, public listing, subjects/stages/school years, signup forms. Bullets that say «above» may now point into another file in `docs/gotchas/`.

- **The trust score is derived, and so is `is_publicly_listed`.** Approval and workspace participation are two separate decisions; `is_publicly_listed` is computed from both and never assigned directly. A trust score below the data threshold is `null` with band `building`, never `0` — filters must exclude those teachers rather than compare against a number they do not have.
- **The read for a SIGNUP FORM is not the read for the MARKETPLACE, and one cache namespace nearly made them the same thing.** `ListPublicTaxonomy` drops every subject and stage with no publicly listed teacher — correct for a filter bar, whose own docblock says why, and on a REQUIRED signup field a **circular lock**: no listed teacher ⇒ no subject in the list ⇒ the first teacher on the platform can never apply, for ever. The fix is a second Action (`ListSignupTaxonomy` · `ListSchoolYears`, modelled on `ListRegions`) and never an `includeEmpty` flag on the first — one function answering two questions is restored to one answer by the first caller who forgets the flag, and two reads make «the marketplace filter bar does not widen» true by construction. ⚠️ **`MarketplaceCache::key()` IS FLAT** (`marketplace:v{N}:{suffix}`) and `ListPublicTaxonomy` owns the bare suffixes `subjects` and `grade_levels` **literally**, so every signup key carries a `signup:` prefix; without it the two reads serve each other's answers by whichever warmed the key first, alternating, and nothing fails anywhere. ⚠️ **And the door has to read the SAME predicate as the screen**: `RegisterStudentRequest` validated stages against `is_active` alone while the form was fed the participation-filtered list, so the server accepted what the screen never showed — two answers to one question, from opposite sides. `SchoolYear::scopeActivelyOffered()` is now the one spelling, read by the public route and by all four signup `Rule::in` doors.
- **A student's YEAR is stored and their STAGE is derived, and the derivation takes two strings rather than a model.** `school_years` (14 rows, `year-1`…`year-12` plus kindergarten and university) is a second vocabulary beside `grade_levels`, not a replacement: a teacher says «I teach secondary» and a student says «I am in year 10», and the four broad slugs cannot move anyway because `courses.grade_level`, the `grade:{slug}` leaderboard key and the `(subject, grade_level)` **settlement-rate** key are all undefended text carrying them. The old `grade_level_slug` stays as the fallback and is **not** backfilled from — «secondary» does not say which year, and writing one for a student who never said it is inventing data. ⚠️ `SchoolYear::stageFor(?string, ?string)` takes two strings because `parent_student_relations.student_user_id` is **nullable** — a guardian may add a child with no account at all, so there is no `StudentProfile` there to ask; a method on the profile alone would force a second derivation onto the relation. ⚠️ And a LIST reads `SchoolYearDirectory`, bound **`scoped()`**: the column is text with no relation behind it so `->with()` is not even available, a Resource runs once per row, `bind()` would rebuild the map several times per request, and a `singleton()` outlives a queue job and would serve a renamed year until the worker restarts. ⚠️ **`year-`, never `grade-`** — nothing in the database would stop a slug spelled `grade-10` settling into one of those three stage columns.
