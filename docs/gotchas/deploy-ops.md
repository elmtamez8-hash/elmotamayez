# Gotchas — Deploy, queues and operations

Moved verbatim from `CLAUDE.md` (the rule headlines stay there). Read this file before changing `docker/`, `scripts/`, Horizon, the scheduler, env and secrets, dependencies. Bullets that say «above» may now point into another file in `docs/gotchas/`.

- **Operational numbers live in `platform_settings`, not `config/`.** The device limit, upload limits and grant TTL are rows an operator edits from the panel; `config/media.php` is the fallback for a database with nothing seeded. A limit that can only change by shipping code is a limit nobody ever tunes. ⛔ **The PLATFORM TIMEZONE is the exception, since 2026-09-25**: it is `SESSIONS_TIMEZONE` and nothing else, because the scheduler reads it when `schedule:work` boots — before the database may be reachable — and a panel row beside it was a second source that moved the billing day without moving the nightly sweeps (`community.md`). Moving it is an env change plus a restart of the workers AND the scheduler.
- **A Horizon supervisor needs `defaults` AND `environments`.** `defaults` supplies shared values; `environments` decides which supervisors actually START. A queue named only in `defaults` is a queue whose jobs enqueue and are never drained — silently, with the dashboard showing nothing wrong. And a connection/queue pair absent from `waits` falls back to Horizon's 60-second default, which is wrong for any queue with its own tolerance — `QueueTimeoutInvariantTest` fails the build over a supervisor queue missing from `waits`, and over a job `$timeout` at or above its connection's `retry_after` (Redis re-hands a reserved job after `retry_after`, and with `tries: 1` the second worker fails the copy while the first is still running — a false `failed_jobs` row and a `failed()` callback on a job that succeeds). That is why the long supervisors run on `redis-long`.
- **A `queue:work` holds the code it booted with, and that is how a fixed bug keeps reporting itself.** The `wss`-scheme fix went in at 16:24 and the worker started before it, so the pipeline kept failing with the exact error the commit removed — `failed_jobs` filling with a stack trace that no longer matches the file on disk. Two minutes of reading the tree for a defect that was not there. Restart the worker after touching anything it runs, and read the timestamps in `failed_jobs` against `git log` before believing a trace. The same run also showed a dev worker whose `--queue` list omitted `maintenance`: **194** scheduled jobs enqueued and never drained, silently. `config/horizon.php` names it correctly in both `defaults` and `environments` — it was the hand-written command that was wrong, which is exactly why that supervisor's own comment says a queue with no worker says nothing.
- **Provider secrets go in the ENVIRONMENT, and the repo's own "operational numbers live in `platform_settings`" rule does not apply to them.** That rule is about NUMBERS an operator tunes from the panel; a `platform_settings` row is readable by everyone who can open that panel, so a signing key there widens who can mint a valid playback token from "whoever administers the server" to "whoever administers a workspace". The size and duration CEILINGS do come from `platform_settings`, through `MediaLimits` — which is also where the adapter's `capabilities()` reads them, so the announced limit and the enforced one cannot drift into two numbers.
- **The npm advisories: `sharp` is FIXED, `postcss` is accepted, and the guard for what remains is CALL-SITE DISCIPLINE — not the config, whatever an earlier version of this note claimed.** ⚠️ **«They only move with Next 16» was TRUE OF `postcss` AND FALSE OF `sharp`, and this note said it of both for a week.** Measured 2026-09-11 by reading what Next declares rather than what the advisory implies: `next@15.5.25` asks for `"sharp": "^0.34.3 || ^0.35.4"` — **0.35.4 was already permitted**, and the tree sat on 0.34.5 only because the lockfile had resolved the lower branch of that `||`. One `npm update sharp --package-lock-only` closed both `sharp` advisories with no major upgrade, no `overrides`, and nothing but sharp and its own platform binaries moving in the diff. `postcss` needed the `overrides` entry it now has: Next pins it as an **exact** version (`"postcss": "8.4.31"`, not a range), so its private copy could not move any other way — while OUR top-level `postcss` was already above every fix, which is why `npm audit` reporting "postcss" *was* reporting Next's copy. ⚠️ **And `npm install` DOES NOT APPLY A NEW OVERRIDE TO AN EXISTING LOCKFILE — it reports «up to date» and changes nothing**, which reads as «npm rejected it» and is the reason to reach for a full regeneration that churns the whole tree. The minimal form is to delete the offending entry (`node_modules/next/node_modules/postcss`) from the lock and re-run: npm then re-resolves that subtree alone, the nested copy disappears into the top-level one, and the diff is **one entry**. ⚠️ **npm records the override in `package.json` and NOT in the lock's root**, so `--dry-run` is not proof — verify with a real `npm ci` into a throwaway directory, which is also where `npm audit` can answer honestly (`found 0 vulnerabilities`) without a stale `node_modules` beside it. **The lesson generalises past these two packages: an advisory's "fixed in X" says nothing about whether YOUR tree can reach X — read the dependent's declared range, because a pin and a range look identical from the alert page.** ⚠️ **`next/image` optimises same-origin and relative paths with no `images` config at all**, so "no `remotePatterns`, therefore nothing reaches `sharp`" is FALSE — a `/storage/...` path would reach it. What actually closes the path is that `frontend/` contains exactly **three** files that import `next/image` — `(public)/page.tsx`, `PageBanner` and `AuthShell` — and every path that reaches one is a literal under `/public`: the first and third write theirs inline, and `PageBanner`'s `image` prop is supplied by seven public page files plus `PolicyPlaceholder`, each a literal `/marketplace/*.webp`, the receipt renders as a plain link and never as an image, and `ReviewsTab` / `TestimonialsCarousel` use a plain `<img>` with a comment saying why. **So the invalidation trigger is a call site, not a config key: pass any user-supplied or remote image to `next/image` and the sharp advisory is live and this note is wrong.** Re-count the advisories before trusting the wording — the list has already grown once (three `postcss` path-traversal GHSAs arrived after it was written), which is why this says "the advisories" and not a number.
- **`withoutOverlapping()` on `Schedule::job()` guards the DISPATCH, not the run** — for a queued job that is milliseconds around the push, released long before the worker starts, so last night's sweep still walking when tonight's begins runs two copies over the same rows. Every scheduled maintenance sweep therefore carries `WithoutOverlapping` as job middleware — `RunRetentionSweepJob` and the other long jobs by hand, the rest through `App\Shared\Traits\RunsAlone` — since the maintenance supervisor runs two workers and the dispatch lock guards nothing on the worker. `ScheduledSweepsRunAloneTest` names the three deliberate exceptions. ⚠️ **But middleware alone is worse** — its lock does not expire, so a worker killed mid-sweep leaves it held for ever and retention silently never runs again. **`expireAfter()` is the load-bearing half**, not the lock.
- **The backend image had NO `php.ini` at all until 2026-09-25, and every value was PHP's compiled default.** Measured on production: `php_ini_loaded_file()` empty, `display_errors=1` (a fatal's text and file path in the response body), `upload_max_filesize=2M` (a 3 MB receipt refused before the `max:10240` rule that allows it ever ran), `memory_limit=128M`, and `pm.max_children=5` on a 16 GB server — the sixth concurrent request queued. `docker/backend.Dockerfile` now copies `php.ini-production` and adds two small files: `conf.d/zz-app.ini` (20M/21M upload, 512M, `expose_php`/`display_errors` off, OPcache sized for the vendor tree) and `php-fpm.d/zz-app.conf` (`pm=dynamic`, 40 children). Horizon, the scheduler and Reverb read the same `conf.d` — one image. ⚠️ `variables_order` is kept at `EGPCS`, the no-ini default, on purpose: `php.ini-production` drops `E`, and "where the environment is read from" is not something to change in the same commit as everything else. ⚠️ **`opcache.validate_timestamps=0` means a manual `php artisan config:cache` (or `route:`/`view:cache`) inside a running `backend` container is invisible to FPM until the container restarts** — every deploy creates a fresh container, so the deploy itself is unaffected; `opcache.enable_cli` is off, so artisan and the workers are unaffected. ⚠️ **`client_max_body_size 512m` in nginx is NOT inconsistent with the 21M `post_max_size`**: the only large upload that reaches PHP is the local media provider's raw `PUT` (`application/octet-stream`, streamed by `getContent(true)`), which neither PHP limit applies to. A new multipart upload above 20 MB needs the ini raised with it — and so does raising `certificates.design_max_size_kb` in `platform_settings` past 20480.
- **A job that fails for good mails `HORIZON_NOTIFICATION_EMAIL` — once per job class per hour — and nothing else alerts anyone.** Horizon's own notifications only cover a queue that WAITS too long; a failure is a `failed_jobs` row nobody opens /horizon to find. `App\Shared\Listeners\AlertOperatorOfFailedJob` (wired in `HorizonServiceProvider`) sends `JobFailedAlert` synchronously — never queued, because the queue is what is failing — throttled by an atomic `Cache::add()`, and carrying the exception CLASS only: a `QueryException` message holds its bindings and this mail leaves through Brevo. Unset address = silent, exactly as before; set it with `scripts/set-secrets.sh`. ⚠️ **None of this fires when the SERVER is down** — no PHP, no mail. That needs a check from outside: an external uptime monitor (UptimeRobot, Better Stack, or similar free tier) polling `https://<domain>/admin/login` and `https://<domain>/api/v1/marketplace/home` every 5 minutes, alerting to a phone. Those two are chosen for the same reason the deploy smoke test uses them: `/` is Next and can be up while PHP is not, and `/admin/login` is the one path that renders Blade. `scripts/autoheal.sh` (cron every 5 min, installed by `deploy.sh`) restarts any `unhealthy` container of the project — `restart: unless-stopped` only revives a container that DIED — except `mysql`, where a restart under load is worse than the symptom; each restart is a line in `/var/log/elmotamayez-autoheal.log`, and a container restarted every five minutes is a defect nobody fixed.
- **The deploy checks out the SHA CI tested, never "whatever `main` is now".** `deploy.yml` passes `workflow_run.head_sha` as `DEPLOY_SHA`; `deploy.sh` refuses anything that is not a full SHA reachable from `origin/main`, and falls back to `origin/main` only for a manual run. The fetch/reset/`exec` now sit inside ONE `if … fi`, which bash parses whole before running a line of it — so the reset replacing `deploy.sh` under the running shell can no longer skip or splice steps (the 2026-09-19 incident). ⚠️ The comment lines above that block are padded so the PREVIOUS version, which kept reading at byte 1246 after its own reset, lands on a comment line and enters the block from the top; that padding only matters for the first deploy of this change.
- **Rollback is `bash scripts/rollback.sh` (to `:previous`) or `bash scripts/rollback.sh <sha>`.** Before each build the deploy tags the image the RUNNING `backend`/`frontend` containers use as `:previous` (from the container, not from `:latest`, which a failed deploy leaves on an image that never served), and tags each new build `:<12-char sha>`; the last three sha tags survive `image prune`. `roll_service` now warms the config/route/view caches in the new container, STOPS (does not remove) the old one, waits out nginx's 10-second resolver cache, and smoke-tests `/admin/login` + the marketplace API (backend) or `/` (frontend) through the real domain; a failure restarts the old container and removes the new one. ⚠️ A rollback swaps images only: the compose file, nginx config and code on disk stay at the newer commit, migrations are not reversed (they are additive by rule), and the NEXT deploy rebuilds from `main` — the real fix is a revert commit.
