# Gotchas — Community, chat, realtime and gamification

Moved verbatim from `CLAUDE.md` (the rule headlines stay there). Read this file before changing `Modules/Community/`, `Modules/Gamification/`, Reverb/Echo, feature flags. Bullets that say «above» may now point into another file in `docs/gotchas/`.

- **A reversal that shares its original's idempotency key is swallowed for ever.** `award_entries` is written with `insertOrIgnore` keyed on `(student, action_key, source_type, source_id, reversal_of_id)`, and a reversal repeats the first four by definition — so without the fifth column it collides with the entry it is reversing, writes ZERO rows, the read-back finds the ORIGINAL, the code concludes "already recorded" and reports success, and the points are never returned. To anyone watching, FR-010 is implemented. ⚠️ **And the column is `NOT NULL DEFAULT 0`, not nullable**: `NULL != NULL` in a unique index on both engines, so a nullable discriminator stops the guard biting for every ORDINARY award instead — the same event paying twice. Zero compares; the sentinel is the fix (precedent: `concept_stats.lesson_id`). `AwardReversalTest` asserts on the AGGREGATE returning to its pre-award value, never on a row count: counting two rows passes against a design that returns nothing.
- **A cause that was reversed is REINSTATED by negating the chain's head, never re-awarded — and a duplicate award gives its daily slot back.** Three defects shipped together and all three were a re-fired event: `ReviseGrade` re-runs `FinalizeAttempt`, re-grading re-fires `SubmissionGraded`, and a teacher can mark a student absent and back. (1) `AwardPoints` claims the daily allowance BEFORE `writeEntry()`, and a duplicate returns null — a normal return, so the transaction COMMITTED the claim: two revisions of one passed paper exhausted `exam_passed`'s cap of two and the student's genuine next pass that day earned nothing. The claim stays first (the race it guards is real) and a duplicate now releases it inside the same transaction. (2) present → absent → present ended with the points gone for ever: the override listener returned on everything but `Absent`, and a re-award could not have landed anyway, because the original still holds the idempotency key. (3) a pass revised into a fail kept its `exam_passed` points. The fix is `Gamification\Support\AwardChain`: each correction is a row whose `reversal_of_id` is the CURRENT HEAD (original → reversal → reinstatement → reversal…), so the key stays unique, two runners negating the same head collide instead of doubling, and `ReverseAward`/`ReinstateAward` both negate the head's frozen amounts. ⚠️ **Parity, never the sign, is the state** — an odd number of rows for a cause is paid, even is reversed — because `deductible()` can clamp a reversal to 0/0. That is also why `EvaluateBadges::countOf()` counts causes with an odd number of rows: «originals minus every other row» counts a reinstatement as a second reversal. ⚠️ **A reinstatement is not a second `AwardPoints` call**: that would pay today's catalogue price through today's cap, not what the reversal took — a reversal that could only claw back 2 of 5 coins would be answered with 5, and a full cap would refuse the restoration outright. Out of scope and named: a student marked absent at the close and corrected to present later was never awarded, so there is no chain to reinstate; awarding them from the override would need the session's workspace and completion state through a contract. `AwardRefireFairnessTest` asserts on the aggregate and each case was proven to fail with its fix reverted.
- **The gamification catalogue is reference data, so an empty one awards nothing and every assertion passes against zero.** `AwardPoints` looks an action up by key and returns silently when there is no row — an award for an undefined action is an unfilled catalogue, not an error. `tests/Pest.php` therefore seeds `GamificationCatalogSeeder` before every Feature test, exactly as it seeds the notification templates, and it is deliberately a handful of rows because all ~1,600 feature tests pay for it.
- **The day and week boundary lives in `GamificationCalendar` and reads the ONE platform zone, `SessionSettings::timezone()` — which since 2026-09-25 is `SESSIONS_TIMEZONE` and nothing else.** A third declaration of the platform's timezone is the mistake that lets the daily cap drift away from the class schedule in silence. ⛔ **And until 2026-09-25 there were TWO, while this line said one**: `SessionSettings` read a `platform_settings` row that `/admin` → «إعدادات الحصص» could edit, while `routes/console.php` (the scheduler) and `config/notifications.php` read the environment — so a panel save moved the billing day, the freeze day and the gamification week and left the nightly sweeps on the old clock. The scheduler cannot be the side that moves: `routes/console.php` loads when `schedule:work` boots and in every artisan command, `migrate` on an empty database included, so a cache or database read there takes the scheduler and a fresh deploy down with the store. So everything reads the environment, the row is deleted (`2026_09_25_000100`), the key is out of `PlatformSettings::KEYS`, and the panel field is disabled. ⚠️ **The platform zone is for DAY BOUNDARIES only, never for showing a time** — people read their own clock (`UserClock`, `useViewerTimeZone()`; see `live-sessions.md`). ⚠️ And `dayBounds()` returns a pair of UTC timestamps, never a string compared against a column: `whereDate()` wraps the column and throws away its index (the `FreezePeriod::covering()` lesson), and `CONVERT_TZ()` returns **NULL on any MySQL without the timezone tables loaded** — the common case on managed MySQL — so the predicate matches nothing, **the cap is never enforced**, and nothing errors. SQLite has no `CONVERT_TZ` at all, so no local test can see it. `format('W')` is banned for the week key: ISO weeks start Monday, so every Sunday would carry a different number from the six days after it and one week would split into two period keys.
- **A picker is derived from the AUTHORISER'S OWN PREDICATE, never assembled beside it.** 009 shipped six leaderboard scopes of which five were reachable only by typing a URL, and the obvious fix is the trap: the nearest list the profile screen already holds is the student's coin purses, and a teacher board is authorised on an **active enrolment**. A purse outlives the enrolment (a departed teacher's coins still show, deliberately) and lags it (a fresh enrolment has earned nothing yet) — so a purse-built picker offers boards the API answers 403 and hides boards it allows. `ListLeaderboardScopes` reads `EnrollmentDirectory` exactly as `ReadLeaderboard::workspaceFor()` does, and `LeaderboardScopesTest` walks **every returned option through the real endpoint**, which is what fails if the two spellings drift apart again. Same family as `BookingEligibility`'s host check: two spellings of one question put one answer on the screen and another at the door. The grade option comes from `courses.grade_level` — the column the rollup groups on — not from `student_profiles.grade_level_slug`, which is what the student would call their year and can differ, producing an offered board they are not on. And an empty list is a **teacher**: fetching the board anyway is a 403 about a screen that is simply not theirs, so the page says so instead of showing a refusal.
- **A middleware list given to `withBroadcasting()` REPLACES the `api` group, and the thing it drops is spatie's team id.** `/api/broadcasting/auth` carried `auth:sanctum` and a named throttle and nothing else, so `EnsureCurrentWorkspace` never ran — and spatie is in team mode, where **no team id means no roles at all**. `hasPermissionTo('chat.reply')` was therefore false for every teacher, `ConversationPolicy::view()` denied, and every private channel subscription was answered `403` while the same teacher read the same thread over HTTP without trouble, because THAT route is inside the group. The `/api` prefix makes it look like an API route; the prefix is a URL, not a middleware stack. ⚠️ **No test could see it**: `subscribeToChannel()` posts to the route from a process where `Sanctum::actingAs()` has already set the team id, so the suite proves the callback's logic and never the request's. Found on 2026-08-23 by the first real socket, the LiveKit lesson reached from a second direction — and its sibling is **`announce()`'s catch, which does not see a Reverb outage either**: `MessagePosted` is `ShouldBroadcast`, not `...Now`, so `event()` enqueues and returns while the publish fails on the worker. That failure belongs in `failed_jobs`; `SC-015` is about the ROW surviving and the reader being one refresh behind, and both hold with the server killed mid-session.
- **pusher-js unbinds BY FUNCTION REFERENCE, and removes every entry matching it — so two subscribers passing the SAME function are both killed by the first cleanup.** A `useCallback` with empty deps is exactly that function, and React's development double-invoke produces two `listen()` calls from one mount, so the shape reaches a page carrying a single listener. It shipped alongside a second defect in the same file with the same cause: `echo()` guarded construction with a boolean `attempted` flag, so the SECOND concurrent caller — the notification bell and the conversation list both want the socket, which is every panel page — was answered `null` for the life of the tab. Both were invisible while exactly one screen used the socket. The fixes are a memoised PROMISE (every caller awaits the same construction, whenever they arrive) and a per-call wrapper closure so each subscription has its own identity; `leave()` is then refcounted, because it drops the whole channel and the bell and the sidebar share `user.{uuid}` on purpose. ⚠️ **Diagnosing this needs the wire, not the code**: the channel reported `subscribed: true`, the queue job reported `DONE`, and `bind_global` showed the frame arriving — the only thing that named the fault was counting the callbacks bound to the event (`channel.callbacks._callbacks`) and finding one where there should have been two.
- **`window.Pusher.instances[0]` is a corpse after any hot reload.** Every HMR pass builds a new Echo client and the array only grows, so a probe reading index 0 reports «zero channels» about a page whose live socket is fully subscribed — which is how a measurement error becomes an hour spent hunting a third defect that was never there. Read `.at(-1)`. Same family as the repo's own rule about believing a `failed_jobs` trace older than the fix on disk.
- **`hidden_at`, never `deleted_at` — on `messages` and on `announcements` both.** A soft delete puts the row behind Laravel's global scope, which is exactly where the moderation screen and the audit cannot see the thing they just acted on; a moderator who cannot read what they hid cannot undo a mistake, and the report that provoked it points at a row that no longer resolves. Hiding an announcement additionally deletes the `notifications` rows the fan-out wrote — the claim on `hidden_at` comes FIRST, so a second runner finds nothing left to claim and the feed is cleaned exactly once.
- **The broadcast payload is two identifiers, and the second reason is the one that gets «simplified» away.** The obvious reason is that a socket frame is not an authorised response. The load-bearing one is REVOCATION: a channel is authorised once, at subscribe, and the protocol has no revocation call — so an assistant whose permission is withdrawn mid-session keeps receiving every event on a channel they were admitted to. With an identifier alone that is harmless, because the fetch it provokes goes through the authenticated route and is refused there on the very next request. Put the body in `broadcastWith()` and the withdrawal takes effect when they close the tab.
- **`ReadRanksFor` reads ONE week's board, and a rank and a level come from different tables.** Boards are rolled up nightly, so a student who signed up this morning has no `leaderboard_entries` row while their level is cumulative and true today — reading the level off the entry blanks it for exactly the newcomer the badge is encouraging. Absence is a STATE and the key is left out: a zero is «المركز ٠» printed beside the teacher's own name in front of the class. And it is bulk by construction — a Resource runs once per row, so a per-student lookup is the `ClassSessionResource` N+1 reached from a new direction.
- **A departed teacher's chat closes for WRITING and stays open for reading, and the question lives in the policy rather than on the row.** `ConversationPolicy::post()` asks `TeacherOffboardingDirectory::hasDeparted()`. The enrolment cannot express it — 013's FR-035 keeps the course a student PAID for until their term ends, which is the very condition `post()` already reads — so without this a student writes into a workspace with nobody left to answer, for ever, and nothing tells them. It is **not** a `closed_at` column because `StartConversation` authorises an UNSAVED `Conversation` against the same ability: a stamp cannot answer for a row that does not exist yet, and a second guard beside that door is the two-spellings defect `BookingEligibility` and `ListLeaderboardScopes` have each already paid for. It is asked on EVERY kind, rooms included — a lesson room in a workspace with no `chat.reply` holder left is the same void wearing a different name.
- **A socket host written down once is wrong for every other address the same build is opened from.** `NEXT_PUBLIC_REVERB_HOST=localhost` in `frontend/.env` made a phone that loaded the page from `192.168.x.x:3000` dial its OWN localhost — the chat still read and sent, one reload behind, with no error naming a cause, which is exactly what «النقاش لا يظهر لحظيّاً» looks like. And the scheme literal `http` is worse: a browser refuses a `ws://` socket opened by an `https` page as mixed content, silently, so any experiment with local HTTPS (`next dev --experimental-https`, reached for because a phone will not grant a camera to an insecure origin) takes live delivery down with it. Both fall back to `window.location` in `echo.ts` and both are left EMPTY outside production, where the socket really does sit behind a proxy on another host. ⚠️ `NEXT_PUBLIC_*` is inlined at compile time — editing `.env` and restarting the dev server in the wrong order ships the old value with no sign of it.
- **The room's discussion lock is a COLUMN, and it is the only refusal in `ConversationPolicy::post()` that is.** A ban is a workspace-wide fact, a teacher's departure is read from their offboarding, an ended relationship is read from the enrolment — a lock is none of those: it is a decision somebody made about one room at one moment with nothing else to derive it from. `conversations.locked_at` is a timestamp rather than a boolean because «مقفول» is asked about a lesson that ended hours ago as much as about this one, and it is never re-stamped: a second press is not a second decision. Two halves are load-bearing. **Whoever may lift it is exempt from it** (`chat.moderate`, not «the host», because an assistant with moderation is exactly who watches the room while the teacher talks) — a teacher locked out of the room they just closed cannot answer the last question on screen or say why they closed it. And it is **refused on a private thread**: silencing one person there is a BAN, which is declared workspace-wide, recorded and appealable, and two ways to silence somebody with only one of them audited is the one nobody reviews.
- **A permission nothing links to is a permission nobody has, and 021 shipped one for a phase.** FR-046 grants permanent READ of an old group's thread after a transfer; `ConversationPolicy::view()` admits whoever was EVER a member, `post()` refuses them with a sentence, and `CohortChatBanTest` proved all of it — while `ChatTab` knew only the group the reader is in TODAY, so the entitlement sat behind a uuid nobody was ever shown. `/courses/{course}/cohorts` answers `past_cohorts` now and the tab carries a picker. Same family as `writeBans.lift`, which had an endpoint, an Action and no screen — which is why `SilenceControl` withheld «حتى أرفعه بنفسي» until the lift button existed: an open-ended ban whose only exit is a request typed by hand is a control with no way out. **The two ship together, and the test that guarded the ABSENCE was inverted rather than deleted.**
- **A whisper is REFUSED on a private channel and ACCEPTED on a presence one, and that single fact decides both of this spec's channels in opposite directions.** `config/reverb.php` sets `accept_client_events_from => 'members'`. So the attendance channel is **presence** because «يكتب الآن» is otherwise a route, a table and a write per keystroke — and the study-room board is **private** because a presence channel there would open an unmoderated direct chat between children inside a room: no `hidden_at`, no `ConversationPolicy`, no ban check, no `chat.moderate`, and nothing anywhere to read afterwards. Its authorisation asks `StudyRoomAccess`, the same class `JoinStudyRoom` asks; two spellings of one question is how one answer reaches the screen and another reaches the door.
- **A PRIVATE CONVERSATION IS BORN WITH ITS FIRST MESSAGE, A PROSPECT MAY WRITE UNTIL THE TEACHER'S SIDE ANSWERS, AND A GUARDIAN WRITES AS THE CHILD IN THE CHILD'S THREAD (2026-09-28, «تواصل مع المدرّس», hardened by the security review of #276).** **(1) No empty threads.** «راسل» used to `POST /conversations` on press, so an empty conversation stood in both sides' lists before anybody typed — reported from production. The request now REQUIRES `body`; `StartConversation` hands `PostMessage::deliver()` an UNSAVED `Conversation`, and the thread, the student's participant row and the message are one transaction. Every button goes to `/messages/new` (compose) or to the existing thread. ⚠️ The race is still declared: the loser's transaction rolls back **its message with it**, so the loser re-finds the winner and delivers the same words into it — and `attempts` is **1** for a new thread, because a retry would find the model already marked `exists`. A word-for-word repeat of the thread's newest line by the same sender within 60 seconds is a RETRY after a dropped response and writes nothing. `ListConversations` hides `last_message_id IS NULL` rows, except the one named by `?include=`, which is also ORDERED FIRST — NULLs sort last on MySQL and would fall past the limit. **(2) «Subscriber» is `hasActiveEnrollmentInWorkspace()` and nothing beside it** — `ActivateSubscription` writes an enrolment and `JoinCohort` demands one. ⛔ **The student of a private thread is a LEARNER**: `post()` refuses a student account that `teachesOnPlatform()` (true from public teacher signup, BEFORE approval — without this an applicant omitted `student` and wrote to every other teacher as a «prospect») and one whose `platform_role` is `parent` (a guardian always names a child). ⛔ **A guardian carries the child's workspace ban** — the ban at the top of `post()` is asked of the SENDER, and the child's parent was the way around it. **(3) A prospect reaches only a PUBLISHED teacher** (`TeacherStanding` = `TeacherProfile::publiclyListed()` in the workspace): a suspended teacher or an unapproved applicant takes no new prospect threads and no prospect posts; subscribers are never asked. **(4) The cap** is `community.chat.prospect_message_cap` (3, a `platform_settings` row with a backfill migration), counted per THREAD — student and guardian share it — **hidden messages included**, and it also refuses the attachment UPLOAD TICKET once spent (a ticket reserves storage). ⛔ **The budget runs from the EPOCH — the moment the student became a prospect** (owner decision): the thread's start for somebody who never studied here, or `EnrollmentDirectory::accessEndedAt()` (the latest `updated_at` of a non-granting enrolment — every writer that ends one is an Eloquent update) for a former student. Their messages are counted from it and only a teacher-side message **strictly after** it (`messages.from_staff`, stored at send time from the policy's verdict) lifts the cap — so a former student starts from scratch, a reply from their enrolled months unlocks nothing, and nothing is stamped on the conversation that a deploy, a backfill or a missed event could get wrong. The `from_staff` backfill marks old lines truthfully and unlocks nobody: every old staff reply predates the epoch, because the old policy refused both sides after an enrolment ended. ⚠️ **The gate is `UPDATE conversations SET id = id` as the transaction's FIRST statement, then the count, then the insert** — `CreateFreezePeriod`'s idiom; `lockForUpdate()` is a no-op on SQLite and a sequential «send four» test is green with no gate at all. `ContactTeacherTest` pins the order and fires the rival from inside the gate. **(5) The teacher's switch** «استقبال رسائل من غير المشتركين» (`workspaces.settings.inbox.accepts_prospects`, default ON, `settings.update` = the owner) **binds the student's side only** (owner decision): turned off, no prospect writes, and the teacher side still answers in every thread that exists. ⚠️ **The teacher's side answers a prospect and never opens one** — staff may post to a non-subscriber only into a thread that exists AND has a message, or «راسِل» is a cold-message channel to every account on the platform. **(6) A guardian writes AS the child**: `student_user_id` stays the child, the right is an ACTIVE relation carrying `GuardianPermission::Messages`, asked through `GuardianDirectory` by `ConversationSides`; a migration granted it to every accepted relation on deploy (owner decision), and the student removes it on /family. The teacher reads WHO wrote a line from `messages.sent_by_guardian`, stored at send time. **(7) `throttle:conversation-start`** (5/min, 20/hour, 40/day per account) exempts ONLY a teaching account that NAMES a `student` — the teacher-side start, which the policy already confines to their own enrolled students; a teaching account naming nobody is asking to be the student and is counted like anyone. The button reads `GET /conversations/contact-options`, which inspects the same policy on the real row or the same unsaved candidate, and its name is `TeacherContactName` — the course's author with the academy in brackets, never the workspace alone.
- **Chat media reused the lesson-media `complete` endpoint, and its policy answered a TEACHER's question.** A chat picture or voice note is uploaded in three steps — ticket, signed `PUT`, complete — and the client finished it through `POST /media/assets/{asset}/complete`, whose `MediaAssetPolicy::view()` is «may you manage lesson content here» (`LESSONS_MANAGE` + workspace membership). A student holds neither, so every picture a student sent was refused with «لا تملك صلاحية لهذا الإجراء» AFTER its bytes had landed (production, 2026-09-28: the `PUT` answered 200, the `complete` 403). It looked like it worked because the only person who ever tried it in development was the owner, who holds every tenant permission. The fix is a sibling door, `POST /conversations/{c}/attachments/{a}/complete` → `CompleteChatAttachment`, asking the two questions that belong to a chat: `ConversationPolicy::post()` (the same guard as the ticket and the message) AND `media_assets.uploaded_by_user_id` — the thread has two ends, and «may post here» alone lets the other end settle a file they never sent. Both segments are strings resolved without the workspace scope, per the no-implicit-binding rule at the top of `Community/routes/api.php`. ⚠️ **Not a branch in `MediaAssetPolicy`**: Media knowing what a `Conversation` is would point the dependency the wrong way, and the lesson door stays byte-for-byte what it was. ⚠️ And the fixture is what hid it for a month: `ChatAttachmentTest` builds a `Ready` asset by hand, so no test ever walked the real three steps. `ChatAttachmentCompletionTest` does, as a student, with real bytes. ⚠️ **And the old door now refuses anything that is not a lesson's** (`owner_type` must be `Lesson`, else 404): a teacher holding `LESSONS_MANAGE` could otherwise finish a chat asset there, skipping the uploader check and the chat mime list — a PDF passed as a «picture». The chat completion answers `{uuid, status}` only: `MediaAssetResource::failure_reason` can carry a provider's exception text.
- **`join()` read `room.members` — a property Echo's channel object does not have — so «يكتب…» never once sent a whisper.** pusher-js keeps the member list on the SUBSCRIPTION (`room.subscription.members`), and Echo's presence channel wraps it without re-exposing it. `me` was therefore always undefined, and the guard written to stop a whisper before the subscription succeeds (`if (me === undefined) return`) swallowed every one — the typing indicator shipped, rendered, expired on a timer, and had nothing to show. Nothing failed anywhere. The same file now binds its own `here`/`joining`/`leaving`/`client-typing` callbacks on the subscription and UNBINDS them by reference on release: Echo's `here()` wraps the handler in a closure of its own with no way to remove it, so a second holder of the channel (React's development double-invoke) left the first holder's callbacks bound and «joining» counted every arrival twice. The receiving timer and the sending throttle are `lib/typing-indicator.ts`, tested with fake timers.
- **«Online on the platform» is an OCCUPIED `private-user.{uuid}` CHANNEL, asked of Reverb by the server — never a presence channel the counterparts join.** Owner decision 2026-09-28: a WhatsApp-style dot beside every name in the list, privacy trade-off accepted. Every signed-in tab already holds `user.{uuid}` (the bell and the sidebar), so `ReverbOnlineDirectory` asks the Pusher HTTP API once (`GET /channels?filter_by_prefix=private-user.`, cached ten seconds and shared) and `ListOnlineCounterparts` filters the answer to the other end of the reader's OWN private threads — read from `ListConversations`, the same predicate as the list, with no uuid parameter anywhere, so nobody can ask about a person they share no thread with; the answer is conversation uuids, never a user uuid, time or «last seen». The two obvious designs are each a defect: a presence channel per person that counterparts JOIN hands every joiner the MEMBER LIST, so each student would see which other students talk to that teacher; a presence channel per conversation joined from every page is one subscription and one `/broadcasting/auth` per thread, per page load — two hundred for a busy teacher, on the `broadcast-auth` limiter. «The other end» for a student is the workspace OWNER (the name on the row), never «any assistant». The thread header keeps its own, narrower dot and «متصل الآن» from `chat-presence.{uuid}` («has THIS thread open»), and the list merges the open thread's live presence in so the row never lags its header. The list re-asks every 30 s while visible, on becoming visible, and on every `message.posted`. `OnlineCounterpartsTest` asserts WHO the directory was asked about, not only what came back.
- **A confined assistant runs the ROOMS of their own courses only, and until 2026-09-29 the room's teaching side asked membership and `chat.reply` and nothing else.** `ConversationPolicy::publicRoom()` admitted any member holding `chat.reply` to the room under every session, lesson and group in the workspace, and `moderate()` (lock · write-bans), `ModerateMessage` (the moderator's hide, workspace-shaped) and `MessagePolicy::markHelpful()` asked no more — so an assistant confined to one course read, wrote into, locked, silenced and endorsed in every other course's rooms while #286's `ClassSessionPolicy` refused them the far session itself. All of them now end in `ConversationPolicy::withinStaffScope()`: a room asks `mayActOnCourse()` with the course of its session, lesson or group (a **course-less session's room is refused** to a confined assistant, as the session is); a private thread asks `mayActOnStudent()`, `teacherSide()`'s question. Every student branch (seat, opened hour, enrolment, group membership) is untouched — and a scope refusal FALLS THROUGH to them (owner decision 2026-09-29): an assistant confined to one course who also booked a seat in a far session, is enrolled in the far course or sits in the far group reads that room AS A STUDENT, which the first version of this fix took away. That is safe only because no staff power asks `view()`: `moderate()` ends in `withinStaffScope()`, «مفيدة» asks `ConversationPolicy::staffSide()` (never `view` — «may read» is no longer «reads as staff»), and every moderator exemption in `post()` (lock · ejection · group membership · per-thread ban) reads `$moderatesHere` = `chat.moderate` AND the scope, with `runsTheRoom()` scoped the same way for the seat rule. A new staff power on a room must ask one of those, never `view()`. **Three leftovers closed the same day.** (1) The WORKSPACE ban (`subject_type = user`, ban AND lift) has no room to ask, so it asks the PERSON: `ModerationActionPolicy::banPerson()` = `moderate()` + `mayActOnStudent()` — a confined assistant bans only a student enrolled in one of their courses, and a colleague, a prospect or a far-course student is refused (403), because that ban silences the person in every thread of the workspace. (2) `ListConversations` lists a room outside a confined assistant's courses only when `view()` admits them (a student entitlement) — rooms reach a staff list only through a participant row, which nothing writes for a room today, so the per-row policy call is paid on an empty set; their own courses' rooms are decided from `RoomCourses::forMany()` (≤ 3 batched reads — the same class `ConversationPolicy::courseOfRoom()` now delegates to, one spelling). (3) `ConversationResource::can_moderate` is the permission AND the scope: the list stamps `Conversation::$readerInStaffScope` in bulk for a confined reader (rooms from the course map, private threads from the memoised `mayActOnStudent()` the filter already paid), an unconfined reader is answered from the directory's per-request memo (no new query), and only a single-row answer for a confined assistant (`/class-sessions/{s}/chat`, the lock, a new thread) asks `Gate::allows('moderate')` once. `AssistantChatScopeLeftoversTest` carries all three plus a query budget. The unlock rules and exemptions (`UnlockRuleController`) got the same check the same day — the default rule is «no course», so a confined assistant reads it and cannot write it. `AssistantRoomChatScopeTest` · `AssistantUnlockScopeTest` · `AssistantChatScopeLeftoversTest`.
