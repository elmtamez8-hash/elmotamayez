# Gotchas — Tenancy, workspace scope, roles and permissions

Moved verbatim from `CLAUDE.md` (the rule headlines stay there). Read this file before changing `Modules/Tenancy/`, any policy, `WorkspaceScope`/`WorkspaceContext`, Filament resources, platform-permission reads and writes. Bullets that say «above» may now point into another file in `docs/gotchas/`.

- **Platform-owned entities have no scope at all — the Action is the guard.** Since spec 003 the constitution classifies every model into one of three layers, and `notifications`, `notification_preferences`, `parent_student_relations`, `message_templates` and `contact_verifications` are **not** workspace-scoped by design (a student has one feed and one set of preferences across every teacher they study with). That means no global scope touches them, so they are as exposed as an unauthenticated marketplace query. The guard is written explicitly: ownership of the row, plus — for a teacher reading a student's guardians — an **active enrollment in that teacher's own workspace** (`ParentStudentRelationPolicy`). `tests/Feature/Notifications/PlatformOwnershipTest.php` tests both failure directions, including the mirror-image bug of adding `BelongsToWorkspace` where it does not belong, which silently duplicates one person per teacher.
- **`WorkspaceScope` is inert for guests.** `WorkspaceScope::apply()` returns early adding no condition when `WorkspaceContext::id()` is `null`, which it always is without an authenticated user. So an unauthenticated request has **no tenant isolation at all** — a public query without a guard returns every workspace's rows, including drafts. The replacement guard is the `IsPubliclyListed` trait's `publiclyListed()` scope (workspace participation + the model's own `publicListingConstraints()`). Every Action reached from a public route must start from it, and `PublicExposureTest` walks each public payload against `PublicFieldAllowlist` to catch what slips through. Never bind a public route to a model implicitly: `Route::get('/teachers/{teacher}')` resolves by uuid without the guard.
- **Never call `WorkspaceContext::set()` from a job or console command.** It is an application-wide singleton that caches its resolution, so the workspace leaks into whatever the same worker handles next. Use `forWorkspace($workspace, fn () => ...)`. `tests/Feature/Marketplace/TrustScoreJobIsolationTest.php` fails the build if a `set()` appears under `Modules/Marketplace/Jobs/`.
- **An Action that acts on a named student must prove the student is theirs.** `exists:users,uuid` answers a different question: NFR-001أ forbids a teacher learning anything about someone with no active enrolment in their own workspace, so a bare uuid parameter is an identity probe — pass any user's and the response comes back carrying their name. `CreateFreezePeriod` asks `EnrollmentDirectory` before it writes.
- Adding a tenant-scoped model without `BelongsToWorkspace` leaks data across workspaces and no test will catch it unless you add one to `tests/Feature/Tenancy/WorkspaceIsolationTest.php`.
- **`belongsToCurrentWorkspace()` raises NO objection when the context is null — and until 2026-08-26 it denied, which locked every real student out of the product.** `WorkspaceContext::id()` falls back to `users.last_workspace_id`, and **nothing on a student's path writes that column**: its only writers are `CreateWorkspace` (the owner) and `WorkspaceContext::set()` — reached from `AcceptInvitation` and `SwitchWorkspace`, both about workspace MEMBERS — plus the two seeders. Enrolling writes nothing and signing in writes nothing. So the context is null for everybody who registered and bought a course, and comparing a real `workspace_id` against null denied them their own rows. The sharpest tell is `EnrollmentPolicy::view()`, where the very next line is the ownership branch (`student_user_id === $user->getKey()`) — unreachable, for the person who owns the row — and `/learn/lessons/{uuid}` is the ONLY surface in the product that plays a lesson. Five endpoints were dead at once (book a seat · open a session · read your own attendance row · ask why a join was refused · **play any lesson**). ⚠️ **The query layer had always read null the other way**: `WorkspaceScope::apply()` adds no condition when the id is null, and has since 001 — one answer at the query and another at the door is the two-spellings defect this file records six times over. It cannot open anything, because null also means no spatie team id, so every `can()` below it is already false and only an explicit ownership branch can allow. ⚠️ **And no test could see it**: `Sanctum::actingAs()` + `setCurrentWorkspace()` gives the test student a context production never gives them, `addWorkspaceMember()` additionally stamps the column, and both seeders stamp it on their demo students — so even a manual walk misses it unless the fixture is built without a seeder. **A test of anything student-facing must leave `last_workspace_id` NULL and reset the context singleton**, or it is measuring a person who does not exist.
- **A platform-permission read must declare `withoutWorkspaceScope()`, AND repeat it in every eager load.** `WorkspaceContext::id()` falls back to `users.last_workspace_id` for every user including a super admin, so a platform report left scoped shows one teacher's money as the platform's total — and passes its own test on a single-workspace fixture. The bypass is per model: `->with('order')` runs Order's global scope inside the relation query and returns null for every row outside the reader's fallback workspace. That one shipped in the audit chain, answering "nothing was bought" with a 200. Any test of a platform-wide read needs TWO workspaces or it proves nothing.
- **A workspace role may never hold a platform permission, and the guard is on the MODEL.** Roles are editable from `/admin` now, and the same tick box unguarded is how an owner grants themselves the collection report and the platform's half of the price. The picker offers `RolePermissionMatrix::tenantPermissions()` — but a filtered form shapes one request and not the next, so `Tenancy\Models\Role` throws on `givePermissionTo()`/`syncPermissions()` when a platform permission reaches a role with a `team_id`. The platform set is **derived** (`all()` minus everything any workspace role holds), so a permission added tomorrow is platform-level until somebody puts it in a tenant role on purpose. And both seeders import `Tenancy\Models\Role`, not spatie's: `config('permission.models.role')` governs what the PACKAGE resolves internally, while a class named directly in a file is the class that runs — reaching for the base class is the third door `ImmutableAuditTest` already names for the activity log.
- **`roles` is workspace-scoped now, and `/admin` is why.** Every teacher can reach the panel, so an unscoped role list hands one teacher another teacher's roles with an edit button beside each. `TeamRoleScope` keys on spatie's team id (the same number `EnsureCurrentWorkspace` pushes in, so it agrees with every permission check in the request) and is inert when that id is null — the platform context. `RolePolicy` is the row-level half, because a list filtered by a query and a record fetched by id are two different questions. Deleting a DEFAULT role is refused: `SeedDefaultRoles` runs once at workspace creation, so a deleted `teacher` never comes back and every member holding it loses everything at once.
- **Platform standing is a table, because spatie cannot express it.** `model_has_roles` puts `team_id` inside its primary key and forbids NULL, so `finance-admin` — seeded and correct since 006 — could be given to nobody. `platform_staff` carries who, which role, by whom and why; a `Gate::before` turns it into that teamless role's permissions in whichever workspace the officer is looking at. That hook returns **`null`, never `false`** (false short-circuits every policy behind it) and answers only for names in `Permissions::all()` (Filament checks `view`/`update` on models constantly). `PlatformStaffDirectory` memoises per request and declares `withoutTeamScope()` — the one sanctioned bypass, without which the scope hides the very role the officer's permissions come from.
- **Filament Shield generates nothing here.** `permissions.generate` and `policies.generate` are off and `format_custom_permission_keys` is **false** — our names are dotted and lower-case, and the formatter would pascal-case `billing.audit.view` into a string no policy has heard of. Shield's `super_admin` and `panel_user` roles are off too: super-admin is the `users.is_super_admin` column, and a second one wearing a role is two answers to one question.
- **⚠️ «A STUDENT IS A MEMBER OF NO WORKSPACE» IS TRUE OF A SELF-REGISTERED STUDENT AND FALSE IN GENERAL — measured on 2026-09-09, and this file asserts it in four places.** The real development database held `workspace_members` rows of `tenant-owner` ×25, **`student` ×6**, `teacher` ×1, `assistant-teacher` ×1: a teacher or a seeder can put a student into a workspace, and `PaymentTest` builds its buyer that way (`addWorkspaceMember($workspace, 'student')`) — which is also the ONLY shape that reaches `POST /courses/{course}/orders`, since that route asks `orders.create` and spatie's team id is null for anyone who is a member of nothing. **So membership is not the teacher predicate.** Spec 033's «a teacher never buys» guard was first written as `workspaces()->exists()` and would have refused a purchase to every one of those students — the reported bug's mirror image, costing the platform its revenue instead of a stray row. The predicate is the pivot ROLE, asked in the **negative** (`User::teachesOnPlatform()` = `wherePivot('role', '!=', Roles::STUDENT)`), so an unknown custom role fails toward refusal rather than silently reopening the door; a workspace owner always also holds a `tenant-owner` row, so ownership needs no branch of its own. ⚠️ **`users.platform_role` is NOT a substitute**: it agrees perfectly where it is set and is **null for 37 accounts including 8 with teacher-side pivot roles** — a guard reading it lets those eight straight through. ⚠️ And the writer list this file gives — «only `AcceptInvitation` and `CreateWorkspace`» — is short: `UpdateWorkspaceMemberRole`, `CreateAssistantAssignment` and the seeders write that pivot too. What the paragraph below still gets RIGHT is its actual subject: the *self-registered* student who buys a course is a member of nothing, so `WorkspaceContext::id()` is null for them and the scope really is inert on every route they reach.
- **`WorkspaceScope` is inert for a STUDENT, not merely for a guest — and that is what guards every student route in 009.** A student is a member of no workspace at all (only `AcceptInvitation` and `CreateWorkspace` write that pivot), so `WorkspaceContext::id()` is null and `WorkspaceScope::apply()` returns early adding no condition. `BelongsToWorkspace` therefore protects **nothing** on any route a student can reach: an implicit `{reward}` binding resolves any teacher's reward, and `GET /gamification/redemptions` without an explicit `where user_id` returns every redemption on the platform. The guards are the explicit filter and the enrolment check, and `RedeemReward` resolves the uuid INSIDE the Action after checking. The mirror of this is that route-model binding IS safe on the teacher's routes — the reader is a member there, so the scope resolves and a foreign row 404s before any policy runs.
- **A permission classified by ABSENCE passes every test it has while guarding nothing.** `taxonomy.manage` shipped in 009 declared, seeded, named in a migration's docblock, and asserted platform-level by `CatalogPermissionTest` — and read by **no file at all**: `subjects` and `grade_levels` had no policy and no screen for the whole phase. `RolePermissionMatrix::platformPermissions()` is `all()` minus everything any tenant role holds, so the classification is perfectly true of a constant nobody calls, and the tenant-side test (`the owner does not hold it`) is *also* true when the answer is "nobody asks". **The check that catches it is the ALLOW direction**: a deny-only test passes just as well against a `Gate::policy()` line that was never added, because Laravel's guesser fails **open** into "no policy applies" — and it fails open exactly when one policy serves two models, which is the shape this repository keeps choosing (`CataloguePolicy`, `TaxonomyPolicy`). ⚠️ And the deny in such a policy's `delete()` is **not** the guard for the person most likely to press the button: `AppServiceProvider`'s `Gate::before` waves a super admin past every policy method, so refusing deletion has to be repeated on the Filament Resource — the same discovery `CreditPackageResource` already wrote down, reached again from a different module.
- **`WorkspaceContext::forget()` inside a listener signs a paying student out of their own course.** It is an application-wide singleton that CACHES its resolution: pushing a team id into spatie's registrar and then dropping the resolution leaves the next request resolving from scratch, and for a student — who has no `last_workspace_id`, being a member of nothing — that is a null context, a null team id, and therefore **no roles at all**. Their next read answered `403` about a lesson they had paid for: `FR-035` broken from inside `FR-037`'s implementation by a line meant to be housekeeping. `forWorkspace()` is the only correct shape — it sets both and puts both back — and it is the same helper every job uses, for the mirror of this reason.
- **A Filament LIST never calls the row policy, so a careful `view()` guards nothing on a screen.** `OrderPolicy::view()` cuts credit purchases away from a teacher and orders away from anyone without `ORDERS_VIEW_ALL` — uuid by uuid, on the API. `OrderResource` declared no `canViewAny()`, so Filament fell back to `viewAny()`, which was an unconditional `Response::allow()` that **the API never calls at all** (`OrderController::index()` filters by hand and asks no policy). Add `EnsureFilamentAccess` admitting `assistant-teacher` to the panel **by role name**, and an assistant read every student's email beside the amount they paid, in a workspace where FR-003 says they may see no financial data whatsoever. Two rules fall out and they are not the same rule: a policy method **nothing in the HTTP surface exercises** is a method nobody has ever tested, so its default is whatever the first person wrote; and **a table needs its own cut on the query** (`getEloquentQuery()`), because the row-level ability is never consulted for a list — repeating `OrderController::index()`'s credit-purchase filter is not duplication, it is the only place that question gets asked on that screen. Found by the spec 010 agent review, before the phase that exists to enforce FR-003 had written a line.
- **The assistant wall is at the CHECK, never on the role name — and `scoped()` is the third of three container lifetimes, not a style choice.** `Gate::before` asks `AssistantScopeDirectory::isAssistantIn()` and refuses the financial permissions there, so a custom role named anything at all is still walled; a rule written against `assistant-teacher` is one rename away from nothing. The binding is `scoped()` for two OPPOSITE reasons: not `bind()`, because that hook runs on every permission check — dozens per Filament page and once per row of any list that asks a policy — and not `singleton()`, because a worker's container outlives the job, so an assistant revoked at noon would keep passing a cached `true` until the worker restarted. `SC-003` is measured over HTTP and would never have seen it. **`billing.balance.view` is the ONE financial item a teacher may delegate** — a count of remaining sessions with no amount anywhere near it — and `ContextIsolationTest` now fails the build over a `use App\Modules\Payments` written anywhere under `Modules/Community/`, because a behavioural guard only answers about the doors somebody remembered to try.
- **`(int) null === 0` addresses the PLATFORM row of `feature_flags`, and the hazard is the WRITE, not the read.** A null workspace is a guest and the platform default is the right answer for one — but an unresolved uuid on a write would turn a feature off for **every workspace on the platform** from one teacher's screen, so whatever writes there guards with `abort_if` first, exactly as `UnlockRuleController` does over the same sentinel. ⚠️ The reading half is safe only because **every caller passes the workspace explicitly**: `StartAdaptiveSession` and `CreateStudyRoom` take a `$workspaceId` derived from the enrolment, and `ListAdaptiveConcepts`/`ListStudyRooms` filter the student's enrolled workspaces through it. A student is a member of no workspace, so `WorkspaceContext::id()` is null for them always — a flag read from the CONTEXT instead would silently answer the platform row for every student on the platform, and both features are seeded OFF there. `Flags` is bound `scoped()` for the two opposite reasons `AssistantScopeDirectory` is: not `bind()`, because a flag is asked dozens of times in a page, and not `singleton()`, because a worker's container outlives the job and a feature flag is the one thing whose whole purpose is to take effect NOW.
- **A RESOLVED context that does not match is still a DENIAL — and a finance officer who owns a workspace has a resolved context. That is FIVE layers of one defect, and each one hid the next.** `WorkspaceContext::id()` falls back to `users.last_workspace_id` for *every* user including a platform officer, so the moment such an officer also owns a workspace, a platform-wide approval screen starts answering about that one workspace. Spec 024 found all five in three consecutive runs, each fix revealing the next: **route-model binding** resolved `{order}` through the scope and answered **404** about an order that exists (four routes take `{orderUuid}` as a string now and resolve with `withoutWorkspaceScope()` inside the controller — the signed receipt-download route keeps implicit binding, because it has no authenticated user and the scope is therefore inert); **`OrderPolicy`** asked `belongsToCurrentWorkspace()` before the platform branch and answered **403** (the platform branch runs first now, for `view`/`approve`/`reject`, and the workspace check still guards every course order beneath it); the **conditional-UPDATE claims** in `ApproveOrder`/`RejectOrder` plus the owner rule inside `UploadPaymentReceipt` matched **zero rows** ⇒ **422** — the same shape that stopped `ExecuteTeacherOffboarding` completing an exit, reached from a second module; **`NotifyAccessChange`** read `$balance->course` through the scope and got null ⇒ **500 AFTER THE TRANSACTION COMMITS**, which is the worst of the five: the credits are minted, the officer sees an error page, and no notification is ever sent (it reads the course with `withoutWorkspaceScope()` and returns quietly when there is none); and **`OrderResource::getEloquentQuery()`** in Filament simply left the scope on — **no error at all**, just a silently short list that reads as a quiet week. ⚠️ **A one-workspace fixture cannot see any of it, and neither can a fixture whose officer has no workspace** — which is every existing one, and is exactly why this sat unnoticed. Adding a `last_workspace_id` to the finance officer in `StaffCreditGrantTest` — ONE line — exposed all five. Any test of a platform-permission read *or* write needs two workspaces AND an officer who belongs to one of them.
- **A PUBLIC PAGE THAT READS SOMETHING WORKSPACE-OWNED HAS A VICTIM, AND IT IS NOT THE VISITOR.** `/certificates/verify/{code}` resolves the certificate's DESIGN from `certificate_designs`, and the naive read goes through `WorkspaceScope` — which for a guest adds **no condition at all**, so a guest reads it correctly whether the bypass is there or not, and **a guest-only test passes against a build with none**. The person it breaks is a **signed-in teacher from another workspace** following the link: `EnsureCurrentWorkspace` is in the `api` group, their context resolves to their own workspace, the scope bites, and they are shown their own design over somebody else's certificate — or nothing. Family of the five-layer defect spec 024 found in the payments approval chain, where the same `users.last_workspace_id` fallback made a platform-wide read answer about one workspace. The guard is `withoutWorkspaceScope()` **plus** `where('workspace_id', $certificate->workspace_id)` put back by hand, and `DesignScopeBypassTest` needs **two workspaces and a foreign teacher who is logged in**. ⚠️ **It was proved by measurement, not by reading**: swapping the bypass for `CertificateDesign::query()` and re-running that one file made the guest case PASS and only the foreign-teacher case fail — the asymmetry is the whole point, and a file without that second case is a file that proves nothing. ⚠️ **AND THE VICTIM IS A STUDENT TOO, ON A WRITE, THROUGH IMPLICIT ROUTE-MODEL BINDING — measured in a real browser on production 2026-09-14.** «سجّلني في الدَّور» on a full course answered `POST /api/v1/courses/{uuid}/waitlist` ⇒ **404** and «العنصر المطلوب غير موجود أو حُذف» about a course whose name was on the screen. `joinWaitlist` took `Course $course`, so the binding ran through `WorkspaceScope` — and `users.last_workspace_id` is stamped on **every student who was ever added to a workspace** (`addWorkspaceMember`, `AcceptInvitation`, the seeders), so the scope ANDs a workspace that is not the course's. It is spec 032 · T023 reached from the WRITE side: that fix put `withoutWorkspaceScope()->publiclyListed()` inside `ReadPublicCourse` for the page, and the door added two specs later repeated the mistake. The resolution is `publiclyListed()` alone — **the scope drops itself inside that scope** since 2026-09-03, so a second `withoutWorkspaceScope()` beside it is noise — and the predicate has to be the one the SCREEN carrying the button reads, or they are two spellings of one question. ⚠️ **AND IT WAS FIVE LAYERS, NOT ONE — each hid the next, and only the harness that drives the routes found them.** (1) the implicit binding on all fourteen student routes (`/courses/{course}/…`, `/cohorts/{cohort}/…`, `/enrollments/{enrollment}/…`, `POST /courses/{course}/orders`), now a uuid string resolved explicitly — the `/manage/…` routes keep implicit binding, where the scope really is the guard; (2) `EnrollmentPolicy` ran `belongsToCurrentWorkspace()` ABOVE the ownership branch, so the owner of the row was refused their own row while the line that allows them sat unreachable one statement below — and in `completeLessons`/`resetProgress` nothing but the owner can pass the next line anyway, so that check could only ever refuse the person it was guarding, and is deleted; (3) `CoursePolicy::view()` had the same order above its «published ⇒ allow» branch, and a published course is public by definition — the workspace question is about DRAFTS, so `COURSES_VIEW` keeps the check and `published` moves above it; (4) **`Enrollment::course()` and `Order::course()` ran under the scope and returned null**, which is not a thinner page but a 500 — `->title` and `->lessons()` on null took out the curriculum, «تعلّمي», and `NotifyStudentEnrolled`, which kills the enrolment that fired it. The guards themselves were right the whole time: `EnrollmentDirectory` and `CohortDirectory` already declared `withoutWorkspaceScope()` in their own queries — the guard was working and only the door was shut. ⚠️ **Two existing tests asserted 404 on this and both were measuring the incidental refusal**: their actor was a TEACHER, and the real guard («a teacher never enrols/buys») answers 422 and is strictly stronger — it refuses their own workspace's course too, which the scope check waved through. Both now assert 422 AND zero rows written, which is the property either one was reaching for. ⚠️ **AND THE FIFTH ONLY SURFACED WHEN THE LESSON DOORS WERE DRIVEN TOO — AN EAGER LOAD THAT DEFEATS A GUARD DECLARED ONE FILE AWAY.** `Lesson::isVisibleChain()` already carries the per-model bypass, with a comment naming this exact failure — but `EnrollmentController::completeLesson()` ran `$lesson->load(['section','chapter'])` SCOPED one line above it, so both parents came back null and `loadMissing` found them «already loaded» and did not re-fetch them. A PUBLISHED lesson answered `422 not_visible`, so a stamped student could never complete a single lesson at another teacher — `CourseCompleted` never fires and no certificate ever issues, the forever-capped family reached through a preload. **The tell was that the READ door returned 200 on the identical lesson**: it has no such preload. An eager load that overwrites a relation a guard means to fetch with a bypass is worse than no eager load at all — pass the same bypass in the preload, or do not preload that relation.
- **A permission whose only reader sits behind a route no client calls guards NOTHING — and the screen people actually use is the one to check.** `cms.publish` was declared, seeded, withheld from `assistant-teacher` on purpose, and read by exactly one thing in the tree: `ArticlePolicy::publish()`, reached only from `POST /cms/articles/{article}/publish`, which no file under `frontend/src` calls. The surfaces that DO publish asked neither: `ArticleController::store()`/`update()` took `status` straight out of the payload under `cms.create`/`cms.update`, and `CmsArticleResource`'s status select carried no `disabled()`, `visible()` or `dehydrated()` at all while `canEdit()` asked `cms.update`. So an assistant published to the teacher's public blog — firing the IndexNow ping under their name — and took a live post back down, by changing one field. ⚠️ **It is `taxonomy.manage` one step further along**: that one was classified by ABSENCE and read by nobody; this one HAS a reader, a policy method and a passing test, and the door it guards is not a door anyone walks through. The check that finds it is not "is the permission read" but **"which surface performs this act, and what does THAT surface ask"** — and for anything with a Filament resource, the panel is the answer. ⚠️ **And the guard belongs at every door**: `published_at` is the same capability wearing a date (a value in the future de-lists a live article without `status` moving, because `publicListingConstraints()` asks `published_at <= now()`), and the two doors need different treatment — the API's `CreateArticleRequest` does not validate the field at all, so a condition for it there would be a guard nothing can exercise, while the panel really can write it and disables it under the same permission.
- **A FILAMENT CREATE PAGE'S DEFAULT `handleRecordCreation()` IS `new Model($data)` — SO IT STAMPS THE *OFFICER'S* WORKSPACE AND DROPS EVERY NON-FILLABLE COLUMN, SILENTLY.** Spec 034 · FR-017 opened a second door for writing a subscription plan on a named teacher's behalf, and FR-018 forbids inferring that teacher from anything: `BelongsToWorkspace` auto-fills `workspace_id` from the writer's context, which for a platform officer is their own `users.last_workspace_id` fallback — so a form that looks entirely correct writes the plan into the officer's own workspace, where it shows up in *their* students' catalogue and never in the teacher's. `price_minor` is deliberately not `$fillable` (the platform's half of a row two actors write), and mass assignment **discards a non-fillable key in silence** — the `student_profiles` defect of spec 013 reached through a panel instead of a controller. The create page therefore REPLACES that method entirely and calls the Action, exactly as `EditPlan` already replaces `handleRecordUpdate()` for the same column. ⚠️ **And the mirror of it is the read**: `SavePlan::resolveCoverage()` resolves the course with an explicit `where('workspace_id', $teacherWorkspace)` and needed `withoutWorkspaceScope()` added beside it — the scope ANDs the officer's own workspace onto a query about somebody else's course, matches zero rows, and refuses **every teacher's course** with «هذا الكورس غير موجود عندك». No one-workspace fixture can see either half: the officer must own a DIFFERENT workspace than the one being written to, which is the one line that exposed all five layers of the same defect in spec 024.
