# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Educational multi-tenant SaaS (courses → enrollment → exams → certificates → manual payments).
Monorepo: `backend/` (Laravel 13, PHP 8.5, modular monolith), `frontend/` (Next.js 15 App Router), `docker/`, `docs/`.
`AGENTS.md` holds the same command reference; `docs/README.md` has the module/endpoint/permission tables and `docs/erd.md` the schema.

## Commands

All backend commands run from `backend/`:

```bash
php vendor/bin/pest                              # all tests (120)
php vendor/bin/pest tests/Feature/Learning       # one directory
php vendor/bin/pest --filter="lesson"            # one test by name
php vendor/bin/pest --coverage                   # needs pcov/xdebug
./vendor/bin/pint                                # fix PSR-12 style (--test to check only)
./vendor/bin/phpstan analyse                     # Larastan level 8 (phpstan.neon) — see note below
php artisan migrate:fresh --seed                 # reset DB + roles/permissions + demo data
php artisan storage:link                         # once per checkout — serves uploaded receipts at /storage
php artisan serve                                # API on :8000, Filament on /admin, Horizon on /horizon
php artisan scribe:generate                      # regenerate /docs from route annotations
```

Frontend (`frontend/`): `npm run dev` (:3000, rewrites `/api/*` → `localhost:8000`), `npm run build`, `npx tsc --noEmit`.

Local dev uses SQLite; tests use in-memory SQLite with `SCOUT_DRIVER=null` (see `phpunit.xml`). Production is MySQL + Redis + Meilisearch. **SQLite hides column-width bugs** (it stores any integer in an `unsignedInteger` column) — check the migration when writing numeric values that MySQL would reject in strict mode.

`phpstan.neon` runs Larastan at level 8 over `app/` and `database/`, and the tree is clean — keep it that way. It reads every module's `Database/Migrations` directory to type model properties, so a new module must be listed there too.

## Architecture

### Module system

Modules live in `backend/app/Modules/{Name}/` and are **auto-discovered** by `App\Shared\Modules\ModulesServiceProvider` — it scans the directory and registers each `{Name}ServiceProvider` extending `App\Shared\Modules\Module`. Never register a module provider manually in `bootstrap/providers.php`.

The base `Module` class auto-loads, per module:
- `routes/api.php` → auto-prefixed `/api/v1` with the `api` middleware group (root `routes/api.php` is intentionally empty)
- `routes/web.php` → `web` group
- `Database/migrations/`, `Database/factories/`

Model factories currently live centrally in `backend/database/factories/Modules/{Module}/` (namespace `Database\Factories\Modules\{Module}`), not inside the module.

Cross-module coupling goes through **events**, not direct calls into another module's actions. Listeners are wired with `Event::listen()` in the subscribing module's provider `boot()` — there is no `EventServiceProvider`. Key chains:

- `PaymentApproved` → `Payments\Listeners\CreateEnrollmentFromOrder` → `EnrollmentCreated` → `Notifications\Listeners\NotifyStudentEnrolled` → `DispatchNotification`
- `CourseCompleted` / `ExamPassed` → `Certificates\Listeners\IssueCertificateIfEligible` (idempotent) → `CertificateIssued` → notification
- `WorkspaceCreated` → `Tenancy\Listeners\SeedDefaultRoles`

### Multi-tenancy

Single database, partitioned by `workspace_id`. Three moving parts:

1. `BelongsToWorkspace` trait — adds the `WorkspaceScope` global scope and auto-fills `workspace_id` on create. **Every tenant-owned model must use it.**
2. `WorkspaceScope` — filters queries by the current workspace; skipped entirely when the context resolves to `null` (Super Admin operating globally). Bypass deliberately with `withoutWorkspaceScope()` or `WorkspaceContext::withoutScope()`.
3. `WorkspaceContext` — resolves the current workspace from the session key `workspace_id`, falling back to `users.last_workspace_id`. The `EnsureCurrentWorkspace` middleware (in the `api` group and the Filament panel's `authMiddleware`) also pushes that id into spatie's `PermissionRegistrar` team id.

`WorkspaceContext` is an **application-wide singleton that caches its resolution**, so outside an HTTP request never call `set()`: a queued job or console command that does leaks its workspace into whatever the same worker handles next. Use `forWorkspace($workspace, fn () => ...)`, which restores the previous context (and team id) afterwards. In tests, the first call to `id()` freezes the resolution — query tenant models only after `Sanctum::actingAs()` / `setCurrentWorkspace()`.

Validation is a second bypass route: Laravel's `exists` rule is a raw query, so use `App\Shared\Support\WorkspaceRules::exists('table')` instead of `'exists:table,id'` for any tenant-owned table. Scout is a third — `Model::search()` hits the engine outside global scopes and must be given an explicit `->where('workspace_id', ...)`.

spatie/permission runs in **team mode with `team_id = workspace_id`**, so role/permission checks are meaningless until the team id is set — that is why tests must go through `WorkspaceContext::set()` or the `WithWorkspace` helpers. Super Admin is the platform-level `users.is_super_admin` flag, not a tenant role.

### Conventions

- Business logic lives in `Actions/` (`App\Shared\Actions\Action`, one public `handle()`), never in controllers. Controllers: validate via a Form Request → build a DTO → call an Action → return an API Resource. Controllers extend `App\Http\Controllers\Controller` and read the authenticated user via `$this->currentUser($request)`.
- Factories are resolved centrally by `AppServiceProvider::guessFactoryName()` (`App\Modules\X\Models\Y` → `Database\Factories\Modules\X\YFactory`); models don't override `newFactory()`.
- DTOs extend `App\Shared\Data\DataTransferObject` (readonly promoted props, `fromArray()` named constructor).
- Every file is `declare(strict_types=1);`.
- Business rules configured on a model (attempt limits, timers, sequencing) must be enforced in the Action that performs the operation, not only validated on the way in — the Action is the single entry point that seeders, Filament and the API share.
- Models use `HasUuid`: `getRouteKeyName()` is `uuid`, so routes and API payloads expose `uuid`, never the autoincrement id.
- Authorization is policy-based (`{Module}/Policies/`) and permission names come from `Tenancy\Support\Permissions` / role names from `Tenancy\Support\Roles` constants — do not hardcode permission strings.
- Payments go through `Payments\Contracts\PaymentProviderInterface`; `ManualTransferProvider` is the only MVP implementation. Adding a provider must not require changing order/enrollment logic.
- **Notifications go through `Notifications\Actions\DispatchNotification` and nothing else.** Business logic names a recipient and a `NotificationType` — never a channel. Channels implement `NotificationChannelInterface` and are registered with one `->tag('notification.channels')` line; `InAppChannel` is the only implemented one (WhatsApp/email/Telegram/SMS/push are known values marked unimplemented). `ProviderAgnosticTest` fails the build if any `Actions/` file names a channel or provider.
- API auth is Sanctum bearer tokens; the Filament `/admin` panel is session-based and gated by `EnsureFilamentAccess`.

### Tests

Pest, `RefreshDatabase` for all suites, plus the `Tests\Support\WithWorkspace` trait auto-applied to `Feature` (`createWorkspaceWithOwner()`, `addWorkspaceMember()`). Feature tests are the primary safety net — the critical paths listed in `AGENTS.md` (workspace isolation, permissions, enrollment/lesson gating, exam grading, certificate issuance + verification, payment approval → enrollment) must stay green.

## Gotchas

- **Platform-owned entities have no scope at all — the Action is the guard.** Since spec 003 the constitution classifies every model into one of three layers, and `notifications`, `notification_preferences`, `parent_student_relations`, `message_templates` and `contact_verifications` are **not** workspace-scoped by design (a student has one feed and one set of preferences across every teacher they study with). That means no global scope touches them, so they are as exposed as an unauthenticated marketplace query. The guard is written explicitly: ownership of the row, plus — for a teacher reading a student's guardians — an **active enrollment in that teacher's own workspace** (`ParentStudentRelationPolicy`). `tests/Feature/Notifications/PlatformOwnershipTest.php` tests both failure directions, including the mirror-image bug of adding `BelongsToWorkspace` where it does not belong, which silently duplicates one person per teacher.
- **`Notifiable` stays on `User`, and that is deliberate.** Email is an unimplemented *notification channel*, but Laravel's password-reset and email-verification mails still go through `notify()`. They are authentication primitives, not domain notifications — a reset link delivered in-app is unreachable by definition, since the person asking for it cannot sign in to read it. `User::notifications()` is overridden to point at our own model; Laravel's `notifications` table was replaced.
- **A notification with no template is silently dropped.** `TemplateRenderer` refuses to render a missing or unapproved template (FR-037) and `DispatchNotification` logs it rather than failing the enrollment/payment that triggered it. `NotificationTemplateSeeder` is therefore reference data, not fixtures — `tests/Pest.php` seeds it before every Feature test, or every notification assertion would pass vacuously against zero.
- **`WorkspaceScope` is inert for guests.** `WorkspaceScope::apply()` returns early adding no condition when `WorkspaceContext::id()` is `null`, which it always is without an authenticated user. So an unauthenticated request has **no tenant isolation at all** — a public query without a guard returns every workspace's rows, including drafts. The replacement guard is the `IsPubliclyListed` trait's `publiclyListed()` scope (workspace participation + the model's own `publicListingConstraints()`). Every Action reached from a public route must start from it, and `PublicExposureTest` walks each public payload against `PublicFieldAllowlist` to catch what slips through. Never bind a public route to a model implicitly: `Route::get('/teachers/{teacher}')` resolves by uuid without the guard.
- **The trust score is derived, and so is `is_publicly_listed`.** Approval and workspace participation are two separate decisions; `is_publicly_listed` is computed from both and never assigned directly. A trust score below the data threshold is `null` with band `building`, never `0` — filters must exclude those teachers rather than compare against a number they do not have.
- **Never call `WorkspaceContext::set()` from a job or console command.** It is an application-wide singleton that caches its resolution, so the workspace leaks into whatever the same worker handles next. Use `forWorkspace($workspace, fn () => ...)`. `tests/Feature/Marketplace/TrustScoreJobIsolationTest.php` fails the build if a `set()` appears under `Modules/Marketplace/Jobs/`.
- **The watermark is the renewal loop, not something watched for.** A playback grant is short-lived; the overlay component is what calls `/playback/{grant}/renew`. Remove it from the DOM and renewal stops, the grant expires, and the next byte-range request is refused — the decision sits on the server, where it cannot be edited away. This is also why the local provider serves with `Accept-Ranges: bytes`: without range requests, expiry could not cut a file already in flight.
- **The device limit counts devices, not sessions.** Signing in twice on one laptop is two sessions on one machine; counting sessions at a limit of one would log a student out of the computer they are sitting at, punishing the account holder and leaving the person they shared the password with untouched. Enforcement is deleting the Sanctum token — the one number a client cannot forge. The fingerprint only merges; it is forgeable and pretending otherwise would be a lie. The browser half of the fingerprint is `X-Device-Id`, a random id `lib/api.ts` keeps in `localStorage`; without it two people on the same phone model look like one machine.
- **The transcript is derived, and the caption file expires with the grant.** `media_captions` stores a WebVTT path and nothing else — no transcript column, because a stored second copy of the same words drifts from the subtitles at the first typo fix. `WebVtt::parse()` derives it server-side (validation) and `TranscriptPanel.tsx` derives it again in the browser from the file the `<track>` already fetched. That file is served by `/playback/{grant}/captions/{caption}`, not from a public path: a `<track>` sends no `Authorization` header either, and a permanent caption URL would be the lesson's entire script, permanently linkable. When an asset has captions the watermark rotates through the **top** corners only — the browser's caption band is exactly the `bottom-14` row, and a viewer who needs captions cannot work around a covered word.
- **A correct password on a two-factor account issues no token at all.** `/auth/login` answers `{two_factor: true, challenge}` and the challenge lives ten minutes in the cache, not a table — nothing reads one of those rows a minute later. Minting a Sanctum token and then restricting it would mean any flaw in the restriction is a full sign-in with the password alone, which is the thing the second factor exists to prevent. The exchange goes through `StartAuthSession` like any other sign-in, so the device limit and its alert still apply. The secret lives on `user_security_settings` and `User` implements Filament's `HasAppAuthentication` **by hand** (its traits assume columns on `users`), so one enrolment serves both `/admin` and the API — two implementations would mean two QR codes for one person.
- **`2fa.required` is applied route by route, never to a group.** The five sensitive routes each carry it in their own definition, where it is visible when the route is read; a blanket rule is either too wide or grows an exception list nobody prunes. Before `two_factor_required_at` it passes and the frontend nags; after it, 403 with `code: two_factor_required`. Recovery codes are stored hashed, so the confirm response is the only place they exist in readable form — a "show them again" endpoint cannot be built without weakening the storage.
- **The notification bell is the session heartbeat.** Enforcement is instant server-side, but a client only finds out when it next speaks: the bell's 60s poll is what makes a passively-reading page discover it, and the 401 handler in `frontend/src/lib/api.ts` is what turns that into `/login?ended=…`. Drop the interval "because a badge does not need polling" and an evicted account keeps showing its owner a screen they are no longer entitled to. The `session_uuid` saved at sign-in is what lets a tokenless client still ask *why*.
- **`users` carries what every account has; anything true of one role gets its own table.** `student_profiles` and `user_security_settings` exist for that reason. `guardian_profiles` and `admin_profiles` deliberately do not — no field is theirs yet, and an empty table is not a design. Adding a role-specific column to `users` will be rejected in review.
- **Attendance never passes through the broadcast provider.** The register is built from a heartbeat hitting our own route and the server does the arithmetic: `stay_seconds += min(now − last_ping_at, 2 × interval)`. Three properties fall out of that one line — two devices do not double the time, leaving and returning aggregates into one stay, and an hour of silence is capped rather than credited. It is also why all of attendance was provable before any broadcast contract existed. A provider that reports its own attendance is a provider you cannot leave.
- **Seats are claimed by an atomic conditional UPDATE**, never `count()` then `insert()` — that is the definition of the race — and never `lockForUpdate()`, which is a no-op on SQLite, so a test written around it passes locally and proves nothing about the MySQL it will run on. `SeatConcurrencyTest` walks the same path real concurrency does.
- **`SessionCompleted` is not `SessionDelivered`.** Completion is "the session ended"; delivery is "the teacher joined, stayed long enough, and it ended normally". Two events rather than one with a flag, because a flag makes the condition optional for the listener — and only delivery carries the frozen seat count spec 006 bills against. `billable_seats` is likewise written **once**, at the cancellation deadline, and never recomputed: it answers a question about a moment that has passed, and a consumer that derives it from live bookings will get a different answer every day.
- **The model is `ClassSession`, never `Session`.** `AuthSession` (spec 004) already owns that word, and two things called Session in one product is a line every reader misreads once. The frontend follows: `lib/class-sessions.ts` beside `lib/sessions.ts`.
- **A `->delay()` runs immediately on the `sync` queue connection.** A delay is a queue-driver feature and `sync` has no queue, so any test that exercises a session timeline must `Queue::fake()` — otherwise `CloseClassSessionJob` fires inside `OpenBroadcastRoom` and closes the session before the teacher joins, collapsing the timeline into a green test that proves the opposite of what it claims.
- **A freeze period is read, never written to.** Scheduling, booking, `MarkAbsenteesJob` and `SyncTeacherCountersJob` consult it; no counter ever moves. That is why FR-043's "counters resume with their previous values" holds without a line of resumption code — there is nothing to undo. Sessions already booked inside one are suspended, not deleted.
- **A Resource runs once per row, so a query inside one is an N+1 by construction.** `ClassSessionResource` asked every published session where its recording went — one `lessons` SELECT per row, on both the teacher's calendar and every student's timetable. The fix is the `recordingLesson` relation plus eager loading at each call site; the fallback query stays as the last branch, because a caller who forgets would otherwise publish a recording with no way in, silently. `QueryBudgetTest` fails if the eager load is dropped.
- **`whereDate()` costs the index the column was given.** MySQL cannot use `(workspace_id, starts_on, ends_on)` once a function wraps the column, and `FreezePeriod::covering()` is consulted on every booking, every schedule and every absentee sweep. Compare against a date string instead. When the column is a *timestamp* and the bound is a date, the upper bound is the START of the next day — `<= ends_on` silently drops everything after midnight on the last day.
- **`SESSIONS_VIEW` and `ATTENDANCE_VIEW` are two different questions.** The first says "you may see the sessions you can book" and every student holds it; the second says "you may read who attended one". Authorising the register with the first hands each student the class roll — names, stay durations, and the reason a teacher changed someone's mark. A reader without `ATTENDANCE_VIEW` gets their own row, which is ownership rather than permission and therefore not a 403.
- **An Action that acts on a named student must prove the student is theirs.** `exists:users,uuid` answers a different question: NFR-001أ forbids a teacher learning anything about someone with no active enrolment in their own workspace, so a bare uuid parameter is an identity probe — pass any user's and the response comes back carrying their name. `CreateFreezePeriod` asks `EnrollmentDirectory` before it writes.
- **`SessionCancelled` carries the seat holders, because by the time a listener runs nobody holds a seat.** Releasing them is part of cancelling, so a listener that reads the bookings afterwards sees one undifferentiated pile and tells the student who cancelled last month that their session is off. The Action reads the ids while they are still true.
- **`teacher_profiles.attendance_rate` is the TEACHER's attendance**, not their students'. It is the share of countable sessions actually delivered; a student's absence never touches it. The name reads the other way, which is why the meaning is written in `SyncTeacherCountersJob`, in `docs/README.md`, and in a test that fails if anyone changes it.
- **Operational numbers live in `platform_settings`, not `config/`.** The device limit, upload limits and grant TTL are rows an operator edits from the panel; `config/media.php` is the fallback for a database with nothing seeded. A limit that can only change by shipping code is a limit nobody ever tunes.
- Module directory names are matched literally by `Module::registerMigrations()`/`registerFactories()`. Migrations must live in `Database/Migrations` (capital M) — a casing mismatch resolves fine on Windows/macOS and silently loads **zero** migrations on Linux.
- Adding a tenant-scoped model without `BelongsToWorkspace` leaks data across workspaces and no test will catch it unless you add one to `tests/Feature/Tenancy/WorkspaceIsolationTest.php`.
- Frontend stores the Sanctum token in `localStorage` and sends `Authorization: Bearer` (`frontend/src/lib/api.ts`); it relies on the Next.js rewrite, so the backend must be running on :8000.
- Don't run `npm run build` while `npm run dev` is up — both write `.next/`, and the dev server then dies with `Cannot find module './NNN.js'`. Stop dev first (or accept that you must `rm -rf .next` and restart it).
- **The frontend is Arabic-only and RTL-only** (spec 002). One root layout, `frontend/src/app/layout.tsx`, declares `lang="ar" dir="rtl"`, loads Cairo, and runs the pre-paint theme script; `(public)` and `(app)` are nested layouts that add chrome only. Adding a second `<html>` anywhere re-splits the product.
- **Colours come from `@theme` in `globals.css`, never from a class.** No `bg-gray-*`, no `bg-white`, no hex in a component. `text-white` is allowed *only* as the foreground of `bg-primary`/`bg-secondary`/`bg-danger`; `accent` and `trust-medium` have their own `-foreground` tokens because white fails 4.5:1 on them. Layout uses logical properties (`ms-*`, `start-*`, `text-start`) — never `ml-*`/`left-*`. Direction lives in icon *names* (`ChevronStartIcon`), not in a CSS flip.
- **Shared UI lives in `frontend/src/components/ui/`** (`Button`, `Card`, `Badge`, `Alert`, `Table`, the `Field` family, `states/`). Components there take no free-form `className` — appearance is a closed set of variants. `components/marketplace/` is now marketplace-specific only. Arabic status labels and money/date formatting go through `src/lib/labels.ts`.
- **Never show a raw error to the user.** 422 goes through `fieldErrors()` and lands under its field; everything else goes through `userMessage()` in `src/lib/errors.ts`. Validation text itself is Arabic from `backend/lang/ar/`, and every new `FormRequest` field needs an entry in that file's `attributes` array or it renders as `phone_number`.
- **Rate limiters are named** (`throttle:auth` · `throttle:registration` · `throttle:public`, defined in `AppServiceProvider::registerRateLimiters()`). Inline `throttle:5,1` is banned: `ThrottleRequests` keys guests on `domain|ip` with no route in the hash, so every inline limit shares one counter and the strictest one wins — browsing the marketplace used to lock a visitor out of logging in.
- **`npx playwright test` needs an API that can answer concurrently, or the *build* fails before a single test runs.** The committed config builds for production, and Next prerenders `signup/teacher` and `signup/parent/children` by fetching the API — in parallel workers. `php artisan serve` is PHP's built-in server with **one thread**, so it answers the first and refuses the rest: `TypeError: fetch failed … ECONNREFUSED`, then `Export encountered an error`. Start the API as `PHP_CLI_SERVER_WORKERS=8 php artisan serve`. Worth the trouble: the production run is 4 minutes and green, the same suite against `next dev` takes 31 and fails on `page.goto` timeouts that mean nothing.
- **A 500 on one page with a `Jest worker … exceeding retry limit` message is a corrupted `.next/`, not a bug in that page.** Delete the directory and restart. The two axe violations it produces (`document-title`, `html-has-lang`) are Next's error page being audited instead of yours, which reads as an accessibility regression on a page nobody touched.
- **Settlement and billing are two contexts with no key between them, and that absence is load-bearing.** The teacher's pay and the student's payment share no foreign key and no query; the only bridge is the `SessionDelivered` event from 005. `ContextIsolationTest` fails the build over a violation in either direction — including a billing event consumed under `Modules/Settlement/`, and including a field added to a teacher-facing Resource that is not in `TeacherFieldAllowlist`. The table lists are derived from each side's `Schema::create` calls, so 006's credit tables are covered the day they land.
- **Counts come from `teaching_units`; money comes from `ledger_entries`.** `LedgerEntryType` carries `Deduction` and `Bonus`, which have **no teaching unit behind them** — a total derived from units omits the first manual adjustment anyone writes, and the statement stops matching the close the same day. The ledger is the balance; the statement reads it. The ledger is also append-only, enforced on the model (`LedgerEntry::booted()` throws on `updating`/`deleting`) rather than only in the Action. A bulk `update()` retrieves no models and so bypasses that guard, which is why period stamping is the one sanctioned post-insert write and stays the only one.
- **Settlement money is an integer in minor units**, departing from Payments' `decimal(12,2)` on purpose: Laravel's `decimal:2` cast returns a **string**, so every sum goes through a float. Tolerable for an order total, not on the table that decides a salary. `formatMinorMoney()` on the frontend is the only place it becomes text — the API never sends pre-formatted money, because a formatted string is a number the client has to parse back before it can add anything up.
- **A close claims units with `< ends_on + 1 day`, never `<= ends_on`.** `ends_on` is a DATE and `delivered_at` a timestamp, so the second form binds midnight and silently drops every unit taught on the closing day — the same boundary that cost `FreezePeriod::covering()` a fix in 005. Standalone ledger lines (a deduction, a bonus) carry **no** date filter at all: an adjustment is typed *after* the window ended, so a date filter there would push every deduction into the next period and pay in full a window meant to be reduced.
- **The settlement audit filters by asking for six subject types, not by removing rows.** `activity_log` is one shared table that billing writes to as well; a reader that fetched it and then dropped the billing rows would be one forgotten branch away from showing an auditor of teacher pay what a student paid. `SettlementAuditSubjects` is the whole filter, and it is platform-wide by design — the table has no `workspace_id` column and `settlement.audit.view` reaches super-admin alone.
- **Reordering the tree is a write to ACCESS RIGHTS, not to a display order.** `Enrollment::accessTo()` derives what a student may open from the triplet of section, chapter and lesson positions, so moving an item changes who can reach what, immediately. Every reorder therefore sends the COMPLETE sibling list plus `structure_version`, and `StructureVersion::claim()` — one conditional `UPDATE … WHERE structure_version = ?`, the seat idiom — is both the check and the bump. Comparing a loaded model and incrementing later is the lost update it exists to prevent: two teachers both pass, both write, neither sees a 409. Never `lockForUpdate()`, a no-op on SQLite.
- **The progress denominator excludes a recording through BOTH its doors.** A recording is entitled by a SEAT, not by enrolment, so `countableForProgress()` drops it *and* `accessTo()` refuses to let it stand as a prerequisite. One without the other still bricks the course: left in the denominator, a seatless student can never reach 100%; left in the chain, it locks everything after it. This is the family of the spec's worst defect — an item that enters the denominator and can never be completed caps every enrolled student below 100%, so `CourseCompleted` never fires and no certificate ever issues, permanently. Six roads led there and all six are named in `docs/README.md`; the two that outlive publishing are **archiving** and **deleting** the last item a student had left, which is why anything moving the countable set fires `CourseStructureChanged` → `ResyncCourseProgress`. `progress_pct` is otherwise written when a lesson is completed and at no other moment.
- **A publish is previewed by the code that performs it, never by an estimate beside it.** `PreviewPublishImpact` borrows `PublishTreeNodes::resolve()`, its `assertReady()`, `Lesson::progressEligible()`, `CourseProgress::percentage()` and `ExamGateSatisfaction`; the ONE thing it simulates is the three status conditions, because that is what a publish changes. A second denominator computed "just for the preview" is how the teacher gets shown a number no student ever had (`SC-018`). The preview also returns the item list it costed, and the client publishes THAT list — deriving the draft set on both sides is the same drift wearing a different face.
- **Renumbering comes before the index, and `chunkById` before `chunk`.** 016 added `unique(chapter_id, order)` to rows that already held duplicates, so the densify migration must run before the index migration or the deploy fails on live data. And the uuid backfill walks with `chunkById`: `chunk` paginates by OFFSET while the predicate (`uuid IS NULL`) shrinks under it, so every page after the first skips as many rows as the previous page fixed — and reports success. The parking offset in a reorder is `max(order) + 1` for the same reason a constant fails: `max(order)` tracks a group's LIFETIME create count, not its row count.
- **Authored text is Markdown, rendered per response, never stored as HTML.** `MarkdownRenderer` strips raw HTML rather than escaping it, so the allowlist is the Markdown feature set itself — there is no sanitiser configuration to get wrong. A stored `content_html` would be a second copy of the same words that drifts from the source at the first typo fix, and a stored-HTML column is an XSS sink with a teacher's keyboard attached to it.
- **A credit is one session at ONE teacher's rate, and the account it hangs off is platform-wide.** `student_credit_accounts`, `credit_packages` and `terms_consents` carry **no** `workspace_id` by design — one person, one account, one catalogue, one signature. The BALANCE underneath is workspace-scoped, because a credit is not portable between teachers. Adding `BelongsToWorkspace` to the account would silently duplicate one person per teacher, which is the mirror-image bug `PlatformOwnershipTest` exists to catch in both directions.
- **The floor guards BOOKING, never the recording of a debt.** `CreditMovement::$enforceFloor` defaults to **false**: a session that was delivered is owed whether or not the student can pay for it — spec 014 has already earned the teacher their fee from the same `SessionDelivered` event, so refusing the entry would leave the platform owing money with no claim against anyone. A test that expects `InsufficientCreditsException` must pass `enforceFloor: true` or it is asserting the wrong requirement.
- **`is_withheld` is derived from FIVE inputs and stored as none of them**: the balance, the ceiling, the billing mode, an open exam window, and a CURRENT terms consent. So a lift is instantaneous and no `access_holds` table can drift from it — and a published new version of the terms stops deferral for everyone who has not signed it, on their next booking, with nothing to sweep. Never add a column for it; `WithholdingReader::stamp()` is the bulk form, and a per-row read inside a Resource is an N+1 by construction.
- **The credit-limit demotion IS the switch to prepaid for that student.** The floor is `−credit_limit_credits`, so a ceiling of zero and a prepaid mode produce the identical predicate; a per-student `mode` column would be a second answer to a question the floor already answers. And the limit moves by **deltas** with the earning counter CONSUMED — a `limit = f(consent, history)` recomputed from scratch hands the defaulted student their ceiling back on their first payment afterwards. The initial `0 → 1` is an EVENT (first consent, and the birth of any later balance), never a state anything derives.
- **`isBlocked` asks the balance as well as the floor.** `$floor < 0` was the whole test for "owes money" and the demotion breaks it: the ceiling goes to zero while the balance stays negative, so in a `remind` workspace the defaulted student books at −3, −4, for ever — exactly the person the demotion was aimed at.
- **Withholding is per COURSE, never per person, and balances are never summed.** +10 in maths and −6 in physics reads as +4 and unblocked when added up, while the design withholds per course precisely so the paid-up course stays open. The API sends no total because there is no correct one.
- **No money reaches the student's or the teacher's screen.** A credit's price is the teacher's approved settlement rate plus two platform constants, so a total shown to either side is solvable for the other's rate across two package sizes. `StudentBalanceAllowlist` and `PublicFieldAllowlist` fail the build over a field that leaks it, and `formatMinorMoney()` on the frontend is the only place a number becomes currency.
- **Approving a credit purchase and moving a ceiling are PLATFORM permissions**, held by no tenant role. A package a teacher could define is a sale price a teacher sets (FR-021ب); a ceiling a teacher could raise is a teacher deciding how much the platform may be owed. `billing.credits.adjust` currently has no HTTP surface at all — the Action exists and enforces its own rules, and a screen for it has not been built.
- **Reconciliation is a JOB, and the obvious check inside it is blind.** Three `GROUP BY`s over the fastest-growing tables with no tenant filter would run on every refresh of a page. And the ledger-vs-balance comparison proves almost nothing on its own: both sides are written by the same path in the same transaction, so a session that was never charged leaves them in perfect agreement. The two invariants that see it come from outside — one consumption entry per seat of a charged session, and a positive balance equalling what its lots hold.
- **An expiry claims its lot first and then posts with `drawsFromLots: false`.** Posting it as an ordinary negative movement lets the drawer take the same credits a second time out of lots that have not expired. Expiry is switched OFF at launch (`validity_days` defaults to null) but the soonest-expiring-first draw order is live from day one — turning expiry on later must not rewrite which lot paid for which past session.
- **The dormancy notice needs its own column.** The notice moves no credits, so a predicate on `last_transaction_at` alone re-sends it every night to the student least likely to want it; `notified_dormant_at` is stamped BEFORE the dispatch (a lost reminder beats one a night for ever) and cleared by the ledger on the next movement. It is a reminder, never an expiry: nothing is forfeited and nothing moves to another teacher, which would be a re-pricing.
- **`insertOrIgnore` writes a row without booting the model, so `HasUuid` never fires** — and on MySQL the resulting NOT NULL violation is downgraded to a warning and `''` is stored, after which *every* later entry on the platform collides with that row on `unique(uuid)`, is read as "already recorded", and is silently skipped. The ledger stops after one row while every caller reports success. **This is a rule about the insert ARRAY, not a ban on the call.** `CreditLedger::writeEntry()` uses `insertOrIgnore` deliberately and correctly: the unique index is the idempotency guard, and `uuid` and `created_at` are passed EXPLICITLY because the model layer is not there to supply them. `create()` in a try/catch was rejected in R7 — it makes a real failure (a null, a foreign key, an out-of-range value) indistinguishable from a duplicate. What `insertOrIgnore` needs instead is the read-back: zero rows means *either* a duplicate or a swallowed failure, so the entry is fetched by its key and a miss **throws** rather than returning null.
- **The floor comparison is CAST to signed, and MySQL alone will tell you why.** `remaining + limit >= n` evaluated at `remaining = −3` on `unsignedInteger` columns raises **ERROR 1690, BIGINT UNSIGNED value is out of range** — and SQLite has no unsigned arithmetic to overflow, so no local test can ever reproduce it. The guard is `CAST(... AS SIGNED)` in `CreditLedger::applyToBalance()` and the signed column widths in the migration; both carry the reason beside them, because the failing environment is the one nobody runs the suite in.
- **The entry is written BEFORE the lots are drawn and before the balance moves.** Decrementing first means a redelivered event debits twice while the duplicate entry is ignored once — and the balance stops equalling the sum of its entries, permanently, with nothing to notice it. `ReconcileCreditBalancesJob` is what would notice, the next night, by which time the cause is a week of traffic away.
- **`Queue::fake()` with no arguments makes half the billing suite assert zero rows.** The charge listener is queued, so a bare fake swallows it and "four attendance states ⇒ four consumption entries" becomes a confident assertion about an empty table. Fake the timeline jobs only — `Queue::fake([CloseClassSessionJob::class, SendSessionReportsJob::class])` — and let the charge run on `sync`. Calling the Action directly instead tests the arithmetic and proves nothing about the wiring.
- Playwright projects carry an authenticated `storageState` produced by `e2e/auth.setup.ts` so the panel can be audited. A spec that tests an anonymous visitor must opt out with `test.use({ storageState: { cookies: [], origins: [] } })`, or it silently tests a signed-in one.
