# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Educational multi-tenant SaaS (courses → enrollment → exams → certificates → manual payments).
Monorepo: `backend/` (Laravel 13, PHP 8.5, modular monolith), `frontend/` (Next.js 15 App Router), `docker/`, `docs/`.
`AGENTS.md` holds the same command reference; `docs/README.md` has the module/endpoint/permission tables and `docs/erd.md` the schema.

## Commands

All backend commands run from `backend/`:

```bash
php vendor/bin/pest                              # all tests (120)
php vendor/bin/pest tests/Feature/Learning       # one directory
php vendor/bin/pest --filter="lesson"            # one test by name
php vendor/bin/pest --coverage                   # needs pcov/xdebug
./vendor/bin/pint                                # fix PSR-12 style (--test to check only)
./vendor/bin/phpstan analyse                     # Larastan level 8 (phpstan.neon) — see note below
php artisan migrate:fresh --seed                 # reset DB + roles/permissions + demo data
php artisan storage:link                         # once per checkout — serves uploaded receipts at /storage
php artisan serve                                # API on :8000, Filament on /admin, Horizon on /horizon
php artisan scribe:generate                      # regenerate /docs from route annotations
```

Frontend (`frontend/`): `npm run dev` (:3000, rewrites `/api/*` → `localhost:8000`), `npm run build`, `npx tsc --noEmit`, `npm test` (vitest + jsdom, ~2s, no build and no servers), `npm run test:e2e` (Playwright — builds for production, needs both servers).

Local dev uses SQLite; tests use in-memory SQLite with `SCOUT_DRIVER=null` (see `phpunit.xml`). Production is MySQL + Redis + Meilisearch. **SQLite hides column-width bugs** (it stores any integer in an `unsignedInteger` column) — check the migration when writing numeric values that MySQL would reject in strict mode.

`phpstan.neon` runs Larastan at level 8 over `app/` and `database/`, and the tree is clean — keep it that way. It reads every module's `Database/Migrations` directory to type model properties, so a new module must be listed there too.

## Architecture

### Module system

Modules live in `backend/app/Modules/{Name}/` and are **auto-discovered** by `App\Shared\Modules\ModulesServiceProvider` — it scans the directory and registers each `{Name}ServiceProvider` extending `App\Shared\Modules\Module`. Never register a module provider manually in `bootstrap/providers.php`.

The base `Module` class auto-loads, per module:
- `routes/api.php` → auto-prefixed `/api/v1` with the `api` middleware group (root `routes/api.php` is intentionally empty)
- `routes/web.php` → `web` group
- `Database/migrations/`, `Database/factories/`

Model factories currently live centrally in `backend/database/factories/Modules/{Module}/` (namespace `Database\Factories\Modules\{Module}`), not inside the module.

Cross-module coupling goes through **events**, not direct calls into another module's actions. Listeners are wired with `Event::listen()` in the subscribing module's provider `boot()` — there is no `EventServiceProvider`. Key chains:

- `PaymentApproved` → `Payments\Listeners\CreateEnrollmentFromOrder` → `EnrollmentCreated` → `Notifications\Listeners\NotifyStudentEnrolled` → `DispatchNotification`
- `CourseCompleted` / `ExamPassed` → `Certificates\Listeners\IssueCertificateIfEligible` (idempotent) → `CertificateIssued` → notification
- `WorkspaceCreated` → `Tenancy\Listeners\SeedDefaultRoles`

### Multi-tenancy

Single database, partitioned by `workspace_id`. Three moving parts:

1. `BelongsToWorkspace` trait — adds the `WorkspaceScope` global scope and auto-fills `workspace_id` on create. **Every tenant-owned model must use it.**
2. `WorkspaceScope` — filters queries by the current workspace; skipped entirely when the context resolves to `null` (Super Admin operating globally). Bypass deliberately with `withoutWorkspaceScope()` or `WorkspaceContext::withoutScope()`.
3. `WorkspaceContext` — resolves the current workspace from the session key `workspace_id`, falling back to `users.last_workspace_id`. The `EnsureCurrentWorkspace` middleware (in the `api` group and the Filament panel's `authMiddleware`) also pushes that id into spatie's `PermissionRegistrar` team id.

`WorkspaceContext` is an **application-wide singleton that caches its resolution**, so outside an HTTP request never call `set()`: a queued job or console command that does leaks its workspace into whatever the same worker handles next. Use `forWorkspace($workspace, fn () => ...)`, which restores the previous context (and team id) afterwards. In tests, the first call to `id()` freezes the resolution — query tenant models only after `Sanctum::actingAs()` / `setCurrentWorkspace()`.

Validation is a second bypass route: Laravel's `exists` rule is a raw query, so use `App\Shared\Support\WorkspaceRules::exists('table')` instead of `'exists:table,id'` for any tenant-owned table. Scout is a third — `Model::search()` hits the engine outside global scopes and must be given an explicit `->where('workspace_id', ...)`.

spatie/permission runs in **team mode with `team_id = workspace_id`**, so role/permission checks are meaningless until the team id is set — that is why tests must go through `WorkspaceContext::set()` or the `WithWorkspace` helpers. Super Admin is the platform-level `users.is_super_admin` flag, not a tenant role.

### Conventions

- Business logic lives in `Actions/` (`App\Shared\Actions\Action`, one public `handle()`), never in controllers. Controllers: validate via a Form Request → build a DTO → call an Action → return an API Resource. Controllers extend `App\Http\Controllers\Controller` and read the authenticated user via `$this->currentUser($request)`.
- Factories are resolved centrally by `AppServiceProvider::guessFactoryName()` (`App\Modules\X\Models\Y` → `Database\Factories\Modules\X\YFactory`); models don't override `newFactory()`.
- DTOs extend `App\Shared\Data\DataTransferObject` (readonly promoted props, `fromArray()` named constructor).
- Every file is `declare(strict_types=1);`.
- Business rules configured on a model (attempt limits, timers, sequencing) must be enforced in the Action that performs the operation, not only validated on the way in — the Action is the single entry point that seeders, Filament and the API share.
- Models use `HasUuid`: `getRouteKeyName()` is `uuid`, so routes and API payloads expose `uuid`, never the autoincrement id.
- Authorization is policy-based (`{Module}/Policies/`) and permission names come from `Tenancy\Support\Permissions` / role names from `Tenancy\Support\Roles` constants — do not hardcode permission strings.
- Payments go through `Payments\Contracts\PaymentProviderInterface`; `ManualTransferProvider` is the only MVP implementation. Adding a provider must not require changing order/enrollment logic.
- **Notifications go through `Notifications\Actions\DispatchNotification` and nothing else.** Business logic names a recipient and a `NotificationType` — never a channel. Channels implement `NotificationChannelInterface` and are registered with one `->tag('notification.channels')` line; `InAppChannel` and `WhatsAppChannel` are implemented (email/Telegram/SMS/push are known values marked unimplemented). `ProviderAgnosticTest` fails the build if any `Actions/` file names a channel or provider — which is why `default_country_code` sits at the top of `config/notifications.php` and not under its `whatsapp` block: the Action that normalises a phone number may not name a channel to read its own setting.
- API auth is Sanctum bearer tokens; the Filament `/admin` panel is session-based and gated by `EnsureFilamentAccess`.

### Tests

Pest, `RefreshDatabase` for all suites, plus the `Tests\Support\WithWorkspace` trait auto-applied to `Feature` (`createWorkspaceWithOwner()`, `addWorkspaceMember()`). Feature tests are the primary safety net — the critical paths listed in `AGENTS.md` (workspace isolation, permissions, enrollment/lesson gating, exam grading, certificate issuance + verification, payment approval → enrollment) must stay green.

## Gotchas

- **Platform-owned entities have no scope at all — the Action is the guard.** Since spec 003 the constitution classifies every model into one of three layers, and `notifications`, `notification_preferences`, `parent_student_relations`, `message_templates` and `contact_verifications` are **not** workspace-scoped by design (a student has one feed and one set of preferences across every teacher they study with). That means no global scope touches them, so they are as exposed as an unauthenticated marketplace query. The guard is written explicitly: ownership of the row, plus — for a teacher reading a student's guardians — an **active enrollment in that teacher's own workspace** (`ParentStudentRelationPolicy`). `tests/Feature/Notifications/PlatformOwnershipTest.php` tests both failure directions, including the mirror-image bug of adding `BelongsToWorkspace` where it does not belong, which silently duplicates one person per teacher.
- **`Notifiable` stays on `User`, and that is deliberate.** Email is an unimplemented *notification channel*, but Laravel's password-reset and email-verification mails still go through `notify()`. They are authentication primitives, not domain notifications — a reset link delivered in-app is unreachable by definition, since the person asking for it cannot sign in to read it. `User::notifications()` is overridden to point at our own model; Laravel's `notifications` table was replaced.
- **A notification with no template is silently dropped.** `TemplateRenderer` refuses to render a missing or unapproved template (FR-037) and `DispatchNotification` logs it rather than failing the enrollment/payment that triggered it. `NotificationTemplateSeeder` is therefore reference data, not fixtures — `tests/Pest.php` seeds it before every Feature test, or every notification assertion would pass vacuously against zero.
- **`WorkspaceScope` is inert for guests.** `WorkspaceScope::apply()` returns early adding no condition when `WorkspaceContext::id()` is `null`, which it always is without an authenticated user. So an unauthenticated request has **no tenant isolation at all** — a public query without a guard returns every workspace's rows, including drafts. The replacement guard is the `IsPubliclyListed` trait's `publiclyListed()` scope (workspace participation + the model's own `publicListingConstraints()`). Every Action reached from a public route must start from it, and `PublicExposureTest` walks each public payload against `PublicFieldAllowlist` to catch what slips through. Never bind a public route to a model implicitly: `Route::get('/teachers/{teacher}')` resolves by uuid without the guard.
- **The trust score is derived, and so is `is_publicly_listed`.** Approval and workspace participation are two separate decisions; `is_publicly_listed` is computed from both and never assigned directly. A trust score below the data threshold is `null` with band `building`, never `0` — filters must exclude those teachers rather than compare against a number they do not have.
- **Never call `WorkspaceContext::set()` from a job or console command.** It is an application-wide singleton that caches its resolution, so the workspace leaks into whatever the same worker handles next. Use `forWorkspace($workspace, fn () => ...)`. `tests/Feature/Marketplace/TrustScoreJobIsolationTest.php` fails the build if a `set()` appears under `Modules/Marketplace/Jobs/`.
- **The watermark is the renewal loop, not something watched for.** A playback grant is short-lived; the overlay component is what calls `/playback/{grant}/renew`. Remove it from the DOM and renewal stops, the grant expires, and the next byte-range request is refused — the decision sits on the server, where it cannot be edited away. This is also why the local provider serves with `Accept-Ranges: bytes`: without range requests, expiry could not cut a file already in flight.
- **The device limit counts devices, not sessions.** Signing in twice on one laptop is two sessions on one machine; counting sessions at a limit of one would log a student out of the computer they are sitting at, punishing the account holder and leaving the person they shared the password with untouched. Enforcement is deleting the Sanctum token — the one number a client cannot forge. The fingerprint only merges; it is forgeable and pretending otherwise would be a lie. The browser half of the fingerprint is `X-Device-Id`, a random id `lib/api.ts` keeps in `localStorage`; without it two people on the same phone model look like one machine.
- **The transcript is derived, and the caption file expires with the grant.** `media_captions` stores a WebVTT path and nothing else — no transcript column, because a stored second copy of the same words drifts from the subtitles at the first typo fix. `WebVtt::parse()` derives it server-side (validation) and `TranscriptPanel.tsx` derives it again in the browser from the file the `<track>` already fetched. That file is served by `/playback/{grant}/captions/{caption}`, not from a public path: a `<track>` sends no `Authorization` header either, and a permanent caption URL would be the lesson's entire script, permanently linkable. When an asset has captions the watermark rotates through the **top** corners only — the browser's caption band is exactly the `bottom-14` row, and a viewer who needs captions cannot work around a covered word.
- **A correct password on a two-factor account issues no token at all.** `/auth/login` answers `{two_factor: true, challenge}` and the challenge lives ten minutes in the cache, not a table — nothing reads one of those rows a minute later. Minting a Sanctum token and then restricting it would mean any flaw in the restriction is a full sign-in with the password alone, which is the thing the second factor exists to prevent. The exchange goes through `StartAuthSession` like any other sign-in, so the device limit and its alert still apply. The secret lives on `user_security_settings` and `User` implements Filament's `HasAppAuthentication` **by hand** (its traits assume columns on `users`), so one enrolment serves both `/admin` and the API — two implementations would mean two QR codes for one person.
- **`2fa.required` is applied route by route, never to a group.** The five sensitive routes each carry it in their own definition, where it is visible when the route is read; a blanket rule is either too wide or grows an exception list nobody prunes. Before `two_factor_required_at` it passes and the frontend nags; after it, 403 with `code: two_factor_required`. Recovery codes are stored hashed, so the confirm response is the only place they exist in readable form — a "show them again" endpoint cannot be built without weakening the storage.
- **The notification bell is the session heartbeat.** Enforcement is instant server-side, but a client only finds out when it next speaks: the bell's 60s poll is what makes a passively-reading page discover it, and the 401 handler in `frontend/src/lib/api.ts` is what turns that into `/login?ended=…`. Drop the interval "because a badge does not need polling" and an evicted account keeps showing its owner a screen they are no longer entitled to. The `session_uuid` saved at sign-in is what lets a tokenless client still ask *why*.
- **`users` carries what every account has; anything true of one role gets its own table.** `student_profiles` and `user_security_settings` exist for that reason. `guardian_profiles` and `admin_profiles` deliberately do not — no field is theirs yet, and an empty table is not a design. Adding a role-specific column to `users` will be rejected in review.
- **Attendance never passes through the broadcast provider.** The register is built from a heartbeat hitting our own route and the server does the arithmetic: `stay_seconds += min(now − last_ping_at, 2 × interval)`. Three properties fall out of that one line — two devices do not double the time, leaving and returning aggregates into one stay, and an hour of silence is capped rather than credited. It is also why all of attendance was provable before any broadcast contract existed. A provider that reports its own attendance is a provider you cannot leave.
- **Seats are claimed by an atomic conditional UPDATE**, never `count()` then `insert()` — that is the definition of the race — and never `lockForUpdate()`, which is a no-op on SQLite, so a test written around it passes locally and proves nothing about the MySQL it will run on. `SeatConcurrencyTest` walks the same path real concurrency does.
- **`SessionCompleted` is not `SessionDelivered`.** Completion is "the session ended"; delivery is "the teacher joined, stayed long enough, and it ended normally". Two events rather than one with a flag, because a flag makes the condition optional for the listener — and only delivery carries the frozen seat count spec 006 bills against. `billable_seats` is likewise written **once**, at the cancellation deadline, and never recomputed: it answers a question about a moment that has passed, and a consumer that derives it from live bookings will get a different answer every day.
- **The model is `ClassSession`, never `Session`.** `AuthSession` (spec 004) already owns that word, and two things called Session in one product is a line every reader misreads once. The frontend follows: `lib/class-sessions.ts` beside `lib/sessions.ts`.
- **A `->delay()` runs immediately on the `sync` queue connection.** A delay is a queue-driver feature and `sync` has no queue, so any test that exercises a session timeline must `Queue::fake()` — otherwise `CloseClassSessionJob` fires inside `OpenBroadcastRoom` and closes the session before the teacher joins, collapsing the timeline into a green test that proves the opposite of what it claims.
- **A freeze period is read, never written to.** Scheduling, booking, `MarkAbsenteesJob` and `SyncTeacherCountersJob` consult it; no counter ever moves. That is why FR-043's "counters resume with their previous values" holds without a line of resumption code — there is nothing to undo. Sessions already booked inside one are suspended, not deleted.
- **A Resource runs once per row, so a query inside one is an N+1 by construction.** `ClassSessionResource` asked every published session where its recording went — one `lessons` SELECT per row, on both the teacher's calendar and every student's timetable. The fix is the `recordingLesson` relation plus eager loading at each call site; the fallback query stays as the last branch, because a caller who forgets would otherwise publish a recording with no way in, silently. `QueryBudgetTest` fails if the eager load is dropped.
- **`whereDate()` costs the index the column was given.** MySQL cannot use `(workspace_id, starts_on, ends_on)` once a function wraps the column, and `FreezePeriod::covering()` is consulted on every booking, every schedule and every absentee sweep. Compare against a date string instead. When the column is a *timestamp* and the bound is a date, the upper bound is the START of the next day — `<= ends_on` silently drops everything after midnight on the last day.
- **`SESSIONS_VIEW` and `ATTENDANCE_VIEW` are two different questions.** The first says "you may see the sessions you can book" and every student holds it; the second says "you may read who attended one". Authorising the register with the first hands each student the class roll — names, stay durations, and the reason a teacher changed someone's mark. A reader without `ATTENDANCE_VIEW` gets their own row, which is ownership rather than permission and therefore not a 403.
- **An Action that acts on a named student must prove the student is theirs.** `exists:users,uuid` answers a different question: NFR-001أ forbids a teacher learning anything about someone with no active enrolment in their own workspace, so a bare uuid parameter is an identity probe — pass any user's and the response comes back carrying their name. `CreateFreezePeriod` asks `EnrollmentDirectory` before it writes.
- **`SessionCancelled` carries the seat holders, because by the time a listener runs nobody holds a seat.** Releasing them is part of cancelling, so a listener that reads the bookings afterwards sees one undifferentiated pile and tells the student who cancelled last month that their session is off. The Action reads the ids while they are still true.
- **`teacher_profiles.attendance_rate` is the TEACHER's attendance**, not their students'. It is the share of countable sessions actually delivered; a student's absence never touches it. The name reads the other way, which is why the meaning is written in `SyncTeacherCountersJob`, in `docs/README.md`, and in a test that fails if anyone changes it.
- **Operational numbers live in `platform_settings`, not `config/`.** The device limit, upload limits and grant TTL are rows an operator edits from the panel; `config/media.php` is the fallback for a database with nothing seeded. A limit that can only change by shipping code is a limit nobody ever tunes.
- Module directory names are matched literally by `Module::registerMigrations()`/`registerFactories()`. Migrations must live in `Database/Migrations` (capital M) — a casing mismatch resolves fine on Windows/macOS and silently loads **zero** migrations on Linux.
- Adding a tenant-scoped model without `BelongsToWorkspace` leaks data across workspaces and no test will catch it unless you add one to `tests/Feature/Tenancy/WorkspaceIsolationTest.php`.
- Frontend stores the Sanctum token in `localStorage` and sends `Authorization: Bearer` (`frontend/src/lib/api.ts`); it relies on the Next.js rewrite, so the backend must be running on :8000.
- Don't run `npm run build` while `npm run dev` is up — both write `.next/`, and the dev server then dies with `Cannot find module './NNN.js'`. Stop dev first (or accept that you must `rm -rf .next` and restart it).
- **The frontend is Arabic-only and RTL-only** (spec 002). One root layout, `frontend/src/app/layout.tsx`, declares `lang="ar" dir="rtl"`, loads Cairo, and runs the pre-paint theme script; `(public)` and `(app)` are nested layouts that add chrome only. Adding a second `<html>` anywhere re-splits the product.
- **Colours come from `@theme` in `globals.css`, never from a class.** No `bg-gray-*`, no `bg-white`, no hex in a component. `text-white` is allowed *only* as the foreground of `bg-primary`/`bg-secondary`/`bg-danger`; `accent` and `trust-medium` have their own `-foreground` tokens because white fails 4.5:1 on them. Layout uses logical properties (`ms-*`, `start-*`, `text-start`) — never `ml-*`/`left-*`. Direction lives in icon *names* (`ChevronStartIcon`), not in a CSS flip.
- **Shared UI lives in `frontend/src/components/ui/`** (`Button`, `Card`, `Badge`, `Alert`, `Table`, the `Field` family, `states/`). Components there take no free-form `className` — appearance is a closed set of variants. `components/marketplace/` is now marketplace-specific only. Arabic status labels and money/date formatting go through `src/lib/labels.ts`.
- **Never show a raw error to the user.** 422 goes through `fieldErrors()` and lands under its field; everything else goes through `userMessage()` in `src/lib/errors.ts`. Validation text itself is Arabic from `backend/lang/ar/`, and every new `FormRequest` field needs an entry in that file's `attributes` array or it renders as `phone_number`.
- **Rate limiters are named** (`throttle:auth` · `throttle:registration` · `throttle:public`, defined in `AppServiceProvider::registerRateLimiters()`). Inline `throttle:5,1` is banned: `ThrottleRequests` keys guests on `domain|ip` with no route in the hash, so every inline limit shares one counter and the strictest one wins — browsing the marketplace used to lock a visitor out of logging in.
- **Component logic is tested with `npm test` (vitest + jsdom); Playwright answers a different question.** The frontend had ONE test surface until the day three interface defects shipped together — a second tap that silently turned a right answer into a zero on a graded paper, a screen that offered to upload a video for an article, and a player that told every non-Safari student «صيغة غير مدعومة». None is reachable from the backend suite, and none was worth a Playwright run: that config builds for production and needs two servers, so nobody runs it inside a development loop. `npm test` needs neither and finishes in about two seconds. **The dividing line is the question, not the layer**: "does this component do what it says" is vitest; "does the product work end to end, and is it accessible" stays Playwright. Two configuration details are load-bearing — `include` is scoped to `src/**/*.test.{ts,tsx}` (the default would swallow `e2e/*.spec.ts` and die inside Playwright's runner), and globals are OFF so every test imports `describe`/`it`/`expect` by name and `npx tsc --noEmit` needs no test-only `types` entry. SC-012 (a player surviving a rejected segment) is measured here by mocking `hls.js` and calling the ERROR handler it registers; reproducing it for real would mean rotating a signing key against a live CDN mid-playback.
- **`npx playwright test` needs an API that can answer concurrently, or the *build* fails before a single test runs.** The committed config builds for production, and Next prerenders `signup/teacher` and `signup/parent/children` by fetching the API — in parallel workers. `php artisan serve` is PHP's built-in server with **one thread**, so it answers the first and refuses the rest: `TypeError: fetch failed … ECONNREFUSED`, then `Export encountered an error`. Start the API as `PHP_CLI_SERVER_WORKERS=8 php artisan serve`. Worth the trouble: the production run is 4 minutes and green, the same suite against `next dev` takes 31 and fails on `page.goto` timeouts that mean nothing.
- **A 500 on EVERY page is two route files resolving to one path, and route groups produce no URL segment.** `(app)/(shell)/privacy/page.tsx` and `(public)/privacy/page.tsx` both answer `/privacy` — the nested layouts do NOT keep them apart, whatever a comment says — and Next refuses to serve the **whole application**, not just those two: `/`, `/login`, `/dashboard`, all 500 with `You cannot have two parallel pages that resolve to the same path`. It shipped and sat for a session because neither `npx tsc --noEmit` nor `npm test` builds routes, and the message names the two files while the symptom is global. The in-app screen is `/settings/privacy` now; `/privacy` belongs to the public policy, which is linked from every footer and both signup forms. ⚠️ **And the dev server does not recover on its own** — it holds the stale build manifest and keeps printing the old error after the file moves. Restart it.
- **A 500 on one page with a `Jest worker … exceeding retry limit` message is a corrupted `.next/`, not a bug in that page.** Delete the directory and restart. The two axe violations it produces (`document-title`, `html-has-lang`) are Next's error page being audited instead of yours, which reads as an accessibility regression on a page nobody touched.
- **Settlement and billing are two contexts with no key between them, and that absence is load-bearing.** The teacher's pay and the student's payment share no foreign key and no query; the only bridge is the `SessionDelivered` event from 005. `ContextIsolationTest` fails the build over a violation in either direction — including a billing event consumed under `Modules/Settlement/`, and including a field added to a teacher-facing Resource that is not in `TeacherFieldAllowlist`. The table lists are derived from each side's `Schema::create` calls, so 006's credit tables are covered the day they land.
- **Counts come from `teaching_units`; money comes from `ledger_entries`.** `LedgerEntryType` carries `Deduction` and `Bonus`, which have **no teaching unit behind them** — a total derived from units omits the first manual adjustment anyone writes, and the statement stops matching the close the same day. The ledger is the balance; the statement reads it. The ledger is also append-only, enforced on the model (`LedgerEntry::booted()` throws on `updating`/`deleting`) rather than only in the Action. A bulk `update()` retrieves no models and so bypasses that guard, which is why period stamping is the one sanctioned post-insert write and stays the only one.
- **Settlement money is an integer in minor units**, departing from Payments' `decimal(12,2)` on purpose: Laravel's `decimal:2` cast returns a **string**, so every sum goes through a float. Tolerable for an order total, not on the table that decides a salary. `formatMinorMoney()` on the frontend is the only place it becomes text — the API never sends pre-formatted money, because a formatted string is a number the client has to parse back before it can add anything up.
- **A close claims units with `< ends_on + 1 day`, never `<= ends_on`.** `ends_on` is a DATE and `delivered_at` a timestamp, so the second form binds midnight and silently drops every unit taught on the closing day — the same boundary that cost `FreezePeriod::covering()` a fix in 005. Standalone ledger lines (a deduction, a bonus) carry **no** date filter at all: an adjustment is typed *after* the window ended, so a date filter there would push every deduction into the next period and pay in full a window meant to be reduced.
- **The settlement audit filters by asking for six subject types, not by removing rows.** `activity_log` is one shared table that billing writes to as well; a reader that fetched it and then dropped the billing rows would be one forgotten branch away from showing an auditor of teacher pay what a student paid. `SettlementAuditSubjects` is the whole filter, and it is platform-wide by design — the table has no `workspace_id` column and `settlement.audit.view` reaches super-admin alone.
- **Reordering the tree is a write to ACCESS RIGHTS, not to a display order.** `Enrollment::accessTo()` derives what a student may open from the triplet of section, chapter and lesson positions, so moving an item changes who can reach what, immediately. Every reorder therefore sends the COMPLETE sibling list plus `structure_version`, and `StructureVersion::claim()` — one conditional `UPDATE … WHERE structure_version = ?`, the seat idiom — is both the check and the bump. Comparing a loaded model and incrementing later is the lost update it exists to prevent: two teachers both pass, both write, neither sees a 409. Never `lockForUpdate()`, a no-op on SQLite.
- **The progress denominator excludes a recording through BOTH its doors.** A recording is entitled by a SEAT, not by enrolment, so `countableForProgress()` drops it *and* `accessTo()` refuses to let it stand as a prerequisite. One without the other still bricks the course: left in the denominator, a seatless student can never reach 100%; left in the chain, it locks everything after it. This is the family of the spec's worst defect — an item that enters the denominator and can never be completed caps every enrolled student below 100%, so `CourseCompleted` never fires and no certificate ever issues, permanently. Six roads led there and all six are named in `docs/README.md`; the two that outlive publishing are **archiving** and **deleting** the last item a student had left, which is why anything moving the countable set fires `CourseStructureChanged` → `ResyncCourseProgress`. `progress_pct` is otherwise written when a lesson is completed and at no other moment.
- **`LessonEditor` renders by `asset_kind`, and the ONE type that had a page of its own is where the bug came from.** Video was routed to `/manage/courses/{course}/lessons/{lesson}` — a screen whose heading said «فيديو الدرس» and whose input was `accept="video/*"` — while the course overview linked EVERY item to it whatever its type. So opening an article offered to upload a video for it, and `RequestUploadTicket` refused with «هذا النوع من العناصر لا يحمل ملفاً خاصاً به»: a correct answer to a request the screen invented. That page also never fetched the lesson, so it never knew about an existing video — a teacher who had already uploaded one was told «لا يوجد فيديو لهذا الدرس بعد» on every visit, with no way to replace it or reach its captions. `VideoEditor` joins the `AssetUploader` family with the others and the page is deleted; the overview links to `/content?lesson={uuid}`. **The rule underneath: a screen that does not know an item's type must not offer an action that depends on it** — `LessonTypeRegistry` answers that question and `LessonResource` already sends `family` and `asset_kind` so nothing restates it in TypeScript.
- **A publish is previewed by the code that performs it, never by an estimate beside it.** `PreviewPublishImpact` borrows `PublishTreeNodes::resolve()`, its `assertReady()`, `Lesson::progressEligible()`, `CourseProgress::percentage()` and `ExamGateSatisfaction`; the ONE thing it simulates is the three status conditions, because that is what a publish changes. A second denominator computed "just for the preview" is how the teacher gets shown a number no student ever had (`SC-018`). The preview also returns the item list it costed, and the client publishes THAT list — deriving the draft set on both sides is the same drift wearing a different face.
- **Renumbering comes before the index, and `chunkById` before `chunk`.** 016 added `unique(chapter_id, order)` to rows that already held duplicates, so the densify migration must run before the index migration or the deploy fails on live data. And the uuid backfill walks with `chunkById`: `chunk` paginates by OFFSET while the predicate (`uuid IS NULL`) shrinks under it, so every page after the first skips as many rows as the previous page fixed — and reports success. The parking offset in a reorder is `max(order) + 1` for the same reason a constant fails: `max(order)` tracks a group's LIFETIME create count, not its row count.
- **Authored text is Markdown, rendered per response, never stored as HTML.** `MarkdownRenderer` strips raw HTML rather than escaping it, so the allowlist is the Markdown feature set itself — there is no sanitiser configuration to get wrong. A stored `content_html` would be a second copy of the same words that drifts from the source at the first typo fix, and a stored-HTML column is an XSS sink with a teacher's keyboard attached to it.
- **A credit is one session at ONE teacher's rate, and the account it hangs off is platform-wide.** `student_credit_accounts`, `credit_packages` and `terms_consents` carry **no** `workspace_id` by design — one person, one account, one catalogue, one signature. The BALANCE underneath is workspace-scoped, because a credit is not portable between teachers. Adding `BelongsToWorkspace` to the account would silently duplicate one person per teacher, which is the mirror-image bug `PlatformOwnershipTest` exists to catch in both directions.
- **The floor guards BOOKING, never the recording of a debt.** `CreditMovement::$enforceFloor` defaults to **false**: a session that was delivered is owed whether or not the student can pay for it — spec 014 has already earned the teacher their fee from the same `SessionDelivered` event, so refusing the entry would leave the platform owing money with no claim against anyone. A test that expects `InsufficientCreditsException` must pass `enforceFloor: true` or it is asserting the wrong requirement.
- **`is_withheld` is derived from FIVE inputs and stored as none of them**: the balance, the ceiling, the billing mode, an open exam window, and a CURRENT terms consent. So a lift is instantaneous and no `access_holds` table can drift from it — and a published new version of the terms stops deferral for everyone who has not signed it, on their next booking, with nothing to sweep. Never add a column for it; `WithholdingReader::stamp()` is the bulk form, and a per-row read inside a Resource is an N+1 by construction.
- **The credit-limit demotion IS the switch to prepaid for that student.** The floor is `−credit_limit_credits`, so a ceiling of zero and a prepaid mode produce the identical predicate; a per-student `mode` column would be a second answer to a question the floor already answers. And the limit moves by **deltas** with the earning counter CONSUMED — a `limit = f(consent, history)` recomputed from scratch hands the defaulted student their ceiling back on their first payment afterwards. The initial `0 → 1` is an EVENT (first consent, and the birth of any later balance), never a state anything derives.
- **`isBlocked` asks the balance as well as the floor.** `$floor < 0` was the whole test for "owes money" and the demotion breaks it: the ceiling goes to zero while the balance stays negative, so in a `remind` workspace the defaulted student books at −3, −4, for ever — exactly the person the demotion was aimed at.
- **Withholding is per COURSE, never per person, and balances are never summed.** +10 in maths and −6 in physics reads as +4 and unblocked when added up, while the design withholds per course precisely so the paid-up course stays open. The API sends no total because there is no correct one.
- **No money reaches the student's or the teacher's screen.** A credit's price is the teacher's approved settlement rate plus two platform constants, so a total shown to either side is solvable for the other's rate across two package sizes. `StudentBalanceAllowlist` and `PublicFieldAllowlist` fail the build over a field that leaks it, and `formatMinorMoney()` on the frontend is the only place a number becomes currency.
- **Approving a credit purchase and moving a ceiling are PLATFORM permissions**, held by no tenant role. A package a teacher could define is a sale price a teacher sets (FR-021ب); a ceiling a teacher could raise is a teacher deciding how much the platform may be owed. `billing.credits.adjust` currently has no HTTP surface at all — the Action exists and enforces its own rules, and a screen for it has not been built.
- **`concept_stats.lesson_id` is `NOT NULL` and zero means "the concept overall".** NULL never equals NULL, so a unique index carrying a nullable column does not bite on the one row every screen reads: `upsert()` matches nothing and INSERTs, a new row every night, and after a month the page shows whichever came back first — a number thirty days old while the correct one sits beside it, with not one error logged. `RollupIdempotencyTest` runs the job TWICE for that reason; one run is green for ever and proves the opposite. The rollup also excludes two families of row that are invisible in a naive `COUNT`: `is_practice` attempts (the flag is on `exam_attempts` while the answers are on `exam_answers`, so the join exists only for it), and essays with `requires_grading` and no `graded_at` — `GradeAttempt` writes those `is_correct = false` because no machine can judge them, so counting them reports every essay in the bank as 100% wrong, permanently. And a sample below `assessments.min_sample_size` stores `wrong_pct = NULL`, never zero: "nobody got this wrong" is what makes a teacher delete a good question two students happened to sit.

- **Reconciliation is a JOB, and the obvious check inside it is blind.** Three `GROUP BY`s over the fastest-growing tables with no tenant filter would run on every refresh of a page. And the ledger-vs-balance comparison proves almost nothing on its own: both sides are written by the same path in the same transaction, so a session that was never charged leaves them in perfect agreement. The two invariants that see it come from outside — one consumption entry per seat of a charged session, and a positive balance equalling what its lots hold.
- **An expiry claims its lot first and then posts with `drawsFromLots: false`.** Posting it as an ordinary negative movement lets the drawer take the same credits a second time out of lots that have not expired. Expiry is switched OFF at launch (`validity_days` defaults to null) but the soonest-expiring-first draw order is live from day one — turning expiry on later must not rewrite which lot paid for which past session.
- **The dormancy notice needs its own column.** The notice moves no credits, so a predicate on `last_transaction_at` alone re-sends it every night to the student least likely to want it; `notified_dormant_at` is stamped BEFORE the dispatch (a lost reminder beats one a night for ever) and cleared by the ledger on the next movement. It is a reminder, never an expiry: nothing is forfeited and nothing moves to another teacher, which would be a re-pricing.
- **`insertOrIgnore` writes a row without booting the model, so `HasUuid` never fires** — and on MySQL the resulting NOT NULL violation is downgraded to a warning and `''` is stored, after which *every* later entry on the platform collides with that row on `unique(uuid)`, is read as "already recorded", and is silently skipped. The ledger stops after one row while every caller reports success. **This is a rule about the insert ARRAY, not a ban on the call.** `CreditLedger::writeEntry()` uses `insertOrIgnore` deliberately and correctly: the unique index is the idempotency guard, and `uuid` and `created_at` are passed EXPLICITLY because the model layer is not there to supply them. `create()` in a try/catch was rejected in R7 — it makes a real failure (a null, a foreign key, an out-of-range value) indistinguishable from a duplicate. What `insertOrIgnore` needs instead is the read-back: zero rows means *either* a duplicate or a swallowed failure, so the entry is fetched by its key and a miss **throws** rather than returning null.
- **The floor comparison is CAST to signed, and MySQL alone will tell you why.** `remaining + limit >= n` evaluated at `remaining = −3` on `unsignedInteger` columns raises **ERROR 1690, BIGINT UNSIGNED value is out of range** — and SQLite has no unsigned arithmetic to overflow, so no local test can ever reproduce it. The guard is `CAST(... AS SIGNED)` in `CreditLedger::applyToBalance()` and the signed column widths in the migration; both carry the reason beside them, because the failing environment is the one nobody runs the suite in.
- **The entry is written BEFORE the lots are drawn and before the balance moves.** Decrementing first means a redelivered event debits twice while the duplicate entry is ignored once — and the balance stops equalling the sum of its entries, permanently, with nothing to notice it. `ReconcileCreditBalancesJob` is what would notice, the next night, by which time the cause is a week of traffic away.
- **`Queue::fake()` with no arguments makes half the billing suite assert zero rows.** The charge listener is queued, so a bare fake swallows it and "four attendance states ⇒ four consumption entries" becomes a confident assertion about an empty table. Fake the timeline jobs only — `Queue::fake([CloseClassSessionJob::class, SendSessionReportsJob::class])` — and let the charge run on `sync`. Calling the Action directly instead tests the arithmetic and proves nothing about the wiring.
- **A valid signature is not a check on the amount, and the two get conflated the moment one class does both.** A provider can sign a perfectly correct notification saying 100 for a payment of 500 — the signature proves the body came from them, not that the body agrees with the order. `HandleProviderCallback` compares the amount separately and answers `mismatch`: no charge, no credits, the withholding stays, and the case enters the reconciliation report. A verifier that returned "valid" for both questions would credit the student 100 and close the debt of 500.
- **A provider with no gateway accepts no notification at all.** `manual` has none, so anything arriving at `/webhooks/payments/manual` naming a real reference is an impersonation, not a late callback — it is refused with zero effect, and an unknown provider is a `404`. Both answers are `202`-shaped from outside for the reason the signature is: a distinct reply for a wrong signature is an oracle telling an attacker when they are getting warm.
- **One capture per order is a UNIQUE COLUMN, not a partial index.** `captured_order_id` is nullable and carries `unique()`; it is written `= order_id` inside the same atomic conditional UPDATE that moves the status to captured, and NULL does not collide with NULL, so every non-captured row coexists freely. MySQL has no partial indexes — `WHERE status = 'captured'` on an index is a Postgres feature — so the "obvious" form of this guard silently does not exist on the database this ships to. The column is deliberately NOT `$fillable`: mass-assignable, it becomes a second way to claim the lock from outside the transaction that owns it.
- **The callback's idempotency key is TWO columns, `(provider, external_id)`.** An id is unique within the provider that issued it and nowhere else, so a single-column key means the second gateway ever integrated starts silently swallowing the first one's notifications as duplicates. The sweep exploits the same index deliberately: it REPLAYS the notification the provider should have sent rather than capturing by hand, so a sweep and a late callback for one payment collapse into one row.
- **A Horizon supervisor needs `defaults` AND `environments`.** `defaults` supplies shared values; `environments` decides which supervisors actually START. A queue named only in `defaults` is a queue whose jobs enqueue and are never drained — silently, with the dashboard showing nothing wrong. And a connection/queue pair absent from `waits` is not watched at some default: it is not watched, so a backed-up payments queue tells nobody while every callback in it has already been answered `202`.
- **A platform-permission read must declare `withoutWorkspaceScope()`, AND repeat it in every eager load.** `WorkspaceContext::id()` falls back to `users.last_workspace_id` for every user including a super admin, so a platform report left scoped shows one teacher's money as the platform's total — and passes its own test on a single-workspace fixture. The bypass is per model: `->with('order')` runs Order's global scope inside the relation query and returns null for every row outside the reader's fallback workspace. That one shipped in the audit chain, answering "nothing was bought" with a 200. Any test of a platform-wide read needs TWO workspaces or it proves nothing.
- **A workspace role may never hold a platform permission, and the guard is on the MODEL.** Roles are editable from `/admin` now, and the same tick box unguarded is how an owner grants themselves the collection report and the platform's half of the price. The picker offers `RolePermissionMatrix::tenantPermissions()` — but a filtered form shapes one request and not the next, so `Tenancy\Models\Role` throws on `givePermissionTo()`/`syncPermissions()` when a platform permission reaches a role with a `team_id`. The platform set is **derived** (`all()` minus everything any workspace role holds), so a permission added tomorrow is platform-level until somebody puts it in a tenant role on purpose. And both seeders import `Tenancy\Models\Role`, not spatie's: `config('permission.models.role')` governs what the PACKAGE resolves internally, while a class named directly in a file is the class that runs — reaching for the base class is the third door `ImmutableAuditTest` already names for the activity log.
- **`roles` is workspace-scoped now, and `/admin` is why.** Every teacher can reach the panel, so an unscoped role list hands one teacher another teacher's roles with an edit button beside each. `TeamRoleScope` keys on spatie's team id (the same number `EnsureCurrentWorkspace` pushes in, so it agrees with every permission check in the request) and is inert when that id is null — the platform context. `RolePolicy` is the row-level half, because a list filtered by a query and a record fetched by id are two different questions. Deleting a DEFAULT role is refused: `SeedDefaultRoles` runs once at workspace creation, so a deleted `teacher` never comes back and every member holding it loses everything at once.
- **Platform standing is a table, because spatie cannot express it.** `model_has_roles` puts `team_id` inside its primary key and forbids NULL, so `finance-admin` — seeded and correct since 006 — could be given to nobody. `platform_staff` carries who, which role, by whom and why; a `Gate::before` turns it into that teamless role's permissions in whichever workspace the officer is looking at. That hook returns **`null`, never `false`** (false short-circuits every policy behind it) and answers only for names in `Permissions::all()` (Filament checks `view`/`update` on models constantly). `PlatformStaffDirectory` memoises per request and declares `withoutTeamScope()` — the one sanctioned bypass, without which the scope hides the very role the officer's permissions come from.
- **Filament Shield generates nothing here.** `permissions.generate` and `policies.generate` are off and `format_custom_permission_keys` is **false** — our names are dotted and lower-case, and the formatter would pascal-case `billing.audit.view` into a string no policy has heard of. Shield's `super_admin` and `panel_user` roles are off too: super-admin is the `users.is_super_admin` column, and a second one wearing a role is two answers to one question.
- Playwright projects carry an authenticated `storageState` produced by `e2e/auth.setup.ts` so the panel can be audited. A spec that tests an anonymous visitor must opt out with `test.use({ storageState: { cookies: [], origins: [] } })`, or it silently tests a signed-in one.
- **A unique index carrying a nullable column does not bite, and 008 has TWO of them.** `concept_stats.lesson_id` and `unlock_rules.course_id` are `NOT NULL` with **0** meaning "no narrower scope", because NULL never equals NULL: `upsert()` matches nothing on the one row every workspace reads, INSERTs a new one every night, and after a month the screen shows whichever came back first — a number thirty days old beside the correct one, with not one error logged. `RollupIdempotencyTest` runs the job TWICE for that reason; one run is green for ever and proves the opposite. The price of the sentinel is that `(int) null === 0`, so a failed uuid resolve addresses the DEFAULT row — `UnlockRuleController` guards it with `abort_if` before writing.
- **The snapshot is the denominator, and `attempt_items` is written at START.** Grading reads the snapshot, never the live question, so an exam edited after a student sat it cannot change what they were marked on. Two consequences that are not obvious: a migration had to BUILD those rows for every pre-existing attempt or each one's denominator is zero — and `SC-015` passes blind, because it measures `score` alone — and `GradeAttempt` writes an answer row for **every** item rather than for the answered ones, since a question left blank is the strongest evidence of a gap and would otherwise be missing from the mistake notebook entirely.
- **A question carries EXACTLY ONE correct option, and «at least one» was the rule until a teacher asked why two was allowed.** `GradeAttempt::matchesSnapshot()` compares the correct SET against the selected SET, and every answering surface in this product is single-select — so a second correct option is a question one tap can never satisfy: every student wrong for ever, and a `wrong_pct` of 100% that reads as the hardest item in the bank, which is the number a teacher deletes a good question over. **It is the same defect as NO correct option, reached from the opposite side**, which is why one rule refuses both. Guarded in `SaveQuestionRequest` and again in `SaveQuestion::guardExactlyOneCorrect()` — the importer, the seeder and the panel reach `syncOptions` with no form behind them — and named separately in `ImportQuestions`, because a per-row reason is read beside a row number and must say which COLUMN to edit. The two answering surfaces (`PracticeRunner.tsx`, `exams/[uuid]/take/page.tsx`) replace the selection rather than accumulating it — they used to add, so a second tap silently turned a right answer into a zero on a graded paper.
- **The practice pool subtracts the exam not yet sat, and the notebook deliberately does NOT filter practice.** One bank question serves several exams, so a question missed last month can also be in next week's paper: practise it and the platform marks it instantly and shows the explanation, which is the exam handed over a week early. The mistake notebook is the mirror image — answering correctly IN a practice run is exactly how a mistake gets fixed, so filtering practice out means the "test me on my mistakes" loop can never resolve anything and returns the same questions for ever.
- **`SeedCommand` runs every seeder inside `Model::unguarded()`.** So `$fillable` protects the application and not the seeders: dropping `exam_id` from `Question::$fillable` in 008 left `DemoDataSeeder` writing the column, which was the last writer standing between the codebase and `T180`'s drop. Any claim of the form "nothing writes this column any more" has to be checked against `database/seeders/` separately, because the guard everyone reasons from is switched off there.
- **`getContent()` escapes non-ASCII, so a leak assertion with an Arabic needle is vacuously true.** `expect($response->getContent())->not->toContain('حلُّ زميلي.')` never matches, whatever the payload holds — the body carries `حل...`. Every exposure test in this product asserts on Arabic text, so the whole file would pass against a response that leaked everything. `AssessmentExposureTest::bodyText()` re-encodes with `JSON_UNESCAPED_UNICODE`; the ASCII sentinels the Courses and Marketplace exposure tests use (`DRAFT_SENTINEL`, a distinctive English name) are the other way of being safe.
- **The unlock gate guards booking and joining, and deliberately not the nightly sweep.** `BookingEligibility::openingRefusal()` is the new door; `refusalReason()` stays what `ReleaseIneligibleBookings` calls, because that sweep **cancels** seats — folding the homework condition into it would repossess a paid seat over an unfinished worksheet. Excused counts as attended (only `absent` fails, an excusal being the teacher's decision that the absence is not held against the student), "previous" skips cancelled and suspended sessions, and a submitted-but-unmarked homework satisfies a score threshold: the late party there is the teacher.

- **The recording retry loop did not exist, and its absence was a teacher's pay.** `IngestSessionRecordingJob::giveUpOrRetry()` increments `recording_attempts`, writes `recording_status = 'pending'` — and **returns**. No `release()`, no second dispatch; the only sender was `SessionCompleted`, which fires once. So the first "not finished yet" was also the last attempt and the counter froze at 1. It was silent because `NullBroadcastProvider` declares `recording: false`, so the job returned before reaching that branch — **017 is what switches it on**, which is why `RetryPendingRecordingsJob` ships with it. And the cost was never a badge on a screen: `Settlement\Support\PackageCompletion` reads the same column and withholds the fee for any session whose recording is not one of `published`, `failed`, `no_course` — so an eternal `pending` withholds pay for a lesson that was actually taught. **`no_course` releases it too** (a session with no course has no lesson to publish into), and `null` and `ingesting` do NOT, which is the part that bites: `RetryPendingRecordingsJob` sweeps `'pending'` alone, so a session whose ingest job died before writing anything holds a wage with nothing left to move it.
- **The guard against a second delivery is a conditional UPDATE, and it was a read followed by a write — with two senders by design.** `SessionCompleted` fires once and `RetryPendingRecordingsJob` re-dispatches every fifteen minutes, so two runners overlapping on one session is ordinary. Both read `media_asset_id` as null, both call `videos/fetch`, and **every call to it creates a video**: a second one, billed monthly, referenced by nothing, invisible without going to look. `UPDATE … WHERE media_asset_id IS NULL` is both the check and the claim — the seat idiom, the same one `captured_order_id` and `StructureVersion::claim()` use, and never `lockForUpdate()`, a no-op on SQLite. The asset row is INSERTed before the claim because the claim needs its id, which is safe precisely because nothing has been delivered yet: a loser deletes its own row having spent one local insert and no provider call. `recording_attempts` moves by `increment()` for the same reason — `$session->recording_attempts + 1` lets two runners write the same number, and a budget that never advances is an unbounded retry loop wearing a counter. **A single-threaded test still reaches this**: `recording()` is asked BETWEEN the read and the claim, so a callback there is the other runner winning inside exactly that window — no threads, no sleeps, and the sequential "second pass" test does NOT cover it (the second call reads a session that already has an asset and never reaches the claim).
- **`ReconcileAssetStatus` is the self-heal, and it needed a ceiling AND a verdict — either alone is a defect.** It runs every five minutes and spends up to two provider calls per `Processing` row (a title search plus a GET), and it had no age ceiling and no attempt budget of any kind: an asset whose delivery never landed was interrogated 288 times a day for the life of the deployment, and the standing bill grew with every asset that ever got stuck. But a ceiling on its own leaves that asset «قيد التجهيز» permanently — the exact state the job was scheduled to abolish, reached by another road — so past `media.reconcile_ceiling_hours` (48) it is written failed WITH a reason, which is what makes manual upload the way out instead of a guess. The age is measured from `created_at`, never `updated_at`: the sweep touches the row on passes that change nothing, and an age measured from the last touch is an age that resets itself. Two days matches the recording sweep's own window — no transcode takes that long and the ingest budget gave up hours earlier — but it does mean the "a late Ready overwrites failed with published" promise is now bounded: it covers a slow encode, not an abandoned one.
- **`recording_status` has THREE stuck values, not one — and the two nobody swept were the ones a crash leaves behind.** The column is nullable with no default and no initial writer outside the ingest jobs, so a job that dies before its first write leaves NULL; `'ingesting'` is written BEFORE the hand-off and corrected on the same pass, so only a hard kill (the 60-second job timeout across four provider calls, or an OOM) can strand it — `catch (Throwable)` covers a throw and never a kill. `RetryPendingRecordingsJob` selected `'pending'` alone, so both sat for ever while `PackageCompletion` held the teacher's fee for a lesson that was actually taught. **The crash was one connection away**: `recording()` is a live HTTP call and it stood ABOVE the `try` in `IngestSessionRecordingJob`, with Horizon at `tries: 1` — one refused connection ended the job with nothing written and a `failed_jobs` row as the only trace. Every provider call is inside that `try` now, and the sweep takes all three states. - **The API KEY travels in every ticket and the SECRET never does — a criterion banning both is a criterion that cannot pass.** `LIVEKIT_API_KEY` is the JWT's `iss` claim, which is how the server knows which key to verify against; it opens nothing alone. `LIVEKIT_API_SECRET` signs. `SC-005` was written as "zero provider key in any payload", which is false by protocol — and a test written to it would have been deleted rather than maintained. Same family as `room_url`, which the browser *must* have or nothing connects.
- **LiveKit cannot revoke a ticket and RECREATES a deleted room on the first join, so FR-009 is kept by two guards of OURS — and simplifying either one silently reopens a closed lesson.** There is no revocation call in the protocol, so a ticket still inside its ttl rebuilds the room `CloseBroadcastRoom` just deleted. ⚠️ **Auto-create IS controllable on Cloud, contrary to what this line said until it was checked against a real dashboard** — «Automatically create rooms on participant join» is a project-level checkbox under Settings → General, and it ships **ON**. Turning it off removes the rebuild entirely, but it does not remove the need for the two guards: they are what makes the behaviour correct on a self-hosted server, on a project where somebody re-enables it, and in the window before `OpenBroadcastRoom` has run. What actually holds the door shut is (1) `IssueJoinTicket` refusing to mint anything once `room_closed_at` is set, and (2) `BroadcastController` re-running that same issuance on **every `presence` heartbeat**, which evicts whoever is inside. - **An eligibility endpoint must ask whether the caller is the host before answering.** `BookingEligibility` answers questions about a STUDENT — an enrolment, a balance, a piece of homework — and no teacher holds any of them in their own workspace. So `/eligibility` told the host of a session «لست مسجّلاً عند هذا المدرّس», and the room page printed it under a refusal banner on their own lesson while the actual refusal was usually the clock. The host check is `Gate::allows('host', $session)` — the same `ClassSessionPolicy` ability the host routes are gated on in `BroadcastController` (not inside `PerformHostAction`, which carries no authorization of its own), never a re-derived condition, because two spellings of "is this the host" put one answer on the screen and another at the door.

- **A provider DECLARES which kinds it accepts, and the day that was merely assumed a PDF got a video object.** `ProviderCapabilities::$kinds` (null = all) plus `MediaProviderResolver::forKind()`: the configured provider gets first refusal and our own disk takes what it declines. The column is stamped from whoever actually took the file, never from the config, or `for()` would resolve the wrong provider for every routed asset. And `PUT /media/upload/{token}` now asks `$asset->provider === $provider->identifier()` — the local route used to accept a commercial provider's asset and write a disk path into `provider_asset_id`. Compared against the COLUMN, never the config, so a pre-flip local asset still in `Pending` stays uploadable after the switch.

The provider map lives in `MediaServiceProvider` alone and is INJECTED into `MediaProviderResolver`, so the resolver names no vendor and `tests/Feature/Media/ProviderNameContainmentTest.php` passes over it (a path, not a namespace — the file is Pest-style with no class, and `LiveSessions/` has one of the same basename).
- **`ingestFromUrl()` is the only change to 004's contract, and the download was MOVED rather than deleted.** It now lives in `LocalMediaProvider`, which is what a provider with no remote fetch has to do. Both providers declare `remoteFetch: true`: the flag answers "can you take a file over from a URL", not "did the bytes avoid our network" — declaring `false` on the local one would be honest about bandwidth and wrong about capability, and would force every caller into two branches for one question. The bandwidth is `SC-001`'s question, and `ZeroVideoBandwidthTest` asks it **as a negation over the whole `Http::fake()` request list plus a positive control**: asserting that `videos/fetch` was called passes on an implementation that downloads, uploads, then calls it — and asserting only negations passes vacuously over a delivery that did nothing at all.
- **`videos/fetch` DOES return the new video's id — the OpenAPI schema is wrong and this file trusted it for a day.** ⚠️ Verified against a live account on 2026-08-17: the 200 is `{"id":"42d1c5e3-…","success":true,"message":"OK","statusCode":200}` and `GET /videos/{id}` returns that value as its `guid`. The schema types the response as `StatusModel` (`{success, message, statusCode}`) and research §R3 built the whole design on it, dismissing the narrative docs page — which showed an id and was **right**. Read the id, and save it inside `ingestFromUrl` before anything else can fail; that is the only window in which it can be lost.
- **A presigned R2 url needs no `headers`, and `headers: []` is a 400.** ⚠️ Both verified live on 2026-08-18. The presigned url carries its own authentication in the query string, so the `headers` field of `videos/fetch` is for sources that need custom auth and ours never is — which is why the key is **omitted** rather than sent empty: `[]` encodes as a JSON array where the schema wants an object, answered `400 {"errors":{"$.headers":[…]}}`, classified permanent, and every recording would have failed on its first attempt. Also measured: Bunny starts the fetch immediately (a 2.8 MB clip was `Ready` with five renditions **15 seconds** after delivery on the free best-effort tier), so `BUNNY_SOURCE_URL_TTL_MINUTES=120` covers the download window with room to spare.
- **The title is still a cross-system JOIN KEY — as the RECOVERY key, not the happy path.** A delivery whose response never came back (a timeout after Bunny accepted, a worker killed between the POST and the save) leaves an asset with no id and a video that exists, and `{prefix}:{asset_uuid}` is the only thing naming one from the other. So changing `BUNNY_TITLE_PREFIX` still orphans every asset not yet recovered, and a duplicate title is still worth reporting — the exposure narrowed, the case did not disappear. And because every call creates a video, `IngestSessionRecordingJob` refuses to deliver twice for one session — a retry after a `429` would be a second video, billed monthly, referenced by nothing. The recovery is the existing sweep, not a webhook: `RetryPendingRecordingsJob` already runs every fifteen minutes, so polling costs zero new routes, zero signature verification and zero tables.
- **A recording can be neither ready nor failed, and that middle state is load-bearing.** A delivery accepted with no id recovered is `Processing`: `Ready` would publish a lesson over a file nothing can address, and `failed` would release the teacher's held fee for a recording still on its way. The session stays `pending` and not `ingesting`, because the sweep only re-sends for `pending` — and `PackageCompletion` withholds pay for anything outside `published`/`failed`/`no_course`. `'ingesting'` is written before the delivery and corrected on the same pass, so only a hard worker kill can strand it; `null` is the wider door, and neither value is swept. An attempt IS spent on "still encoding", deliberately; if a provider's encode outlives the budget the fix is not a bigger number, it is `ReconcileAssetStatus`, whose late `Ready` still fires `MediaAssetReady` and overwrites `failed` with `published`.
- **`token_path` is the whole of the playback protection, and its absence passes any test that asks for the index.** The manifest is HLS, so a token on `playlist.m3u8` alone leaves every `.ts` segment served openly — whoever holds one URL holds the video, with no grant, no watermark and no device limit behind it. The signature is the **advanced** scheme, `HS256-` + Base64URL(HMAC-SHA256(key, signature_path + expires + signing_data)), over the video's DIRECTORY; the basic scheme is an MD5 with no path allowance and cannot protect HLS at all. `SC-002` therefore measures what fetches BYTES, not the index.

- **`token_path` is SIGNED as well as sent, and it goes in the PATH, not the query — two separate mistakes that each 403 every video.** The exclusion list from `signing_data` is `token` and `expires` alone, so the hashed message is `signature_path + expires + "token_path=" + signature_path`; hashing `path + expires` on the reasoning that "we add no query parameters of our own" ignores that `token_path` is one, and ships an invalid signature. And the token belongs in the path (`/bcdn_token=…`), because RFC 3986 lets a relative reference inherit the base query **only when its own path is empty** — Bunny's `playlist.m3u8` is a master playlist pointing at `720p/video.m3u8`, so in the query form the index loads signed and every rendition and `.ts` beneath it leaves bare. Both shipped in 019 and both were green, because the suite asserted the token's SHAPE — which a wrong signature also has. The guard is `tests/Feature/Media/BunnyTokenVectorTest.php`, which needs no account and no network; **never replace it with another structural assertion.** ⚠️ **It is a PIN, not independent corroboration, and this file used to call it «the vendor's own published vector» — which is false: `BunnyWay/BunnyCDN.TokenAuthentication` publishes a reference implementation and no vectors.** The digest was computed from that implementation, so a misread algorithm would have been pinned just as confidently. What corroborates it is an account: on 2026-08-18 a URL from `manifest()` answered **200** from a real zone, and so did `720p/video.m3u8` and `video0.ts` beneath it — inherited under the one path token, no second signature anywhere. The viewer's IP is deliberately excluded from the signature: a phone moving from wifi to mobile data changes address and the lesson would cut out mid-way.
- **`recording_attempts` is a budget of five that everyone read as «an hour and a quarter», and nothing made that true.** ⚠️ Measured 2026-08-18: a `queue:work` started before a code fix and restarted after it left **72** `RetryPendingRecordingsJob` passes queued; they drained in one second and spent the entire budget inside it. The session was written `failed`, the teacher told the recording was lost and every seat holder told the same — about a file sitting intact in R2, mid-transcode, which `ReconcileAssetStatus` published **five minutes later**. A paused Horizon supervisor, a deploy, or any queue outage produces the identical pile in production. The gap is enforced now by `recording_attempted_at`, stamped inside the same statement that increments the counter; `updated_at` was unusable for it for the reason `notified_dormant_at` exists — it moves for every unrelated write to the row. The constant is **14** minutes against a 15-minute schedule: an exact match skips every other pass, because a scheduler is never punctual to the second.
- **«Still encoding» spends no attempt, because that phase belongs to another job.** Before the hand-off the question is whether the BROADCAST provider has finished assembling the file and nothing else is watching, so the budget belongs there. After it, the file is delivered and its id saved, and the question is whether the MEDIA provider has finished transcoding — `ReconcileAssetStatus` owns that, every five minutes, under `media.reconcile_ceiling_hours`. Charging it to the ingest counter meant an encode slower than five sweeps wrote the session `failed` and told the student «التسجيل غير متاح» about a video that published twenty minutes later: **a false sentence that stays in their feed, which no later success removes.** So `Processing` writes `pending` and returns; `Failed` is a verdict and is taken as permanent, because the asset the provider refused is the asset a retry would present again.
- **A `queue:work` holds the code it booted with, and that is how a fixed bug keeps reporting itself.** The `wss`-scheme fix went in at 16:24 and the worker started before it, so the pipeline kept failing with the exact error the commit removed — `failed_jobs` filling with a stack trace that no longer matches the file on disk. Two minutes of reading the tree for a defect that was not there. Restart the worker after touching anything it runs, and read the timestamps in `failed_jobs` against `git log` before believing a trace. The same run also showed a dev worker whose `--queue` list omitted `maintenance`: **194** scheduled jobs enqueued and never drained, silently. `config/horizon.php` names it correctly in both `defaults` and `environments` — it was the hand-written command that was wrong, which is exactly why that supervisor's own comment says a queue with no worker says nothing.
- **A valid Bunny token 403s when the request carries NO `Referer`, and that cost an hour of hunting a signing bug that did not exist.** ⚠️ Measured 2026-08-18: the zone answers `403` to a correctly signed URL fetched by `curl`, and `200` to the same URL with any referrer at all — `localhost`, `evil.example.com`, anything. So it is **not** a security control (a header is forged in one flag) and must never be counted as one; it is Bunny Stream's «block direct URL file access», aimed at a URL pasted into an address bar. Two consequences that are not obvious: a server-side probe, a smoke test or a monitoring check that omits the header reads a perfect signature as a broken one — which is exactly how the six-variant elimination above started, with every variant 403 and the key the obvious suspect. And a `Referrer-Policy: no-referrer` added to the frontend one day would 403 **every video for every student**, with the CDN as the only place the refusal appears; Next's default (`strict-origin-when-cross-origin`) sends the origin and is what currently keeps playback alive.
- **The pull zone answers `Access-Control-Allow-Origin: *` — on the bytes, not only on the index.** و-٥ closed by measurement on 2026-08-18: the master playlist, `720p/video.m3u8` and `video0.ts` each carry it, and `*` covers production as much as it covers localhost — an echoed-origin answer would have meant a green localhost proving nothing about a deployed host. hls.js reads the manifest with `XMLHttpRequest`, so without that header Safari (native HLS, no XHR) would be the only browser that plays anything, and no error would name the cause.
- **`PlaybackGrantResource` sends OUR route as `manifest_url`, never the manifest's own url.** For a redirect provider that url is the CDN hostname plus `provider_asset_id` — the one field FR-011 and that class's own docblock forbid in a payload. It travelled for free while the only provider pointed the manifest back at us, and would have started leaking the moment one did not. The signed url exists only as the `302` Location from `stream()`; a segmented player follows the redirect and resolves segments against the final url. ⚠️ **That does NOT make every segment a fresh trip through the grant** — this line used to claim it did. A VOD playlist is fetched once and never refreshed, so after that single redirect the segments come from the provider's host and this server is not consulted again. Revocation on a redirect provider is therefore the RELOAD (`reload_after_seconds`) plus the signed token's own expiry, not the per-range re-check that guards our own disk.
- **The player needed hls.js, and «صيغة غير مدعومة» was the shipped answer until 019.** `VideoPlayer.tsx` gated on `format === "progressive" || isNativeHlsSupported()` — correct while nothing produced HLS, and the moment a provider did, every student not on Safari would read an unsupported-format warning on a lesson that was fine. hls.js is imported **dynamically** and only where MSE is needed, so a progressive lesson downloads no player library, and `src` is left unset when the library drives the element — setting both makes the browser fetch a manifest it cannot parse and report an error over a video that plays.
- **`ReconcileAssetStatus` existed since 004 and was never scheduled.** Invisible, because nothing reached `Processing` and stayed there while the only provider settled an asset inside the request that uploaded it. It now runs every five minutes — and asks about `Processing` **only**, never `Uploading`: bytes still arriving *here* are not a question for a provider, and a 2 GiB PUT outlives the sweep's one-minute age check, so settling one mid-transfer would read a partial file and could publish it as complete.
- **`Http::fake()` APPENDS stub sets and the first matching pattern wins.** So a test that fakes an empty answer and later re-fakes a populated one still gets the empty one — the earlier stub is still registered. It reads as a missing feature and invites "fixing" the assertion. Use ONE closure fake driven by state the test mutates (`BunnyIngestTest`, `BunnyDeleteTest`), and `Http::preventStrayRequests()` where the requirement is that no call happens at all (`manifest()` must not touch the network — it runs on every playback request, and a call there turns a provider slowdown into zero viewing instead of degraded viewing).
- **Provider secrets go in the ENVIRONMENT, and the repo's own "operational numbers live in `platform_settings`" rule does not apply to them.** That rule is about NUMBERS an operator tunes from the panel; a `platform_settings` row is readable by everyone who can open that panel, so a signing key there widens who can mint a valid playback token from "whoever administers the server" to "whoever administers a workspace". The size and duration CEILINGS do come from `platform_settings`, through `MediaLimits` — which is also where the adapter's `capabilities()` reads them, so the announced limit and the enforced one cannot drift into two numbers.

- **The npm advisories are accepted rather than fixed, and the guard is CALL-SITE DISCIPLINE — not the config, whatever an earlier version of this note claimed.** They only move with **Next 16**, a breaking upgrade: `postcss` is genuinely pinned inside `next/node_modules`, while `sharp` is Next's hoisted `optionalDependencies` entry at the top level (`npm audit` reporting "postcss" *is* reporting Next's copy; the top-level Tailwind one is patched and separate). ⚠️ **`next/image` optimises same-origin and relative paths with no `images` config at all**, so "no `remotePatterns`, therefore nothing reaches `sharp`" is FALSE — a `/storage/...` path would reach it. What actually closes the path is that `frontend/` contains exactly **three** `next/image` call sites and all three pass literal `/public` paths (`(public)/page.tsx`, `PageBanner`, and `PolicyPlaceholder` through it), the receipt renders as a plain link and never as an image, and `ReviewsTab` / `TestimonialsCarousel` use a plain `<img>` with a comment saying why. **So the invalidation trigger is a call site, not a config key: pass any user-supplied or remote image to `next/image` and the sharp advisory is live and this note is wrong.** Re-count the advisories before trusting the wording — the list has already grown once (three `postcss` path-traversal GHSAs arrived after it was written), which is why this says "the advisories" and not a number.

- **A channel class alone delivers nothing, and the guard is a COUNT.** `NotificationType::defaultChannels()` returned `[InApp]` for all thirty-five types, so shipping `WhatsAppChannel` without touching it would have created no delivery row at all — nothing fails, because nothing runs, and every assertion about the new channel passes by finding nothing to contradict it. - **Every WhatsApp message is an approved template, and `body_ar` is documentation of one — not the text that is sent.** Free-form text is permitted only inside the 24-hour window a user opens *by replying*, and we receive nothing, so that window never opens. What travels is the template NAME (`message_templates.type`) and an ORDERED parameter list (`variables`), read out of the notification payload — the Arabic sentence lives at the provider. So editing `body_ar` from `/admin` changes the notification bell and changes nothing on a phone. **Order is the whole meaning**: a list built by walking the payload, whose key order is whatever a listener happened to write, puts a student's name where the duration belongs in a message to their parent, with no error anywhere. Rows are seeded `pending`, never `approved` — claiming an approval that has not happened turns the first send into a provider error code nobody can map back to a row.
- **The verification code cannot go through `DispatchNotification`, by construction.** `canReach()` asks whether the recipient has a **verified** contact detail, and the code is by definition the message that goes to an **unverified** one — so dispatched normally it is skipped every time, for ever, and no number on the platform can ever be proven. `ContactVerificationController` calls the channel directly through the `SendsVerificationCodes` capability (asked as a capability, not an `instanceof`, so a channel that cannot carry a code simply does not implement it). It writes no feed row: a one-time code has no business in a list a person reads later. ⚠️ This also makes `contact_verification` **the first template that must be approved** — before it, nothing else can be delivered to anyone.
- **A phone number is normalised where it is WRITTEN, never where it is sent**, and read from `contact_verifications`, never from `users.phone`. That column is a free string nobody confirmed, and a typo in it is a message about a child sent to a stranger. `PhoneNumber::toE164()` is Qatar-shaped by design (`libphonenumber` is the world's metadata for one market); the upgrade trigger is a second country, and it is written beside the class.
- **Permanent vs transient is read from the provider's own answer** (`is_transient` in the error body), never from a code list copied into the tree — a copied list ages at the provider's next release and then either drops real messages or burns five attempts and the rate budget on a number the first reply already refused. The rule: a 4xx that is not 429 and does not declare itself transient is permanent; everything else is retried by `DeliverNotificationJob`'s existing backoff.
- **A reversal that shares its original's idempotency key is swallowed for ever.** `award_entries` is written with `insertOrIgnore` keyed on `(student, action_key, source_type, source_id, reversal_of_id)`, and a reversal repeats the first four by definition — so without the fifth column it collides with the entry it is reversing, writes ZERO rows, the read-back finds the ORIGINAL, the code concludes "already recorded" and reports success, and the points are never returned. To anyone watching, FR-010 is implemented. ⚠️ **And the column is `NOT NULL DEFAULT 0`, not nullable**: `NULL != NULL` in a unique index on both engines, so a nullable discriminator stops the guard biting for every ORDINARY award instead — the same event paying twice. Zero compares; the sentinel is the fix (precedent: `concept_stats.lesson_id`). `AwardReversalTest` asserts on the AGGREGATE returning to its pre-award value, never on a row count: counting two rows passes against a design that returns nothing.
- **`WorkspaceScope` is inert for a STUDENT, not merely for a guest — and that is what guards every student route in 009.** A student is a member of no workspace at all (only `AcceptInvitation` and `CreateWorkspace` write that pivot), so `WorkspaceContext::id()` is null and `WorkspaceScope::apply()` returns early adding no condition. `BelongsToWorkspace` therefore protects **nothing** on any route a student can reach: an implicit `{reward}` binding resolves any teacher's reward, and `GET /gamification/redemptions` without an explicit `where user_id` returns every redemption on the platform. The mirror of this is that route-model binding IS safe on the teacher's routes — the reader is a member there, so the scope resolves and a foreign row 404s before any policy runs.
- **The gamification catalogue is reference data, so an empty one awards nothing and every assertion passes against zero.** `AwardPoints` looks an action up by key and returns silently when there is no row — an award for an undefined action is an unfilled catalogue, not an error. `tests/Pest.php` therefore seeds `GamificationCatalogSeeder` before every Feature test, exactly as it seeds the notification templates, and it is deliberately a handful of rows because all ~1,600 feature tests pay for it.
- **The day and week boundary lives in `GamificationCalendar` and reads the EXISTING `sessions.timezone` row.** A third declaration of the platform's timezone is the mistake that lets the daily cap drift away from the class schedule in silence. ⚠️ And `dayBounds()` returns a pair of UTC timestamps, never a string compared against a column: `whereDate()` wraps the column and throws away its index (the `FreezePeriod::covering()` lesson), and `CONVERT_TZ()` returns **NULL on any MySQL without the timezone tables loaded** — the common case on managed MySQL — so the predicate matches nothing, **the cap is never enforced**, and nothing errors. SQLite has no `CONVERT_TZ` at all, so no local test can see it. `format('W')` is banned for the week key: ISO weeks start Monday, so every Sunday would carry a different number from the six days after it and one week would split into two period keys.
- **The focus-timer mute is a filter on the READ, and the design put it in the wrong place.** Spec 009's contract said "a new condition in `DispatchNotification`", and the diagnosis behind it is right — `QuietHours::deferUntil()` returns null immediately for anything that is not an external channel, so the bell has never passed through it. But the notification ROW is written before any channel is consulted (003 FR-007: one record however many channels carry it) and the bell reads that row, not a delivery row — so a check inside the dispatcher could only DROP the message or defer a delivery nothing looks at, and the badge lights either way. `NotificationController::muteDuringFocus()` filters the feed and the unread count instead: it mutes for exactly the length of the session, loses nothing, and needs no column. `isMandatory()` stays the valve.
- **Quiet hours and digesting were written in 003 and never once ran** — both apply to external channels only, and `isExternal()` was false for every channel that existed until 020. They are exercised against the real class in `WhatsAppDeliveryPathTest`, not only against the fake one, for exactly that reason.
- **A permission classified by ABSENCE passes every test it has while guarding nothing.** `taxonomy.manage` shipped in 009 declared, seeded, named in a migration's docblock, and asserted platform-level by `CatalogPermissionTest` — and read by **no file at all**: `subjects` and `grade_levels` had no policy and no screen for the whole phase. `RolePermissionMatrix::platformPermissions()` is `all()` minus everything any tenant role holds, so the classification is perfectly true of a constant nobody calls, and the tenant-side test (`the owner does not hold it`) is *also* true when the answer is "nobody asks". **The check that catches it is the ALLOW direction**: a deny-only test passes just as well against a `Gate::policy()` line that was never added, because Laravel's guesser fails **open** into "no policy applies" — and it fails open exactly when one policy serves two models, which is the shape this repository keeps choosing (`CataloguePolicy`, `TaxonomyPolicy`). ⚠️ And the deny in such a policy's `delete()` is **not** the guard for the person most likely to press the button: `AppServiceProvider`'s `Gate::before` waves a super admin past every policy method, so refusing deletion has to be repeated on the Filament Resource — the same discovery `CreditPackageResource` already wrote down, reached again from a different module.
- **A picker is derived from the AUTHORISER'S OWN PREDICATE, never assembled beside it.** 009 shipped six leaderboard scopes of which five were reachable only by typing a URL, and the obvious fix is the trap: the nearest list the profile screen already holds is the student's coin purses, and a teacher board is authorised on an **active enrolment**. A purse outlives the enrolment (a departed teacher's coins still show, deliberately) and lags it (a fresh enrolment has earned nothing yet) — so a purse-built picker offers boards the API answers 403 and hides boards it allows. `ListLeaderboardScopes` reads `EnrollmentDirectory` exactly as `ReadLeaderboard::workspaceFor()` does, and `LeaderboardScopesTest` walks **every returned option through the real endpoint**, which is what fails if the two spellings drift apart again. Same family as `BookingEligibility`'s host check: two spellings of one question put one answer on the screen and another at the door. The grade option comes from `courses.grade_level` — the column the rollup groups on — not from `student_profiles.grade_level_slug`, which is what the student would call their year and can differ, producing an offered board they are not on. And an empty list is a **teacher**: fetching the board anyway is a 403 about a screen that is simply not theirs, so the page says so instead of showing a refusal.

- **A column added by a migration and not to `$fillable` is a column that silently never gets written — and spec 013 shipped THREE of them on one table.** `date_of_birth`, `dob_is_estimated` and `guardian_contact` landed in the `student_profiles` migration; `RegisterStudent` passes all three to `create()`; mass assignment **discards a non-fillable key in silence** — no exception, no log, a `201` and a profile row with three nulls in it. So the guardian-consent gate FR-009 hangs on the student's AGE never fired for anyone who signed up themselves, the contact they typed for their guardian was thrown away, and the coming-of-age sweep walked an empty set. ⚠️ **Every US1 assertion was correct and none of them could see it**: they were made against the response body and against `parent_student_relations`, and the response echoes what was submitted rather than what was stored. It was found by MEASUREMENT — one `tinker` round-trip — while writing the sweep that reads the column two phases later. `ownership_transferred_at` is deliberately NOT fillable for the opposite reason: it is claimed by a conditional UPDATE, the `captured_order_id` rule. **And the same shape ruins a fixture**: `created_at` is not fillable either, so a test row aged inside a `create()` array is born today, and every retention assertion over it passes against data too young to sweep — proving the opposite of what it claims. Age by query.
- **A `date` column compared against a bare date string is off by one day, and the day it loses is the only one that matters.** The model's date format writes `2008-08-21 00:00:00` into `student_profiles.date_of_birth`, so `<= '2008-08-21'` compares as a STRING and is FALSE for the person born that day: `TransferDataOwnershipJob` skipped them and told them tomorrow — on a date the law attaches meaning to. The predicate is `< (threshold + 1 day)`, which is right on both engines. **On MySQL the `<=` form works**, so no local test of it would ever have disagreed with production; the same boundary already cost `FreezePeriod::covering()` and a settlement close their own fixes.
- **The three expiry behaviours are not interchangeable, and `Anonymise` is unavailable wherever the identifying column is `NOT NULL`.** `exam_attempts.student_user_id` and `attendances.student_user_id` both are, and `->change()` on either re-declares the column and REBUILDS the table on SQLite — a trade this repository has refused twice in writing. So `exam_attempt` expires as `Delete` (its `exam_answers` are already gone at 1095 days, so at five years the row is a bare score naming a person for no reader), while `attendances` anonymises by clearing the FREE TEXT and keeping the row: deleting a seat breaks `ReconcileCreditBalancesJob`'s "one consumption entry per seat" invariant for ever, with no cause anybody can find. ⚠️ **And `Archive` needs a mark or it never converges**: "older than N days" is true again tomorrow, so `media_assets.archived_at` is what stops the same recording being re-archived — and the same file re-deleted at the provider, billed each time — every night, counted afresh in `retention_sweep_runs` each night. `Delete` cannot show that defect in a test, because a deleted row does not come back; the idempotency fixture therefore MUST include an archive category.
- **A legal hold has a FOURTH door, and it is the one with nobody asking.** `PlaceLegalHold` suspends an erasure REQUEST; retention needs no request at all, so a hold that only touched `data_requests` would let the nightly sweep delete the exact rows a court ordered kept — on a schedule, with the hold row sitting green beside it and not one line logged. `RunRetentionSweepJob` resolves the held subject ids once and passes them down through `PersonalDataOwner::expire()`, so `Compliance` still names no module's table and no module imports `LegalHold`. Two shapes of that exemption are traps: on `lesson_progress` it has to run through `enrollment_id` (the table names nobody), and on a nullable column a bare `whereNotIn` spares nothing — `NULL NOT IN (…)` is NULL — while the `orWhereNull` that fixes it ORs at the TOP level unless it is grouped, discarding the age bound and deleting the whole table.
- **Retention on a class recording is a write to the COURSE TREE, and the seventh road to 016's worst defect.** A recording IS a lesson, so expiring the asset without archiving the lesson leaves an item pointing at an id nothing resolves. It is survivable today only because `progressEligible()` drops any lesson carrying a `class_session_id` — make recordings countable tomorrow and every enrolled student is capped below 100% for ever. `FR-031ب` therefore mandates `CourseStructureChanged`, fired **once per COURSE**: fifty recordings ageing out together would otherwise run fifty full resyncs over one identical set of enrolments, which is what actually threatens the sweep's timeout. The dedup lives in the listener, where the courses are known, which is why `Media` announces a BATCH of `(id, owner_type, owner_id)` and each module claims the type it recognises. And `MediaProviderResolver::for()` reads the asset's `provider` COLUMN and makes that class — so a test mock bound to `MediaProviderInterface` is never consulted, the real provider runs, and "no second deletion" passes by counting zero of both.
- **`withoutOverlapping()` on `Schedule::job()` guards the DISPATCH, not the run** — for a queued job that is milliseconds around the push, released long before the worker starts, so last night's sweep still walking when tonight's begins runs two copies over the same rows. `RunRetentionSweepJob` is the one job in `routes/console.php` that departs from the file's idiom: `WithoutOverlapping` as job middleware. ⚠️ **But middleware alone is worse** — its lock does not expire, so a worker killed mid-sweep leaves it held for ever and retention silently never runs again. **`expireAfter()` is the load-bearing half**, not the lock.
