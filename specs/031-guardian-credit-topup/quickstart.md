# Phase 1 · دليلُ التحقّق — وليُّ الأمرِ يشحنُ رصيدَ ابنِه

**Feature**: `031-guardian-credit-topup` · **Date**: 2026-09-08

سيناريوهاتٌ تُشغَّلُ لإثباتِ أنّ الميزةَ تعملُ من طرفٍ إلى طرف. **لا شيفرةَ تنفيذٍ هنا** —
هي في `tasks.md` وفي المرحلةِ نفسِها.

## المتطلّباتُ المسبقة

```bash
cd backend && php artisan migrate        # لا هجرةَ لهذه المرحلة؛ يُتحقَّقُ أنّ الشجرةَ محدَّثة
cd backend && php artisan serve          # :8000
cd frontend && npm run dev               # :3000
```

بياناتٌ مطلوبةٌ في قاعدةِ التطوير: وصيٌّ نشطٌ بصلاحيّةِ «المدفوعات» على طالبٍ **له حساب**،
وذلك الطالبُ له تسجيلٌ نشطٌ في كورسٍ لمدرّسٍ **له سعرُ تسويةٍ معتمَد** (وإلّا لم تُسعَّرْ حزمة).

---

## ١ · المسارُ السعيد (`US1` · `SC-001` · `SC-005`)

1. ادخلْ بحسابِ الوصيّ ← `‎/billing/purchase`.
2. **المتوقَّع**: منتقي طالبٍ فيه اسمُ الابن — لا «لا كورساتٍ مسجَّلاً بها».
3. اختَرِ الابنَ ← تظهرُ **كورساتُه** ← اختَرْ كورساً ← تُسعَّرُ الحزم.
4. اختَرْ حزمةً وارفعْ إيصالاً وأرسِلْ ← `201`.
5. من `‎/orders` بحسابِ الوصيّ: الطلبُ ظاهرٌ، وعليه «لـ {اسم الابن}»، وزرُّ السدادِ متاح.
6. اعتمدِ الطلبَ من `‎/admin` بحسابِ موظّفٍ ماليّ.
7. **المتوقَّع**: رصيدُ **الابنِ** في ذلك الكورسِ ارتفعَ بعددِ حصصِ الحزمة، و**لا حسابَ
   رصيدٍ ولا وعاءَ** باسمِ الوصيّ.

## ٢ · الرفضُ حينَ لا يكونُ الابنُ طرفاً (`US2` · `SC-002`)

بحسابِ الوصيِّ نفسِه، ومعرِّفِ كورسٍ لمدرّسٍ آخرَ لا تسجيلَ للابنِ عندَه:

```bash
# التسعير — يجب ألّا يُعيدَ رقماً
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8000/api/v1/billing/packages?course=$OTHER_COURSE&student_uuid=$CHILD"

# الشراء — يجب ألّا يُنشِئَ صفّاً
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d "{\"course\":\"$OTHER_COURSE\",\"package\":\"$PKG\",\"student\":\"$CHILD\"}" \
  http://localhost:8000/api/v1/billing/purchases
```

**المتوقَّع**: `403` في كليهما، وصفرُ صفوفٍ جديدةٍ في `orders`.

## ٣ · جملةُ الرفضِ الموحّدة (`FR-006`)

كرِّرِ الشراءَ ثلاثَ مرّاتٍ بـ`student` مختلف: طالبٌ ليسَ ابنَك · ابنٌ بلا صلاحيّةِ «المدفوعات»
· معرِّفٌ عشوائيٌّ صحيحُ الشكل. **المتوقَّع**: الجملةُ نفسُها حرفاً بحرفٍ في الثلاث.

## ٤ · المنتقي يطابقُ الخادمَ في الاتّجاهَين (`US3` · `SC-003`)

بحسابِ وصيٍّ لثلاثةِ أبناء: واحدٌ بلا حساب، وواحدٌ بلا صلاحيّةِ دفع، وواحدٌ صالح.

**المتوقَّع**: المنتقي يحملُ **اسماً واحداً**، وهو الوحيدُ الذي يقبلُه الخادم. ووصيٌّ بلا ابنٍ
صالحٍ يرى جملةَ السببِ ورابطَ «المرتبطون» — **لا نموذجَ شراءٍ فارغاً**.

## ٥ · مسارُ الموظّفِ لم يُمَسّ (`SC-004`) — **الحالةُ التي تُنسى**

بحسابِ موظّفٍ ماليّ، من `‎/admin`: امنحْ أرصدةً لطالبٍ **جديدٍ تماماً بلا أيِّ تسجيل**.

**المتوقَّع**: ينجحُ كما كانَ. تغييرُ شرطٍ يتشاركُه بابانِ بلا سيناريو يحرسُ البابَ الآخرَ
هو كيفَ يُصلَحُ عطبٌ بخلقِ آخر.

## ٦ · مسارُ الطالبِ لنفسِه (`SC-007`)

بحسابِ طالبٍ عاديّ: `‎/billing/purchase` ← لا منتقيَ طالبٍ يظهر، والشراءُ يمرُّ كما كان.

## ٧ · الإيصالُ لمن رفعَه (`SC-006`)

بعدَ سيناريو ١، ادخلْ بحسابِ **الابن** ← `‎/orders`.

**المتوقَّع**: الطلبُ ظاهرٌ (هو صاحبُه) و**بلا رابطٍ إلى إيصالِ أبيه**.
